## [Unreleased]

### Added

- Personal assistants: an access log, and import and export of the knowledge base. Every decryption of an assistant's content outside its own turns is recorded in the new table `assistant_access_log` (migration `0102`) with the assistant, the actor, the actor kind (`owner`, `admin` or `system`), an action code, a target that holds only a scope name or counts, and the time; page paths, titles and bodies are never recorded. This covers the owner's reads on the "My assistant" page (including saving settings and switching shift, whose responses carry the decrypted chat lists), the owner reading their own assistant's conversation logs and task details in the admin console, imports, exports and server-side commands; `assistant-keys rewrap --apply` records `cli.rewrap` for each assistant whose data key it rewrapped. The record is committed in the same transaction as the read, so content is not returned when the commit fails, while a failure to write the record alone is logged (`assistant_access_log_failed`) and does not block the read. Owners see their own log under Settings on the "My assistant" page (`GET /api/me/assistant/access-log`), with access by anyone else highlighted; administrators only see `last_non_owner_access_at` on `GET /api/admin/assistants`. Records are kept for 180 days. Sessions created by the admin CLI on behalf of a member (`--as`) can no longer read an assistant's encrypted content: `/api/me/assistant` refuses them (403), and conversation logs and task details read through such a session come back locked exactly as they do for someone who is not the owner, leaving a `system` record (`cli.chatlogs`, `cli.tasks`) for the owner. This is deliberate; ordinary employees' records are unaffected. Owners can import a zip of Markdown files into the knowledge base (`POST /api/me/assistant/import`): each `.md` file becomes a page at its path without the extension, an optional YAML front matter supplies `title`, `summary` and `pinned`, and an optional `followups.json` at the root adds follow-ups. The import previews first (pages to create, replace and skip with reasons, no bodies, pinned pages marked) and writes only after the owner confirms with the digest of that preview; existing pages are skipped unless overwrite is chosen, a preview made stale by a concurrent change is refused (409), and the whole import is one transaction. Archives are read in memory only and are refused when over 20 MB (the upload is read in chunks and cut off with 413 as soon as it passes the limit), over 2000 page files, over 32 MB unpacked, or containing path traversal, symbolic links, encrypted entries, nested archives, files other than `.md` and the root `followups.json`, or text that is not UTF-8; system clutter (`.DS_Store`, anything under `__MACOSX/`, `Thumbs.db`, names starting with `._`) is skipped and counted in the preview instead. `GET /api/me/assistant/export` downloads all pages and open follow-ups in the same format. Runtime nodes need no upgrade; ordinary employees are not affected. See `docs/feishu.md` and `docs/operations.md`.
- Personal assistants have a page of their own and an admin list. "My assistant" (under AI collaboration, visible to every signed-in user) shows the owner their assistant's state, runtime, shift, cold start, today's turns against the budget and message-watch health, lets them clock in, clock out or return to working hours on the spot (the same as saying so in the private chat), and has six sections: what needs the owner (pending approvals with a link to the approval system taken from `TOWER_WEB_URL`, including dispatches to other AI employees that wait for approval; blocked sub-tasks; follow-ups due today), running and recently finished sub-tasks and dispatches with the original brief (a dispatch names the employee it went to, the platform's end-of-day tidy-up is marked as such; running ones can be cancelled and the assistant is told), follow-ups in four categories (tick to finish, snooze, recategorise, drop, add), recently settled approvals in every final state (executed, rejected, withdrawn, failed, expired, voided), the knowledge base (index, read, edit, create, delete; pinned pages are clearly marked, and this page is the only place where pinned pages can be pinned, unpinned or rewritten, each page showing whether the owner, the assistant or an import changed it last; page content is always shown as plain text; the voice page can be regenerated up to 3 times a day once the cold start is over, and a voice page the owner edited is never overwritten; attempts are also limited to 3 an hour and 6 in 24 hours whether or not a round was queued, the request is turned away when the assistant app's Feishu usage is tight or another regeneration is still reading, and the Feishu reads no longer hold the request's transaction), and settings (time zone, working hours and days, focus and ignored chats, a daily turn budget that can only be lowered below the platform default, and shutdown, which requires typing the assistant's name). Someone without an assistant sees how to get one, or why they cannot. The page is backed by `/api/me/assistant`, which only serves the interactively signed-in owner: there is no assistant id in any path, bot tokens are refused, writes need the CSRF header, responses are `no-store`, and administrators calling it get their own assistant or none. Knowledge page paths travel in the request body, never in the URL. After the owner's data key is destroyed only numbers, states and times remain. Every read of personal content through the page writes an `assistant_content_access` log line without content. Platform administrators get "Personal assistants" (under Platform management): owner, state, runtime, shift, cold start, today's turns, items waiting to be handed over, sub-tasks and dispatches in progress, watch health and directories pending removal, with a shutdown button that requires typing the owner's login name; it shows metadata only. The settings page gains a "Personal assistants" form for who may set one up, the allowed AI and their order, per-node concurrency and the default daily turn budget. Conversation logs show "only the person who started this can see its content" for a dispatched turn viewed by anyone but its owner. Needs database migration `0103` (two columns on `assistant_settings`); runtime nodes need no upgrade; ordinary employees are not affected. See `docs/feishu.md` and `docs/operations.md`.
- Personal assistants can ask other AI employees (phase 3). `assistant_ask_bot(bot, question, allow_write=false)` hands one question to an ordinary Feishu employee the owner may use (enabled, accepting help requests, and with the owner on its allowed list or no list at all); `assistant_bot_list` shows who can be asked. A reference that matches more than one employee (two with the same name, or one whose key is another's name) is refused with `bot_ambiguous` and the candidates, to be retried with a candidate's id. The employee runs one turn in a session of its own (task kind `assistant_bot_help`, session key `assistant-help:<id>`) as the owner: business system tokens are issued for the owner and credentials the owner saved with that employee are injected, while Feishu and WeCom personal tools, personal schedules, group document tools, help requests, credential requests and the cloud signing proxy are not offered. Nothing is sent to Feishu during that turn; when the employee needs a confirmation, an authorization, a credential or wants to ask a question, the turn ends as `blocked` with what is needed. The answer is stored encrypted in the assistant's `assistant_jobs` row and returns to the assistant's main session as an `assistant_job_result` turn. Questions are limited to 4000 characters, and dispatches share the sub-task limits (3 in progress, 20 a day, 2 hours each); a dispatch has one round and cannot be followed up. A read-only dispatch needs no approval, also from a turn nobody attends, with one exception: a turn nobody attends cannot dispatch to an employee whose runtime is private and owned by someone other than the assistant's owner (`owner_turn_required`; `assistant_bot_list` leaves such employees out in those turns, and a dispatch that needs approval is refused when it is submitted), because the runtime's owner can read the question on their own node. Every dispatch writes an audit entry (`assistant.dispatch`) without the question; `allow_write=true` always goes to the owner for approval first under a new Tower target system `assistant-dispatch` (add its key to `TOWER_TARGET_KEYS` and register it with comparison turned off); an approved dispatch is not refused by the in-progress and daily limits, though it still counts toward them. With `allow_write=false` the platform refuses writes through the business system catalog proxy for that turn; what the employee does with the owner's business tokens is constrained by its prompt only. The question and the answer stay in plaintext in the target employee's records and on its runtime node, like a private chat with it, and are not destroyed with the owner's data key; in the console only the owner can read them, while the employee's managers and platform administrators see that a dispatch happened (time, requester, status, usage; `content_withheld` on the record) and keyword searches leave these records out. Deprovisioning cancels dispatches in progress and waits for the other side to stop. No database migration; runtime nodes need no upgrade. See `docs/feishu.md` and `docs/tower-approval.md`.
- Personal assistants can hand long investigations to sub-tasks. `assistant_spawn(title, brief)` starts a sub-task that runs under the same assistant record and sandbox but in its own session (`<private chat>#job:<id>`), so the owner's chat is not held up and the owner's messages do not interrupt it. A sub-task is read-only: read-only personal tools plus the knowledge base and follow-ups (pinned pages excluded); it has no write tools, no approval tools, cannot start sub-tasks, cannot start or revoke authorization, and gets no schedule tools. It sends nothing to Feishu: its reply stream is not pushed, there are no progress, completion, timeout or interruption notices, a question it asks through the CLI opens no choice card, and hitting the quota offers no switch card (the sub-task fails with `rate_limited`). Its final answer is stored encrypted and returned to the main session as a separate platform turn (`assistant_job_result`) in which the title, the conclusion and any blocking reason are quoted line by line; anything that needs to be done for others is left to the main session to submit for approval. A sub-task that needs the owner's decision calls `assistant_job_blocked(reason)` and ends as `blocked`. The main session can ask follow-up questions in the same sub-task session with `assistant_job_message`, inspect sub-tasks with `assistant_job_list` and stop one with `assistant_job_cancel`. Limits: 3 running at once, 20 per day started by the assistant (owner's time zone), 6 rounds per sub-task, and 2 hours per round before it fails with `job_timeout`; sub-task rounds count toward the daily turn budget, and turns nobody attends cannot start one once the budget is spent. A result turn interrupted by the owner's message is queued again after at least 60 seconds until it has been delivered once (a result turn that cannot be queued at all is retried after 60 seconds, doubling up to 15 minutes); after 3 real failures it is no longer delivered and stays readable through `assistant_job_list`. Deprovisioning cancels running sub-tasks. The end-of-day compile now runs as a platform-started sub-task instead of a turn in the main session: it does not hold up the owner's chat, sends nothing, is not reported back, and does not count toward the 20 per day; the outcomes of rejected and executed approvals are written into its brief by the platform, since a sub-task has no approval tools. Task kind `assistant_compile` is no longer queued; a compile turn still queued during the upgrade fails as an unknown kind and that day's activity is picked up by the next compile. A platform-started turn that meets a paused runtime after being claimed no longer messages the owner, and a turn recovered after a lost worker no longer records the owner as reachable in that session. `GET /api/admin/assistants` adds `jobs_active`. Migration `0100` adds `assistant_jobs` and a foreign key from `assistant_followups.job_id`. Upgrade the scheduler and workers together; runtime nodes need no upgrade. See `docs/feishu.md`.
- Personal assistants keep working hours and go through a cold start before they begin watching messages. An assistant watches its owner's Feishu messages and hands items back only during the owner's working hours (default Monday to Friday 09:30–19:00, `Asia/Shanghai`; overnight shifts are not supported). The owner switches temporarily by sending `上班` or `下班` (or `/上班`, `/下班`) in the private chat; the platform handles these without the model and replies with the time the switch ends: `上班` lasts until closing time (or local midnight outside working days), `下班` until the next shift starts. To change the time zone, working hours, working days, focus chats (at most 5) or ignored chats (at most 50), the owner tells the assistant, which uses the new tools `assistant_settings_get` and `assistant_settings_update`; both work only in a turn the owner started and return `owner_turn_required` in platform-started turns. When a shift ends the platform dispatches one end-of-day compile per assistant per local day as a system sub-task (its own session, not the main one; it sends nothing to the private chat and is not reported back), in which the assistant files the day's progress, approval outcomes and follow-up changes into the knowledge base; the brief carries counts, ids and statuses plus quoted summaries of the day's rejected and executed approvals, and nothing is dispatched for a day without activity or with the daily turn budget spent. After the Feishu authorization completes, the assistant is usable at once in the private chat, and a cold start begins: the platform reads the owner's own recent messages (last 7 days, up to 8 chats, 200 messages, 300 characters each; messages the platform sent for him after an approval are left out) and has the assistant summarize how he writes, as traits rather than quoted sentences, into the pinned page `profile/voice.md` (a page the owner wrote or imported himself is never overwritten) in a separate session whose only tool is `assistant_voice_save` (new task kind `assistant_cold_start`), a silent turn that sends nothing to the private chat; it then asks four questions on form cards (manager and collaborators, responsibilities, focus chats, working hours and time zone), each of which can be skipped, and sending `跳过` skips them all. Watching and hand-over start once the cold start is completed, skipped, or 24 hours have passed (defaults are kept and the owner is told). Assistants set up before this release are not backfilled: their cold start begins the next time the owner writes in the private chat. The admin list `GET /api/admin/assistants` gains `cold_start` and `on_shift`. Migration `0099` adds progress columns to `assistant_settings`. Runtime nodes need no upgrade. See `docs/feishu.md`.
- Personal assistants hand watched items over to the assistant (phase 2 delivery). Items collected in `assistant_inbox` become a turn in the assistant's main session (task kind `assistant_handover`): urgent items within about 5 seconds, batched and held items when their time comes, at most 30 items a turn and one turn in flight per assistant. Items are marked delivered only when the turn ends well; a turn cancelled by the owner's own message, yielded, paused or failed returns its items for the next turn, and an item whose turns really failed three times is voided. After a turn that did not finish the next one waits 60 seconds, doubling while turns keep not finishing up to 15 minutes, and newly arrived items wait with it, so an owner who keeps chatting is not met by a turn that starts and is cancelled every minute. Items a started turn already showed the model are handed over again with a line saying so and asking the assistant to check submitted approvals and recorded follow-ups before acting, because the interrupted turn's transcript is not guaranteed to carry over. The task payload carries item ids only and the digest quotes other people's text line by line. A daily turn budget per assistant (setting `assistant_daily_turn_budget`, default 200, range 10–2000, overridable per owner) counts turns actually started in the owner's local day; once spent, only urgent items are handed over (up to 20 more turns), the rest wait for the next day and the owner is told once. The assistant's main session starts fresh each day in the owner's time zone. Every 5 minutes the platform, without a model, withdraws pending message drafts when the owner has replied himself, the quoted message was recalled or the chat moved on (counted from the draft's last revision, so a draft rewritten after the owner spoke is not withdrawn for it; in a group "moved on" means a message that mentions the owner, replies to the anchored message, is in the same topic as it, or comes from its sender (when the approval carries a topic, every message other people post in that topic counts, since a third person may already have answered), the same rule the checks before submitting and before executing use (a send anchored on a message that has since been recalled is stale too, reply or not), and a chat causes at most one such withdrawal per 30 minutes, with the reminder batched rather than urgent, so a busy group cannot keep a draft in a withdraw-and-redraft loop), notices messages recalled after they were handed over, and reminds the assistant once a day of "processing" reactions left for 4 hours and of follow-ups due today. Fourteen days before a Feishu authorization turns 365 days old the owner gets a daily reminder in the private chat. Messages the platform sends as the owner after approval are remembered by id (`assistant_sent`) so the watcher does not take them for the owner speaking in person, and a stopping scheduler lets the assistant it is serving commit (up to 20 seconds) so a freshly refreshed token is not lost. `GET /api/admin/assistants` shows today's turns, the budget and the number of items waiting. Requires database migrations `0098` (`assistant_delivery`, `assistant_sent`, `chat_sessions.local_day`, `assistant_inbox.failures`, `feishu_personal_grants.authorized_at`) and `0101` (`assistant_approvals.revised_at`, `assistant_inbox.handovers`, `assistant_delivery.handover_misses` / `handover_retry_at`); runtime nodes need no upgrade; ordinary employees are not affected. See `docs/feishu.md` and `docs/operations.md`.
- Personal assistants watch their owner's Feishu messages. The platform polls Feishu as the owner, without a model: during the owner's working hours each assistant lists chats once a minute (direct and group chats, most recently active first), reads only the chats whose order changed or that turn out to have new messages, plus the owner's focus chats and their recent threads, and grades each message in memory as hand over now, batch for 5 minutes, hold while the owner is active in that chat, or ignore. History is not replayed: a chat seen for the first time (a group the owner was just added to, a chat that dropped out of the cursor and became active again) is read from 30 minutes back, or from the last successful poll if polling had stopped for longer; a chat taken off the ignore list is read from that moment; messages older than 24 hours that were already that old at the last successful poll are never boxed; anything sent after the last successful poll is boxed however long ago that was, so private messages and mentions from a weekend or a leave arrive in the first round back. Chats that do not fit into one round (at most 12 history reads) keep that round's starting point and age cutoff until they are read, so the first morning's overflow is still read from the previous evening. Items to hand over are written to `assistant_inbox` with a summary encrypted with the owner's key, once per message; the watch state itself (how far each chat was read, the previous chat order) is encrypted with the same key; a message recalled before it was handed over voids its item and closes follow-ups it started. Handing items to the assistant comes with the delivery layer. Assistants that are not polling (off hours, paused runtime) refresh the owner's token every 24 hours so the authorization does not lapse. A chat Feishu refuses to read three rounds in a row is set aside for an hour so it cannot stall the rest. Feishu rate limits are now recognised for every employee's personal tools: calls made as the owner return `rate_limited` with the wait from the response header instead of a generic failure, a rate-limited token refresh no longer marks the authorization expired, and assistant provisioning retries a rate-limited authorization step instead of abandoning it. The watch loop counts chat-list and history calls per app, stretches everyone's interval as usage nears the per-minute limit (logging `assistant_watch_budget_tight`) and backs off when limited. `GET /api/admin/assistants` shows each assistant's watch state, last successful poll and last error code. Deprovisioning stops the watch first. Requires database migrations `0097` (`assistant_watch`, `assistant_inbox`, `feishu_rate_usage`) and `0101`; runtime nodes need no upgrade; ordinary employees are otherwise not affected. See `docs/feishu.md` and `docs/operations.md`.
- Personal assistants keep a follow-up list. An assistant records things its owner must not lose track of across days in four categories (waiting for the owner's decision, promised by the owner, waiting on someone else, remind on a date), each numbered per assistant and shown as `F012`, with an optional due date and review date in the owner's time zone. New assistant tools `followup_add`, `followup_update`, `followup_snooze`, `followup_close` and `followup_list` read and write the list without calling Feishu and without approval; a snoozed item comes back on its day, and an item recorded with the message that caused it can be closed automatically when that message is recalled (the detection arrives with message watching). Titles and notes are stored encrypted with the owner's data key; category, status, dates and numbers stay in plaintext. When the owner's data key is unavailable, writing a title or notes returns `content_locked` instead of storing empty content. At most 500 open items per assistant. Migration `0096` adds `assistant_followups`; runtime nodes need no upgrade. See `docs/feishu.md`.
- Personal assistants have a private knowledge base (phase 2). Each assistant keeps pages addressed by path in the new `assistant_pages` table; path, title, summary and body are encrypted with the owner's data key, and a keyed digest of the normalized path (case-insensitive, slashes collapsed) keeps one page per path without revealing which pages exist. The assistant reads and writes them with `notes_index`, `notes_read`, `notes_search`, `notes_write` and `notes_delete`, which need no approval. `notes_write` replaces a whole page and takes the version it read, so a concurrent edit is reported as `version_conflict` instead of being overwritten. Limits are 2000 pages, 20 MB in total and 200 KB per page per assistant; search decrypts that assistant's pages in memory and ranks keyword matches. Pinned pages and an index of all pages are placed in the turn block of the first turn of each main session (passed with the user message, never on the command line); later turns only get a change note when a pinned page was updated. Pinned pages over 24 KB in total are left out and only the index is given. Page content enters the turn block as a quotation: body lines, index lines (path, title, summary) and the paths in a change note are all prefixed with `> ` (carriage returns and Unicode line separators count as line breaks), and the block's bracket characters are replaced, so a page cannot close its own block or pose as a platform rule. Lines the platform writes carry no text from a page. Pinning, unpinning, rewriting or deleting a pinned page works only in a turn the owner started; platform-started turns and sub-tasks get `pin_requires_owner`, while unpinned pages stay writable. Migration `0095` adds `assistant_pages`. Runtime nodes need no upgrade. See `docs/feishu.md`.
- Groundwork for personal assistant phases 2 and 3; nothing changes for users yet. The new table `assistant_settings` (migration `0094`) keeps, per assistant, the owner's Feishu identity recorded when setup completes, the time zone, working hours and working days, and the encrypted lists of focus and ignored chats; assistants that are already set up are backfilled from their latest completed setup. Turns the platform starts by itself (hand-overs, sub-tasks and their results, the end-of-day compile) can carry the owner's personal tools without an inbound message: such tasks can only be queued through one function, run as the owner in the owner's private chat, and every use re-checks the record, the owner's account, directory identity and authorization against the recorded identity. Assistant-only tools on the personal MCP are registered in three groups (`knowledge`, `approval`, `jobs`); knowledge tools keep working when the Feishu authorization changes mid-turn, and a sub-task turn gets only knowledge tools and read-only personal tools. Results of approvals submitted in a platform-started turn are delivered to the owner's private chat, and so is a result whose originating inbound event has been purged in the meantime. Platform-started turns run with nobody present and are held tighter than the owner's own turns: the task queue refuses these task kinds without an inbound event unless they come from that one function; they get no cloud signing proxy, no business system catalog, none of the owner's personal credentials, and no business system tokens (`BOT_TOKEN_*`) or business system MCP servers issued in the owner's name, while environment variables configured on the assistant itself are still passed; of the authorization tools only `feishu_authorization_status` is available (`feishu_authorize` and `feishu_revoke_authorization` return `owner_turn_required`); and they never cancel other tasks in the session: when the owner's message is running or queued they go back to the queue with a growing delay (failing quietly with `platform_turn_yielded` after ten attempts), while a message from the owner still cancels a running platform-started turn. An approval result turn counts as unattended even when it reuses the inbound event of the turn that submitted the approval, so all of the above applies to it as well. Assistants created before migration `0093` have no recorded identity and get platform-started turns only after being set up again. Runtime nodes need no upgrade. See `docs/feishu.md`.
- The approval system can be named in personal assistant messages. With `TOWER_DISPLAY_NAME` and `TOWER_WEB_URL` set, the offer card and the welcome message use that name with a link to it instead of the generic "审批系统", so members know where to sign in and approve. Both are optional; without them the wording is unchanged. See `docs/tower-approval.md`.
- Personal assistants (Feishu, private chat only, phase 1). One shared Feishu app serves everyone: a member who messages it in private chat gets an offer card, and accepting creates an assistant record owned by that member, a per-owner data key and a fresh working directory on an assistant-only runtime instance, then asks for the member's Feishu authorization; the assistant then works in Feishu as that member. Messages, replies, transcripts and approval payloads of an assistant are stored encrypted with the owner's key. Turns run only inside a bubblewrap sandbox on a runtime instance started as assistant-only, with no network except a local proxy to the platform and the model APIs, a login credential narrowed to the access token, and the transcript handed back to the platform after every turn so nothing stays on the node. Write actions do not run directly: each goes to an external approval system (Tower) as a request raised by the owner, and runs only after the owner approves. “停用助理” in the private chat (with a confirmation card), `POST /api/admin/assistants/{bot_id}/deprovision`, or the owner's account being disabled (after 24 hours) stops an assistant for good: running work is drained, pending approvals are withdrawn, the Feishu authorization is revoked, the data key is destroyed and the node deletes the working directory. `GET /api/admin/assistants` lists assistants and their state. Who may open one is set by the `assistant_eligibility` setting, and which AI backends assistants may use by `assistant_backends`. Requires database migrations `0087` to `0093`. Upgrade the platform first, then the assistant runtime instances; ordinary employees and ordinary runtime instances are not affected. See `docs/feishu.md`, `docs/operations.md` and `runtime_daemon/README.md`.
- Feishu group topics have their own sessions. A message in a topic (a Feishu thread) belongs to a session keyed `<chat_id>#topic:<thread_id>`; the main chat keeps `chat_id`. Commands in a topic apply to that topic, and topics no longer queue behind each other or the main chat. The first time someone mentions the employee in a topic while the group's main session is alive, the message is held and a card in the topic asks the sender to choose "独立开启新会话" (a fresh session) or "继承主群会话" (a fork of the group's main session, after which the two go their own way). Not choosing within 5 minutes, or sending another message in the topic, counts as a fresh session; a group with no live main session is not asked. Runtimes fork natively when the node reports the new `session_fork_v1` capability, and only through the group's finished turns, so a turn still running in the group never reaches the topic half done: Claude records where each turn ends and forks with `--resume <group> --resume-session-at <entry> --fork-session --session-id <topic>` (a hidden flag; a rejected point falls back to forking from the end), Codex forks through `codex app-server`'s `thread/fork` with `lastTurnId` before a running turn (falling back to `codex exec fork`), and OpenCode, whose CLI can only fork from the latest message, tells the topic it is waiting and forks once the group's turn ends. Claude and Codex topics start from the group's usage baseline so the first turn does not re-bill the group conversation. When the group session is gone on the node, or the node is not upgraded, the first topic turn gets the group's recent conversation as text instead. Colleague answers, collaborations and stop/reset commands stay with the session they started from. Migration `0086` adds `chat_sessions.forked_from`. Runtime nodes need an upgrade for native forking; the platform works with old and new nodes. See `docs/feishu.md`.

- Long-running Feishu replies show whether the employee is alive. The card's top line is now a status line with absolute times in Beijing time, for example "⏳ 进行中 · 17:20 开始 · 最后动作 17:31（运行命令：等 GitHub Actions 跑完）", and replaces the "思考中..." animation, which patched the card every 3 seconds. The line changes only when something happens: a new action, more than 5 minutes without one ("⚠️ 17:31 后没有新动作"), or a command line that has produced nothing for 15 minutes ("⚠️ 疑似卡住", a warning only; the turn is not stopped). Tool steps say what they are doing, using the node's new `x_summary` on tool calls (Claude Bash's `description`, the Codex command, OpenCode's description or title) or, from older nodes, the command in the tool arguments, all redacted. Known long waits (`gh run watch`, `gh pr checks --watch`, `kubectl rollout status`, `sleep N`) show how long they usually take and when they should end, and are not reported as quiet before then. Turns that end because the worker was lost, the runtime node stopped responding for 2 minutes or disconnected, the hard time limit was reached, or a stream had to be recovered get a red "❌ 已中断：原因" heading, and in group chats the asker is mentioned once. Migration `0085` adds `task_streams.activity`. Runtime nodes need an upgrade for Claude summaries (older Claude nodes show only the tool name); the platform works with old and new nodes.

- AI employees keep their rules in `AGENTS.md` plus `docs/`, and CoreMan backs them up to one shared GitHub repository every day. Employees not in development mode get a fixed prompt section: keep `AGENTS.md` short with an index of rule documents, put each topic's details in `docs/<topic>.md` and read it only when the task needs it, and never write secrets there; it does not apply when the working directory is its own Git repository with a remote. With `RULES_BACKUP_REPO` (`owner/name`) and `RULES_BACKUP_TOKEN` (a token with Contents read/write on that repository) set, the scheduler commits every employee's `AGENTS.md`, `CLAUDE.md` and text files under `docs/` to `bots/<bot_key>/` once a day, in a single commit and only when something changed, with an `INDEX.md` of keys and names. Employees whose working directory is its own repository are skipped; employees that cannot be read keep their previous copy. ### Fixed

- Interrupting a personal assistant no longer drops the day's context. When the owner's new message (or a stop) cancels a turn, the node stops the sandbox and uploads the transcript in the background, and the next turn used to start first, see the handover still pending and switch to a new session. The next turn now waits for that upload before it opens, for at most 20 seconds counted from the end of the cancelled turn, and resumes the same session when it arrives; if it never arrives the turn starts a new session as before. Turns that never reached a node are not waited for.
- Personal assistant cards no longer keep a live button after it has done its job. Clicking "开通" used to answer with a toast only; the callback now also replaces the offer card with one that has no button and says the assistant is being set up (an older copy that is already in progress gets the same replacement). The Feishu authorization card is replaced with "已完成授权。" once the authorization completes; if that update fails it is only logged (`assistant_card_update_failed`) and setup still finishes.
- Personal assistant app permissions now list `im:chat.members:bot_access`. Feishu only delivers `im.chat.member.bot.added_v1` to an app that has `im:chat:readonly`, `im:chat` or `im:chat.members:bot_access`; the documented set had none of them, so an assistant app set up from the documentation was never told it had been added to a group and did not leave. `ASSISTANT_SCOPES` and `docs/feishu.md` are corrected; existing assistant apps need the permission added in the Feishu developer console. No code path changes.
- Codex seat sign-in no longer reports "登录已过期" after a successful authorization. The Codex CLI exits on its own once the device code is approved in the browser, and the node used to discard a login whose CLI had already exited before reading its result, so confirming more than a moment after approving failed even though the seat was signed in. The node now keeps the login until it is confirmed or its 15 minutes run out. Runtime nodes need an upgrade.
- Runtime interruptions no longer count as model failures. Node errors such as `control_lost` still fail the task with `run_interrupted` and retain the node error code, but leave existing model health and model failure history unchanged. The task/chat error records explain that the local runtime abandoned a `control_lost` request and point operators to its control-poll, lease and shutdown logs; the code alone does not identify the underlying cause. A turn that a runtime node reports as failed now keeps the node's error code in the task record (`run_interrupted`) and tells the user the turn stopped partway, that some changes may remain, and how to continue. - Feishu group observing. A new per-employee setting, "Group observing" (`bots.group_observe`: `off` by default, `shadow` or `on`, with a required "Observing scope" `group_observe_scope`), lets a Feishu AI employee see every message in its groups, including other bots', and speak up without being @-mentioned when it is needed; @-mentions are answered as before. Non-mentioned group messages are stored but never start a conversation turn. Each one updates a per-group state and enqueues a delayed `group_observe` task, and only the newest message's task judges once the group has been quiet for `group_observe_quiet_seconds` (default 8, at most `group_observe_max_wait_seconds`, default 60, while people keep talking). The judgement is made on the platform side by the OpenAI Decisions API (`POST /v1/decisions`, model `DECISION_MODEL`, default `gpt-6-luna`, key `OPENAI_API_KEY`), given the observing scope and the last 20 group messages of the last 30 minutes; the employee interjects only when the probability exceeds `group_observe_threshold` (default 0.3). How often it speaks is left to the model. Code only keeps turns from overlapping (no judgement while a reply in that group is queued or running, and an interjection never supersedes another turn), honours "@bot 安静" (mutes it in that group for two hours; "@bot 可以说话了" lifts it), and pauses interjections after `group_observe_bot_streak_limit` (default 6) bot messages in a row since the last human message, so bots cannot talk to each other endlessly. Interjection turns get the recent group transcript and a "be brief" rule in the turn block, send no streaming card and no typing reaction, drop the "reply generated" suffix, and send nothing when the agent answers `<NO_REPLY>` or the turn fails. With observing on, @-mention turns also get the recent transcript. `shadow` only records. Every decision, skipped or not, is kept in `group_observe_decisions` for 30 days and listed under the employee's new "Group observing" tab, where admins mark each one "should" or "should not". Turning it on requires the advanced permission `im:message.group_msg.include_bot:read`, which is requested and reported as missing only for observing employees ("Add permissions" in the Feishu app tab, then tenant admin approval), and a configured `OPENAI_API_KEY`. New endpoints `GET /api/admin/bots/{id}/group-observe/decisions` and `PATCH …/decisions/{decision_id}`. Requires database migration `0070`. See `docs/feishu.md`.

- Scheduled contact sync. - Development mode for AI employees whose working directory is a Git repository. A new per-employee switch, "Development mode" (`bots.dev_mode`, off by default), makes each conversation work in its own worktree at `<working directory>/.coreman-worktrees/<session id>` on the branch `coreman/session-<session id>`. The branch starts from the freshly fetched default branch. The path is fixed per session, so Claude resume keeps working, and a removed worktree is rebuilt from its branch. Skills and `.mcp.json` that are not committed are linked into the worktree from the main checkout and listed in `.git/info/exclude`. The system prompt gains a fixed section telling the employee to commit on that branch, open a pull request with `gh` or `glab`, and leave the merge to a person; it never pushes to or merges into the default branch. Every 30 minutes the runtime node fetches each repository that has used development mode. It fast-forwards the main checkout when that checkout is clean and on the default branch, and removes a worktree and its branch only when the branch is already in the remote default branch (merge commit or fast-forward), the worktree has no uncommitted changes, and it has been idle for 7 days. Unmerged worktrees, pushed or not, are never removed and are left for people to review. When a new session starts, the employee first looks for unmerged `coreman/session-*` branches and open pull requests and, if the request continues one, switches its worktree to that branch. The platform sends `worktree: true` in the chat request and the node rewrites `working_dir`; nodes that are not upgraded ignore it and keep running in the main checkout. Requires database migration `0064`, and runtime nodes need an upgrade. See `docs/features/dev-mode.md`.

- Business system operation catalog, phase 2: proxied calls. A system's new "Token delivery" setting can be switched from "To the runtime" (`env`, the default, unchanged behavior) to "Platform proxy" (`proxy`). A proxied system no longer gets a `BOT_TOKEN_<KEY>`: AI employees call it only through the catalog MCP's new `systems_call` (listed only when the turn has such a system), and the platform issues the member's token on the first call, keeps it encrypted with the task until the task ends and never returns or logs it. Only visible catalog operations are callable. Path and query parameters and JSON bodies are validated against the operation's schemas: types, enums, lengths, bounds, required fields, `additionalProperties` and composition; `pattern` and `format` are left to the system. Path values are encoded as single segments and unknown parameters are rejected. `read` operations run directly. `write` needs the new per-system "Allow writes" switch in the AI employee's system permissions (`bot_system_grants.allow_write`, off by default; `write_keys` in the grants API, kept when omitted). `destructive` and `financial` operations are never proxied. Requests go only to the system's own origin with the pinned transport, no redirects or proxies, a 30-second timeout and at most 5 MiB read. JSON results are trimmed to 100,000 characters (errors to 4,000) starting with long lists, with a hint to page or filter; files return only type and size; a token echoed in a response is redacted. Each task may make 30 proxied calls. Every call that reaches a policy decision is recorded in the new `system_calls` table (system, operation, risk, outcome, status, duration, token `jti`; no arguments or bodies), and proxy tokens are recorded in `business_token_issues` with the purpose `proxy`. The prompt marks proxied systems and says when one cannot be used this turn, for example on a runtime without `systems_catalog_v1`. The compiler moves to version 2, so stored catalogs are fetched again in full on their next check. Requires database migration `0060` after `0059`; upgrade the API and workers, upgrade runtime nodes before switching any system to `proxy`, then grant writes where needed. See `docs/business-system-catalog.md`.

- Business system operation catalog, phase 1. A system's "OpenAPI URL" is now fetched and compiled into an operation catalog that AI employees look up level by level (systems → modules → operations → detail) instead of reading a whole API description: the always-present prompt costs about one line per system, and a typical lookup two to three thousand tokens. Saving a system with a changed OpenAPI URL fetches it once as the saving administrator, "Refresh catalog" on the system form fetches it again, and the form shows the catalog status, module, operation and hidden counts, and the first 20 contract findings. The contract checks follow the published Spectral ruleset rule for rule. Fetching is limited to the system's own origin, pins the connection to the registered host, follows no redirects, ignores proxy variables, gives up after 15 seconds and stops reading past 10 MiB; YAML is parsed with the safe loader and rejected before construction when its aliases would expand past two million nodes; only local `$ref`s are followed, at most 32 deep, and cycles are cut. Each fetch uses a business token of at most 300 seconds issued for the operator and recorded in `business_token_issues` with the new purpose `catalog`. Business tokens still reach the runtime unless the system is switched to proxied calls (phase 2, above). `sitemap_url` is renamed `openapi_url`: the admin API and `$COREMAN_SYSTEMS` accept and return both names for one version, and the old column is kept and written alongside for processes on the previous release. A `token_delivery` column (`env` by default) selects the proxy mode described above. Adds the `pyyaml` runtime dependency. Requires database migration `0059`; run it before upgrading the API and workers. Runtime nodes need an upgrade for the catalog tools; nodes that are not upgraded keep the previous one-line system descriptions. See `docs/business-system-catalog.md`.

- One-time secrets for credential requests. An agent often asks for a secret to configure a system for the member, such as a client secret it should write into a service's configuration, and such a value used to be stored as a personal credential, listed under "我的凭证" (My credentials) and injected into every later turn. - Switching an AI employee between runtime nodes that mount the same shared storage (for example an NFS file system as the project root on every node) no longer copies its working directory. The paths do not have to match, since the same storage may be mounted at a different project root on each node, and the check does not rely on the ownership marker, which `git clean -x` can delete. The source node, which created the file, deletes it afterwards. The link pattern used to swallow those characters into the document token, so the link was dropped, the bot could not ask the speaker for consent, and it asked them to resend the links on separate lines. Tokens now stop at the first character that is not a letter or digit. No database migration.

The recent group transcript looked people up by `open_id`, which Feishu issues per app, so a message received by the AI employee's own app never matched the `open_id` stored by contact sync and every person showed up as "colleague N"; the judgement therefore could not tell, for example, that the person the employee assists was asking. The decision instruction also treats a last message that calls the employee by name ("<name>, are you there?", "<name>, take a look") as looking for it, even when it only asks whether it is there; on the earlier 65-case set this added no wrong interjections. No database migration.

- Feishu card subtitles no longer get cut off on phones. Feishu shows a header subtitle on one line and offers no way to expand it, so a `card:header` subtitle is now the first line of the card body in grey text, where it wraps. The rich-card prompt also asks for a short header title and puts figures and details in the subtitle, a callout or the body. No database migration; runtime nodes need no upgrade.

- Codex usage limits now get the same handling as Claude ones. The rate-limit check only recognized Claude's notice (`You've hit your limit · resets …`), while Codex reports `You’ve hit your usage limit.` (with a curly apostrophe, or `… usage limit for <model>`) as a `[codex error]`, so Codex employees that ran out of quota got neither the quota table nor the switch card. Both notices are now recognized; the card still offers only another Codex runtime. The receipt after a successful switch no longer says the conversation was reset, since conversations are carried over; it now asks the user to resend the message that was cut off by the limit. When a switch or another workspace operation is refused because the employee still has running tasks, the reason now lists them, for example "机器人还有任务在执行（对话 2 个、定时任务 1 个）…" (conversations, scheduled runs, skill installations, other tasks), instead of only asking to wait. No database migration, and runtime nodes need no upgrade.

- Multi-select search boxes in the console no longer keep the typed keyword after an option is picked, so typing a pinyin or name fragment, picking a person and searching again no longer means deleting the old text first. This covers the member picker (AI employee members, approvers, allowed users and Feishu app visibility), the allowed AI employees of a business system, and a skill's environment groups. No database migration.

- A failed runtime switch no longer leaves the AI employee silent. When moving the working directory or memories failed, the switch kept the current runtime and directory ("迁移失败，原绑定已保留", original binding kept) but set `bots.workspace_state` to `failed`, and workers only claim tasks of employees whose workspace is `ready`. Every later conversation and scheduled run of that employee stayed queued without an error or a reply until an administrator clicked "初始化 / 重试" (Initialize / retry) in the workspace panel. A failed switch now puts the employee back to `ready` on its current runtime, keeps the phase and reason in the workspace panel (`workspace_phase`, `workspace_error`), shown as a warning, and releases the target directory it had reserved, so the target runtime is no longer reported as having an employee moving in. Retrying is still "Switch runtime", and a successful switch clears the message. A failed workspace initialization is different: the employee's own directory cannot be used (for example `AGENTS.md` and `CLAUDE.md` disagree, or the runtime is too old), so its tasks are still held, as they are for an employee without a runtime (`pending`). Such employees are now marked "工作目录未就绪" (Workspace not ready) in the AI employee list, and the detail page says that messages and tasks stay queued, shows the reason and opens the workspace panel. While the workspace is not ready, installations that were queued and never claimed no longer block them; such an installation runs after a successful initialization and fails as "target changed" if the employee moved to another runtime or directory in the meantime. Employees left in `failed` by a switch before this release need "Initialize / retry" once. No database migration, and runtime nodes need no upgrade. See `docs/memories.md`.

- Runtime nodes looked for Claude Code memories under the working directory path with only `/` replaced, but Claude Code replaces every character that is not a letter or digit. For working directories whose names contain `_`, `.` or similar characters, memories were never collected and memories deployed on a runtime switch landed where Claude Code never reads them. Nodes now use Claude Code's naming. Runtime nodes need an upgrade.

- Claude usage on resumed conversations is no longer counted as the whole conversation so far. When Claude Code resumes a session (`--resume`), the `modelUsage` and `total_cost_usd` of its result are running totals for the session (bare `usage` stays per turn but leaves out sub-agents), and the Claude driver recorded them as the turn's usage. Every turn therefore re-counted all earlier ones, so token totals in chat logs and on the statistics page grew roughly with the square of the conversation length; one 23-turn conversation was recorded as about 1 billion tokens. The driver now keeps each session's last cumulative figures in `claude_usage.json` in the relay session directory and reports the difference, per model and for cost. A new session starts from zero. A resumed session without that file (the session directory was cleaned up after 72 hours idle, or the first turn after the upgrade) reports the bare per-turn usage for that one turn instead of the cumulative total, dropping sub-agent tokens once. Existing chat log rows are not changed. Runtime nodes need an upgrade; no database migration.

- The Feishu gateway uses far less memory per bot. It still runs one process per bot, but the processes are now forked from a forkserver that has already imported the Feishu SDK (whose package import loads every Open Platform API, about 10,000 modules) and frozen the garbage collector, so they share those pages instead of each importing them again. Measured in the runtime image with 7 bots: about 330 MiB in total instead of about 1,250 MiB. Restarts are faster too, since a new bot process no longer spends seconds importing. Previously, with a 1.5 GiB container limit, seven bots left almost no headroom and the gateway could be OOM-killed in a loop, disconnecting every Feishu bot each time. No database migration and no configuration change.

The answer must be a bare JSON object that the platform parses, and those sections asked for Markdown or card blocks instead, so a model that followed them made the collaboration fail with "协作伙伴未提交完整结果".

- Quoting a message on Feishu now gives the model what the message says. Since replies became Card JSON 2.0 cards, quoting a reply older than an hour showed the model only Feishu's "请升级至最新版本客户端，以查看内容" (upgrade your client to view this) placeholder: the streamed reply state that held its text is dropped an hour after the reply ends, and Feishu's message API returns that placeholder for 2.0 cards unless asked for the original card. The gateway now keeps the text of every message a bot sends in `feishu_sent_messages` (a streamed card when its reply ends), kept 90 days like inbound events, and the worker reads quotes of the bot's own messages from there. Other messages are read with `card_msg_content_type=user_card_content`, and the placeholder is never passed off as content. Quotes now cover cards (1.0, 2.0 and template cards, including table rows, chart data and button labels; table cells read back this way come in Feishu's rendered form, not as sent, and are read as text), rich text with its title, mentions by name, files, merged forwards (one line per message with the speaker's name where the directory knows it), calendar events, tasks, votes, locations, contact cards and system messages; voice, video and stickers get a one-line note. Pictures and files in the quoted message are now downloaded like the current message's attachments, through the official resource API with the quoted message's ID, which the fetcher allows only after checking that it is in the same chat. When the API refuses, for example in a group without the `im:message.group_msg` permission (not requested by QR-created apps), the text comes from the inbound event if the bot received the message. A recalled message is marked "[引用的消息已撤回]" (quoted message recalled) and anything else unreadable "[引用消息内容不可用]" (quoted content unavailable). Requires database migration `0052`. See "引用消息" in `docs/feishu.md`.
- Replies ran every message of a turn together into one paragraph. When the model writes a few words, runs a tool and writes again, the relay streams the texts back to back with nothing between them, so a Feishu card or WeCom reply that spanned several tool calls read as one block with sentences glued end to end. Text that resumes after a tool call now starts a new paragraph (a blank line, counting any line breaks already there), in chat replies, background progress pushes and scheduled-run results alike.
- Signed-in administrators could no longer save anything seven days after logging in: every write request failed with "CSRF 校验失败" (CSRF check failed) while pages still loaded. The console session is renewed on use, but the CSRF cookie was only set at login with a fixed seven-day lifetime. It is now renewed together with the session, keeping its value, and a live session that has lost it gets a new one on its next request, so people already affected only need to reload the page instead of signing in again.
- "Add partner" on Collaboration partners showed nothing at all when there was no other Feishu AI employee to choose, which looked like a broken search. The drawer now says so, and that this list only holds AI employees (colleagues are added under Colleagues); the wording no longer says "Feishu partners", which read as directory members.

Catalog sync and skill installation both use it; installation needs the runtime nodes upgraded, since older nodes keep sending `oauth2`. A failed clone that ends in Git's "could not read Username … terminal prompts disabled" is now reported as an authentication failure that points to the token and the username, instead of the generic "cannot sync source" message. Requires database migration `0047`.

### Security

- Service logs no longer contain live platform credentials. httpx wrote one INFO line per outbound request with the full URL, and WeCom takes `access_token`, `corpsecret` and the OAuth `code` as query parameters, so every API call put a working token into the API, worker, scheduler and gateway logs. The `httpx` and `httpcore` loggers are now held at WARNING in every process, including when `LOG_LEVEL=DEBUG`. As a fallback, every log line, traceback and uvicorn access log line has credential-style query values (`*token`, `*secret`, `*ticket`, `code`, `key`) replaced with `***`; this also covers the request URL that `raise_for_status()` puts in its error message. Rotate WeCom app secrets if old logs may have been read by others.

- The process settings object no longer prints secrets. `DATABASE_URL`, `MASTER_KEY`, `MASTER_KEYS_PREVIOUS`, `SESSION_SECRET` and `BOOTSTRAP_ADMIN_PASSWORD` were plain strings in the settings `repr`, so any code that put the settings object into a log line or an error message showed them in clear text; passing it to SQLAlchemy's `create_async_engine` by mistake, for example, raises an `ArgumentError` that quotes the whole object. These fields are now left out of `repr` and `str`; the S3, JWT signing, token provider and cloud proxy credentials were already hidden. No configuration change or migration. If such output may have been seen by others, rotate the affected values.

- Speakers can view their own private chat sessions (Feishu and WeCom) after signing in, whatever their role. Forwarding the link to someone else, opening it with a bot token, or a session that also holds another person's messages all fail. Replies also carry an encrypted link bound to the speaker, the session and the runtime node, valid for 24 hours; it proves ownership before the first turn has been logged. Opening a link while signed out goes to the sign-in page and comes back afterwards; inside the Feishu client, the sign-in page starts Feishu sign-in straight away, as it already did for WeCom. Every opened session page is audited as `runtime.session_view`, recording whether the link, the owner or the viewer's role granted access. Speakers who are not administrators can view only once the node's runtime is upgraded and reports `owner_session_view_v1`. Older runtimes still record environment variables, so until then only administrators can.
- Members can create their own scheduled AI tasks by asking a Feishu bot in a private chat, for example "每个工作日 9 点总结我的飞书未读消息". The assistant drafts the name, schedule and instruction with `schedule_propose`, and only the member's click on the confirmation card creates the task. Anyone allowed to use the bot can do this without being a bot administrator; each member can keep 10 active tasks per bot, recurring runs are at least an hour apart and one-off runs are between a minute and 30 days away. Tasks run as their owner and deliver only to the owner's private chat. The "我的提醒" page becomes "我的定时任务" and lists these tasks next to one-off reminders, with pause, resume, delete and the latest result. Bot administrators see them on the scheduled tasks page, marked as a member's own task, and can only disable them. Requires database migration `0037`.

### Changed

- Creating a WeCom AI employee with a manually entered Bot ID and Secret now verifies them with one long-connection subscription before saving, just like QR-created bots, and rejects credentials that WeCom refuses (HTTP 422) or cannot be checked (HTTP 502). Editing an existing employee's credentials is not verified, so the live connection is not kicked off.
- "Test as myself" on business systems no longer reports a failure just because the home page redirects after sign-in. It now requests the address once without the token and once with it: a 2xx, or a redirect to somewhere other than the unauthenticated destination and not a login page, counts as the token being recognized, and the message names the path it landed on. Redirecting to the same place or to a login page counts as not recognized, and a home page that opens without a token is reported as inconclusive. The response adds `baseline_status_code` and `redirect` (host and path only).
- Business system tokens now use the speaker's email prefix (lowercased) as `sub`, which is how business systems usually look up their own accounts. A login name is generated only on the first contact sync and falls back to the platform user ID when no email was available then, so Feishu members synced without the `contact:user.email:readonly` permission got tokens that business systems could not match. A user without an email, or whose email prefix another account also uses, gets no business system tokens, and the assistant is told to ask them to add an email or contact an administrator; falling back to the login name could give two people the same `sub`. `bot_token` sign-in looks users up by the same rule. The access test reports the token user it used.
- Connecting Feishu now adds tools to the ordinary assistant instead of switching a private chat into a separate personal-data mode. After a member connects, their private chats with that bot keep the bot's prompt, skills, business system access, memory and sessions, and also get tools to read their own Feishu messages, meetings, minutes and documents (and to send messages at the top tier). The "普通助手" and "飞书资料" switch commands are gone and those words are ordinary messages again; group chats still never get the tools. These conversations are stored and resumed like any other private chat and only their owner can view them, replacing the memory-only sessions and context-bound links that `main` had after 0.1.0. Scheduled tasks that their owner created, runs and receives alone may use the owner's authorization too; such runs are visible only to that person, including in chat logs and run history. Runtimes must report the new `feishu_personal_tools_v1` capability, which both the Claude and Codex drivers now do; the old `feishu_personal_restricted_v1` is no longer used, and a bot on an older runtime keeps answering without the personal tools. Requests like "每天……提醒我……" now reach the assistant, which can offer a scheduled task, instead of getting the one-off reminder help text.
- Group chat sessions are still viewable only by `ai_committee` and `platform_admin`, and administrators can still view WeCom private chats of other people. Administrators still cannot view other people's Feishu private chats.
- The `feishu_login_unknown_user` and `wecom_login_unknown_user` log events include the platform `user_id`, so a rejected sign-in can be traced to a person.
- The skills dialog on the employee page keeps every row on one line: skill descriptions and install errors are truncated and shown in full on hover, like the skill catalog, and long names, versions and labels are shortened with an ellipsis instead of wrapping.
- The create employee form now defaults to Feishu and shows only the key, name and runtime; the runtime is required and other settings keep their defaults under "More settings". The edit form is unchanged.
- QR-created Feishu agents get the built-in slash commands `/new`, `/stop`, `/sessions`, `/connect` and `/help`; other Feishu bots can add them from the Feishu app page, where "Add built-in commands" also adds `/connect` to bots that already have the others. Built-in commands, including `sessions`, now also match when sent with a leading slash. `/connect` does the same as sending "连接飞书" (Connect Feishu); a bare `connect` without the slash is still an ordinary message.
- The Feishu app permission list also requests `vc:meeting.meetingevent:read` and `im:chat.members:read`, and no longer reports protocol grants such as `auth:user.id:read` as missing.
- When a runtime is already installed, the installer now names the platform each side connects to and prints commands that run as pasted. The previous hint left out the change into the release directory, so it failed with `No module named 'runtime_daemon'`, and it suggested purging the node even when the service alone had been removed.
- Container images keep `/app` owned by root and read-only and precompile the application's bytecode at build time. Base images are pinned by digest (Dependabot bumps them), and uv's download cache stays out of the image. A release that changes only code now adds about 8 MB per image instead of rewriting a layer of more than 300 MB, and the dependency layer shrinks from 444 MB to 265 MB.
- Installing a skill no longer depends on the runtime node Git host allowlist: sources registered in the skill catalog install on any node, so internal Git servers such as a company GitLab work without editing the node configuration. The allowlist (`git_hosts`) still limits pulling, pushing, backing up and opening pull requests in employee workspaces, and it can now be set when creating an install link under Advanced settings. Runtime nodes need an upgrade to pick this up.
- The README leads with what CoreMan does, a diagram of chat, CoreMan and the runtime, and a four-step quick start with screenshots: start CoreMan, connect a runtime, create an AI employee by scanning a QR code and chat with it. Local development notes moved to `docs/development.md` (Chinese) and `CONTRIBUTING.md` (English).
- An AI employee can take over an existing bot directory that another bot system still uses, for example one shared by several instance users, and keep sharing it with that system. "Use existing directory" when switching runtimes now accepts a directory that no AI employee has claimed (no `.coreman-workspace.json`) and says it will be taken over; a directory claimed by another employee is still refused. Taking over leaves the files as they are: an `AGENTS.md -> CLAUDE.md` layout (with `CLAUDE.md` tracked in Git) is kept instead of being turned around, a lone `CLAUDE.md` gets an `AGENTS.md` link instead of being moved to `CLAUDE.md.preserved-N`, and in a Git work tree the ownership marker is listed in `.git/info/exclude` so a deployment's `git clean -fd` does not delete it. Editing files in the workspace keeps their permissions and group, and new files take the umask or the directory's default ACL instead of `0600`, so other instance users sharing the directory can still read them. Runtime nodes need an upgrade to pick this up; older nodes can still only reuse a directory the employee already owns.

### Fixed

- Runtime session history no longer records a request's environment variables. They carry bot secrets and access tokens, and until now they were written to the node's session logs and streamed to the session page. Runtime nodes need an upgrade; logs written before then expire within the usual 72-hour cleanup.
- A failed skill installation now says why in the skill management dialog instead of always showing "安装未完成". Runtime nodes return the Agent's fixed error message (for example "工作目录不存在", or "Git 来源不在白名单内" from nodes that predate the change above, shown with a hint to upgrade the node or add the host to `git_hosts`) as an `operation_failed` result and write it to `runtime.log`; command output, paths and credentials are still never returned or logged. Checks that fail before anything reaches the node say that nothing was executed, and the worker logs every failure with the task, bot and skill IDs and an error code. Older nodes still report only `execution_failed`; the dialog then points to the node's `runtime.log` and suggests upgrading the node.
- Installing a skill from a private repository that needs the source's access token failed with "操作失败（退出码 128）" on runtime nodes with Git older than 2.31. The token was passed through `GIT_CONFIG_COUNT`, which older Git silently ignores, so the clone was sent without credentials. The node now hands the token to Git through `GIT_ASKPASS`, as workspace Git operations already did, and passes the other settings with `git -c`, including an empty `http.proxy` so the token never goes through a proxy set in `~/.gitconfig`. Runtime nodes need an upgrade.
- The "可安装技能" heading in the skill management dialog no longer sits right under the installed skills table.
- A runtime node could pick up a new request up to a second late. The caller renewed its lease on every read, which briefly locked the request just as the node's long poll, woken by the new request, tried to claim it and skipped it. The lease is now renewed every 10 seconds.
- The runtime install dialog shows the whole hint about replacing an existing runtime with `| sh -s -- --replace`. Its message contained literal `|` characters, which vue-i18n treats as plural separators, so the Chinese hint read only "sh 换成".

### Security

- The line that tells the model who is speaking now carries a random tag generated for each turn (`[SYS_USER:<tag>]`), and a fixed rule that administrators cannot override says that only the line with the current tag identifies the speaker, with the `COREMAN_USER_LOGIN` and new `COREMAN_USER_SUBJECT` (the token `sub`) environment variables as the authority. Before, a file, web page, memory or tool output could print an identical `[SYS_USER]` line. `COREMAN_USER_SUBJECT` is a reserved request-level key.
- Credential values from the turn's environment, and anything shaped like a JWT, are replaced before model output reaches chat replies, streamed text, the thinking panel, question cards, chat logs and scheduled task results. A model repeating a token no longer shows it to everyone who can read the chat. Question card snapshots no longer store the prompt.
- An expired `bot_token` cookie no longer locks out a signed-in administrator. Authentication falls back to the console session and clears the dead cookie, and write requests then pass the standard CSRF check.

## [0.1.0] - 2026-09-16

First public release.

The Changed, Fixed, Security and Removed sections describe differences from the initial public snapshot (`bfdd299`, 2026-09-14) for deployments that tracked `main` before this tag. Such deployments must run database migrations up to `0028` and upgrade Runtime Daemon drivers together with the services; older drivers keep serving chat but do not support collaboration tools, detailed process output or workspace operations.

### Added

- WeCom integration through smart robot long connections and Feishu integration through custom app long connections: streaming replies, images and files, quoted messages, interactive question cards and welcome messages.
- AI teammate (bot) management: prompts, models, runtime binding, working directories, collaborators, usage allowlists, team ownership and encrypted credentials and environment variables.
- Runtime Daemon for Linux and macOS (amd64/arm64): connects outward to CoreMan, discovers Claude Code and Codex CLIs, runs requests through bundled Go drivers, reports health and quota, and supports install links, private CAs, in-place upgrade and uninstall.
- Teams, users and roles (platform administrator, AI committee, team lead, member), WeCom and Feishu sign-in, directory sync, bootstrap administrator and audit logs.
- Scheduled tasks with pre-check scripts and result delivery to private chats, group chats, email and WeCom group robot webhooks.
- Human escalation API with WeCom app and Feishu delivery, reply callbacks, queuing, reminders and follow-ups.
- Skill catalog synced from Git plugin marketplaces, environment presets, approval workflow and persistent installation tasks.
- Memory sync between runtime nodes and the admin console, including memory transfer when a bot switches runtime.
- Business system grants with per-request ES256 `BOT_TOKEN_<SYSTEM>` tokens and a public JWKS endpoint; signed infrastructure API for directory, push, notification and runtime telemetry.
- Chat logs, usage statistics with model pricing, bot health reports, announcements and runtime status with lease, queue, task and outbox views.
- Self-hosted deployment with Docker Compose and Caddy: PostgreSQL-backed task bus with leases and outbox, a/b gateways and workers, drain-based rolling upgrade and rollback, optional S3 attachment storage, Prometheus metrics and alert notifications.
- Admin console in Chinese, Japanese and English.
- Feishu bot collaboration (limited trial): administrators configure directed partner relationships, and in Feishu group chats an AI teammate can search for, inspect and ask a partner for help through a task-scoped MCP endpoint. The partner answers in the group and the original teammate resumes its runtime session. Membership and permissions are checked on every request, and the server enforces a single hop and tool call budgets.
- Feishu replies show a typing reaction while a message is handled, a collapsible thinking panel with an animated heading, and detailed tool and process output from the Claude Code and Codex drivers. The reaction needs the `im:message.reactions:write_only` app permission.
- Workspace management for AI teammates: browse and edit runtime files from the console, back them up to Git, initialize `AGENTS.md` (with `CLAUDE.md` linked to it), and move files and memory to the new runtime (copy, Git or existing directory) when switching runtime nodes.
- Scheduled runs add an overridable "scheduled task constraints" prompt section (`prompt_cron_mode`), editable in Settings.
- Scheduled pushes carry a header (task, bot, duration) and a footer. Jobs without any delivery target send the result to the job creator.
- A separate completion reminder after streamed replies that take 60 seconds or longer, so the chat client notifies the user.
- Allowlist denials are logged as warnings and counted by `coreman_whitelist_denied_total{reason}`.
- Escalation create and poll responses include `delivery_failed` and `failure_reason`.
- WeCom setup and troubleshooting guide (`docs/wecom.md`), a glossary (`docs/glossary.md`), a service topology diagram in `docs/architecture.md`, and an English README (`README.en.md`).
- Trust model and threat boundaries in `SECURITY.md`.

### Changed

- The bundled Claude driver now reports native Claude Code model names (`claude-sonnet-4-6`, `claude-opus-4-6`, `claude-haiku-4-5-20251001`) instead of names with a `vllm/` prefix. The prefix never had a functional meaning: the driver strips anything before the last `/` before calling the CLI. Migration 0023 renames the seeded `vllm/claude-*` catalog entries, prices and bot models to the native names.
- A run waits up to 120 seconds in the queue of a full runtime node instead of failing after the 10-second connect timeout. Reverse-channel calls expire after the bot's timeout (up to 12 hours) instead of a fixed 2 hours, and scheduled runs are no longer capped at 2 hours.
- Gateways drain bots in paced batches that fit the stop grace period.
- New business systems allow no bots until an administrator selects them, and the `coreman` system key is reserved.
- API containers trust forwarded client addresses only from the Caddy network (`COREMAN_EDGE_SUBNET`, default `10.250.250.0/28`).
- Scheduled results longer than 100,000 characters are truncated instead of failing the run.
- A new message in a session whose previous turn is still stopping waits and is re-queued instead of failing with "session busy".
- Database engines use a 10-second connect timeout and a 300-second statement timeout.
- Optimistic-lock conflicts return HTTP 409 with the dedicated code `40901`.
- Documentation opens with user-facing descriptions instead of release status notes.

### Fixed

- Escalations whose question notification cannot be delivered are cancelled instead of waiting until they expire.
- WeCom `gettoken` credential failures are cached briefly instead of being retried on every request.
- `deploy/coreman` refuses to generate new secrets when a PostgreSQL data volume already exists.
- The users page still loads when the team list request fails.
- Audit entries for skills, memories, the skill catalog and runtime nodes record the client IP.
- Listing a bot's skills no longer locks the bot row.
- Claude Code context compaction no longer trips the resume watchdog on long sessions.

### Security

- Bot, environment preset, skill and MCP environment variables can no longer set runtime control variables such as model endpoints, loader hooks, proxies or CLI configuration directories. The Runtime Daemon enforces the same list.
- The application refuses to start with a template or short bootstrap administrator password.

### Removed

- The generated `docs/environment-creation/manual.html`; use `docs/environment-creation/README.md`.
- Unused compatibility routes `/api/robot/memories/*`, `/api/robot/wework-notify`, `/api/robot/organization/tree`, `/api/organization/full`, `/api/push` and `/api/test/bot-token-access`. The remaining escalation compatibility routes require signed requests and no longer accept a plain `X-API-Key` secret.
- The `cron` infrastructure API scope, which no route used, and the `ETEAMS_` reserved environment prefix.
- The `RELAY_NETWORK_MODE` and `TIMEZONE` settings.
- `system_grant_audit` is no longer written (grant changes are recorded in `audit_logs`) and `bots.custom_command_modules` is no longer read. Both will be dropped in the next release.

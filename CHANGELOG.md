# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Business system operation catalog, phase 1. A system's "OpenAPI URL" is now fetched and compiled into an operation catalog that AI employees look up level by level (systems → modules → operations → detail) instead of reading a whole API description: the always-present prompt costs about one line per system, and a typical lookup two to three thousand tokens. Saving a system with a changed OpenAPI URL fetches it once as the saving administrator, "Refresh catalog" on the system form fetches it again, and the form shows the catalog status, module, operation and hidden counts, and the first 20 contract findings. The contract checks follow the published Spectral ruleset rule for rule. Fetching is limited to the system's own origin, pins the connection to the registered host, follows no redirects, ignores proxy variables, gives up after 15 seconds and stops reading past 10 MiB; YAML is parsed with the safe loader and rejected before construction when its aliases would expand past two million nodes; only local `$ref`s are followed, at most 32 deep, and cycles are cut. Each fetch uses a business token of at most 300 seconds issued for the operator and recorded in `business_token_issues` with the new purpose `catalog`. Turns whose runtime declares `systems_catalog_v1` get a task-bound `coreman_systems` MCP (`COREMAN_SYSTEMS_MCP_URL`, `COREMAN_SYSTEMS_MCP_TOKEN`, both reserved) with `systems_browse`, `systems_search` and `systems_describe`; it reaches only the systems the turn already has, hides operations the member's permission codes do not cover when the system declares a permission lookup, marks every result as system-declared text, allows 40 calls per task with at most two identical ones, and rechecks a catalog older than ten minutes with `If-None-Match`, keeping the last good catalog when that fails. `systems_describe` returns a curl template that refers to `$BOT_TOKEN_<KEY>` by name. Business tokens still reach the runtime as before. `sitemap_url` is renamed `openapi_url`: the admin API and `$COREMAN_SYSTEMS` accept and return both names for one version, and the old column is kept and written alongside for processes on the previous release. A `token_delivery` column (`env`, not yet editable) prepares the proxy mode. Adds the `pyyaml` runtime dependency. Requires database migration `0059`; run it before upgrading the API and workers. Runtime nodes need an upgrade for the catalog tools; nodes that are not upgraded keep the previous one-line system descriptions. See `docs/business-system-catalog.md`.

- Business system integration spec. The system form's "Navigation URL" field is now "OpenAPI URL" and links to the integration spec: a contract (OpenAPI 3 plus `x-permission` and `x-agent` extensions) that a business system follows so AI employees can later discover its operations on demand instead of reading a whole API description. The spec and a Spectral ruleset for checking a description in CI are published with the admin console at `/integration/business-system-openapi-contract.md` and `/integration/business-system-contract.spectral.yaml` without login, so administrators can hand the link to the team integrating a new system; the drawer on the form shows the spec, copies the link and downloads both files. How the platform reads the description is described in the operation catalog entry above. No database migration.

- Organization background in Settings. Platform administrators can describe the company once, such as what it does, its business lines, common terms and the business time zone, instead of repeating it in every AI employee's prompt. The text (`prompt_org_context`) goes into the system prompt of every employee, in chats, scheduled runs and health checks, right before the employee's own prompt, which can add to or refine it. It is empty by default and left out entirely while empty; unlike the other prompt sections it may be cleared. It sits outside the collapsed prompt sections on the Settings page. No database migration.

- Business token issuance records. Each issued business-system token is recorded in `business_token_issues` with its purpose, task, AI employee, user, system, provider, expiry and token id (the JWT `jti`; empty for opaque external tokens), never the token itself. Administrators can filter conversation logs by a token id copied from a business system log, and the conversation detail lists the tokens issued for that turn. Migration `0058` is required. See `docs/business-token-providers.md`.
- Per-system business token providers. Deployments can configure named HTTPS issuers in `BUSINESS_TOKEN_PROVIDERS`, then choose a provider, audience and protected access-test API per system. CoreMan requests a token for the verified speaker using HTTP Basic and configurable form fields, with a lifetime bounded by the task timeout and the provider’s optional maximum. Responses are passed through unchanged as Bearer credentials, with actual expiry metadata; removed or failing issuers never fall back to local signing. Existing systems default to `builtin` and retain their keys, claims and Cookie flow; business token lifetimes now match task timeouts without the previous 300-second grace. Migration `0057` is required; upgrade all API/worker processes before enabling external providers. Running CLI processes do not refresh expired tokens automatically. See `docs/business-token-providers.md`.

- One-time secrets for credential requests. An agent often asks for a secret to configure a system for the member, such as a client secret it should write into a service's configuration, and such a value used to be stored as a personal credential, listed under "我的凭证" (My credentials) and injected into every later turn. The request body now takes `save`: `true` keeps the old behaviour for the member's own accounts and keys; `false`, the default, makes it a one-time secret. A one-time secret is not stored in `personal_credentials`: it is held encrypted on the request only for the turn that resumes the conversation after the member submits, overrides a personal credential of the same name there, and is wiped when that turn ends. If the conversation was reset or moved on to someone else's request, the value is dropped at once and the member is told so. The scheduler wipes any one-time value whose resume task has ended or that is older than two hours. The form says "🔑 需要你提供一次性密钥" (one-time secret) and that the value is not kept, the result card says "已交付" (handed over), and the audit action is `personal_credential.handed_off`. One-time and saved requests never settle each other. Scheduled runs can only ask with `save: true`, since nothing resumes them. The system prompt explains when to save and tells the agent to write a one-time secret through the variable (for example `yq -i '.values.X = strenv(X)'`) and to check the result without printing it. Requires database migration `0056`; upgrade the API before the workers. Secrets saved as personal credentials before this change are not reclassified; members can delete them under "我的凭证". See `docs/features/personal-credentials.md`.

- Feishu replies now show images that a Codex AI employee generates. Codex's image generation tool saves files on the runtime node under `$CODEX_HOME/generated_images/<thread>/`, and `codex exec --json` reports no item for it, so users used to get only a server path. The Codex driver now reads the images the turn produced once it ends, plus local images the answer links as `![caption](path)` (replaced in place), and streams them back in a new `delta.images` extension field. Only files inside the working directory or the thread's own image directory are read, recognised as images by their content, up to 10 MB each and nine per turn. The worker uploads each image with the bot's own Feishu credentials and writes `![caption](img_key)` into the answer as its own paragraph, so the streaming card shows it at once and the final card turns it into a native image component; scheduled results get the same treatment. A failed upload leaves a one-line note, and WeCom bots get a note instead of the picture. The system prompt tells Feishu AI employees on Codex that generated images are attached automatically. Runtime nodes need an upgrade; no database migration. See `docs/features/feishu-rich-cards.md`.

- Personal credentials. When a task needs the speaker's own account, password or API key, the agent calls `POST /api/runtime/credentials/requests` with the turn's `COREMAN_CREDENTIAL_TOKEN` and the variable names it wants. Feishu users get a Card JSON 2.0 form with password inputs in their private chat; WeCom users get a link to an OAuth-protected page, since WeCom template cards have no text input. The Feishu gateway encrypts the submitted values before the callback is written to `inbound_events` or `tasks`, and the worker removes that sealed copy once it is processed. Values are stored one row per (AI employee, member, variable), each encrypted with the master key and bound to that row, and no API returns them. They are injected as environment variables only into turns the member triggers: their private chat, their @-mentions in groups, scheduled tasks they created, and the turn that resumes the original conversation after they submit. Secret values of six characters or more are always redacted from replies and chat logs whatever the variable is called. Members can view, update and delete their credentials under "我的凭证" (My credentials). The agent can still read its own environment through a shell; see the feature doc for the boundary. Requires database migration `0054`; runtime nodes need no upgrade. See `docs/features/personal-credentials.md`.

- "Connect Feishu" has a fourth tier, "all permissions except messages" (`no_messages`): the middle tier without the messages and groups domain. It asks for no `im:` permission and no `search:message`, so the assistant can work with calendar, mail, tasks, docs, sheets, Base, wiki, contacts, approvals, OKR and attendance but never reads private or group chats, and cannot send messages or mail. The server refuses every `/im/` API for this tier regardless of what Feishu granted. The Feishu app page shows whether an app supports it. No database migration.

- Feishu replies are now rendered as rich Card JSON 2.0 cards. Besides Markdown, a Feishu AI employee can add fenced blocks whose info string is `card:<type>` and whose body is JSON with data only: `header` (colored title bar), `kpi` (metric tiles), `chart` (line, area, bar, ranking bar, pie, donut, funnel, bar-plus-line combo, progress, ring, radar, scatter), `table`, `callout`, `item` (picture with details), `timeline`, `columns`, `note`, link `actions` and `raw` card elements. CoreMan owns every style decision, so cards read well in both the light and the dark Feishu theme: charts leave text, axis and track colors to Feishu's theme and color data labels through theme palette keys, panels use a translucent color declared for both themes, and colors, icons and fields go through whitelists (Card JSON 2.0 rejects unknown fields outright). Plain Markdown is normalized for Feishu too: list indentation, code block languages, HTML outside Feishu's whitelist, non-web links, and GFM tables with more than five rows or numeric columns become table components. While a reply streams, finished blocks show as readable Markdown and unfinished ones as a placeholder; when it ends the card is replaced in place by the compiled card, with a message-list preview taken from the first sentence or the title bar. Content that does not fit one card (30 KB, 200 elements, 5 tables, 5 charts) goes into follow-up cards, extra charts become data tables, and if Feishu rejects the rich card it falls back in place to a Markdown-only card. Outgoing Markdown messages such as scheduled-run results are also sent as cards, falling back to post messages; Feishu scheduled results are no longer split by bytes, so a block is never cut in half. WeCom and the chat log page show blocks as plain Markdown. Each Feishu AI employee has a "Rich card replies" switch under More settings, on by default; with it off the prompt section is left out and blocks render as Markdown. `coreman feishu-cards preview` sends built-in samples or a file to a member for checking on real clients and only validates without `--apply`. Adds the `markdown-it-py` dependency. Requires database migration `0049`. See `docs/features/feishu-rich-cards.md`.

- Feishu rich cards are now interactive. An `actions` block can hold reply buttons (`{"text": "…", "reply": true}`) next to link buttons. A reply button sends exactly its visible text (at most 40 characters) as the asker's next message, and the answer quotes the card; `reply` is only a marker, so a string there is never sent. Reply buttons are clickable only in the asker's own conversational reply and only by the asker: the worker records the turn's speaker on the stream, the gateway writes that Feishu user ID into the button's callback when it compiles the final card and its follow-up cards, and anyone else's click is refused at once with a "只有提问人可以选择" (only the asker can choose) toast, like choice cards. Scheduled results, personal pushes and other outbox messages show reply buttons as grey text with no action. Feishu's callback does not say whether a chat is private, so the gateway decides it from server state: a click counts as private only when the chat is the clicker's recorded private chat with the bot, written only by typed private messages; click turns never write that record. A click in a verified private chat then gets the same identity check (including `union_id`), Feishu personal tools and personal schedules as a typed message there; reminders still need a typed message. Raw card elements still cannot carry callbacks. The callback answers within Feishu's window with "已收到" (received), or "已选过" (already chosen) for a repeat on the same row, which counts once. Only when the click passes the usual checks (bot enabled, allow-list, identity, commands) and its turn starts is the row's reply buttons disabled, with a grey "已选择" (chosen) line showing who picked what for everyone in the chat: on the streamed card through CardKit with the card's own sequence, and on follow-up cards by patching the stored card. A denied click leaves the card unchanged, and streamed cards more than an hour after the reply finished keep their buttons. AskUserQuestion questions with a single answer and two to four choices (the "other" choice included) now show one button per choice that submits on tap instead of a dropdown plus submit, still reaching the existing answer flow, with labels clipped to 40 characters; multi-select and longer questions keep the form, and WeCom is unchanged. The `people` block and `person` table columns now resolve emails, login names or unambiguous display names of active members with a Feishu account to Feishu user IDs, shown with avatar and name without notifying anyone; the rest stay as plain text. The prompt section documents reply buttons and `people`, and `coreman feishu-cards preview` renders both with the recipient as the asker. See `docs/features/feishu-rich-cards.md`.

- Feishu AI employees can ask colleagues for help, not only other AI employees. Managers of an employee add colleagues under Collaboration partners → Colleagues, each with a note on what they are responsible for; only active members with a linked Feishu account can be chosen, and being added grants no permission to use or manage the employee. The collaboration tools now also mount in private chats and scheduled runs when the employee has colleagues configured: `search_collaborators` returns `type: "ai"` or `type: "human"` (IDs `human:<member UUID>`), and `request_collaboration` shares the existing one-request-per-task and call budgets. The platform decides how to reach the colleague: in a group it looks up the group's members with the employee's own Feishu credentials and, if the colleague is there, replies to the original message with a real @; otherwise, and always in private chats and scheduled runs, the employee messages them directly by Feishu `user_id`. Nobody is contacted unless the turn hands off cleanly. Only the asked colleague's reply that quotes the request (in a group, while @-mentioning the employee) counts as the answer, and it never supersedes other work in the group; the original turn then continues as the original requester, in the current session of the original chat, with the colleague's text and attachments, and cannot ask again. For a scheduled run the recipients first get a note that the run is waiting on the colleague, and the answer starts a follow-up run of the same job (trigger `collaboration`) in the same runtime session, which delivers the result to the job's recipients. Requests remind once after 2 hours and end after 24 hours; a failed delivery (for example Feishu 230013 when the colleague is outside the app's availability scope), a paused or removed colleague, or a stop from the requester ends them early and tells both sides. A colleague can have at most 5 open requests, and a job one at a time. Requires database migration `0048`. See `docs/features/feishu-human-collaboration.md`.

- Members can now create and manage their own scheduled AI tasks from a private chat with an AI employee on Feishu or WeCom, through a skill (`coreman-cron`) rather than only Feishu's `schedule_propose` tool. In a verified private chat each turn gets `COREMAN_SCHEDULE_URL` and `COREMAN_SCHEDULE_TOKEN`, a capability sealed with the master key that names only that turn's task, owner and conversation; every call re-verifies the persisted private-chat origin, so the API at `/api/runtime/personal-schedules` takes no user parameter and only ever touches the speaker's own tasks on that bot. Group chats, collaboration turns and scheduled runs never get it, and a bot or skill variable with the same name is dropped. Creating, editing and re-enabling only open a draft and send a confirmation card (a button card on WeCom, after a message with the full details); the task changes only when the owner clicks it in the same private chat within 30 minutes, and is rejected if the task changed after the card was sent. Pausing, deleting, running now, listing, run history and a pre-check dry run apply directly. Personal tasks can now also send results to colleagues who have messaged the bot privately (up to 20) and to groups where the owner has talked to the bot (up to 10, re-checked before every run), carry a pre-check script, and expire; a task that sends to anyone else never gets the owner's Feishu or WeCom personal tools. Instructions may be up to 8000 characters (was 2000).
- Feishu replies now show images. Feishu does not render Markdown images that point to a web address, so a reply with `![avatar](https://...)` used to show a broken picture. When a reply is final, the Feishu gateway downloads the image, uploads it with the bot's `im:resource` permission and embeds the returned `image_key` in the card, with a "查看原图" (view original) link on the next line unless the reply already links that address. Fallback plain messages and overflow chunks send images as native `img` nodes. The gateway only fetches public addresses, resolving and pinning the IP on every redirect hop, and takes images up to 10 MB within 10 seconds, recognised by their file header (PNG, JPEG, GIF, WEBP, BMP, TIFF, ICO). While a reply is still streaming, when a download or upload fails, or beyond nine images per message, the image shows as a link instead; a failed address is not retried for five minutes. Images on private-network hosts are not fetched and stay links.
- The runtime page now shows which outbound proxy Claude and Codex actually inherit on each node, so a machine that cannot reach the AI services directly is visible before requests start failing. A node reports it in its heartbeat as one of three states: the proxy set on the install link (`proxy` in the node `config.json`, which wins and overwrites the four proxy variables), the service environment's own proxy variables (kept as they are when the install link left the field blank), or none at all, which is flagged as a risk because the CLIs will connect directly. Editing `proxy` in `config.json` adds a "restart to apply" note, since the proxy is decided once at startup and inherited by every driver and CLI process. Only the proxy's host and port are reported: a username and password in an inherited proxy variable stay on the node. Nodes that have not been upgraded report nothing and are shown as unknown, and so is a state that a newer node reports and this release does not understand, since a display-only field must never take a node offline. Requires database migration `0046`. Note that user services do not read `~/.profile` or `~/.bashrc`: a proxy that only a login shell sets never reaches a daemon started by systemd or launchd.
- "Connect Feishu" can now move files. The assistant can download mail attachments, files and images from chats, and files in My Space; upload a local file and send it in a chat, save it to My Space or attach it to a mail; and forwarding a mail now carries the original attachments. The model never holds the owner's Feishu token, so CoreMan fetches and sends files as the owner and keeps them in the object store for an hour: a download tool returns a 30-minute link that the agent fetches with `curl`, and `feishu_prepare_upload` returns a 30-minute link that the agent uploads to with `curl -T`, getting an `upload_id` for the send, save and mail tools. Links and upload IDs are sealed with the master key and bound to the owner, the bot and the current authorization, so revoking or reconnecting ends them; upload links refuse browser requests that carry an `Origin`, and pre-signed mail attachment links are only fetched from Feishu hosts. Limits: 50 MB per download, 30 MB per upload, 10 MB for images, 20 MB into My Space and 18 MB of attachments per mail (Feishu refuses mails over 25 MB). Mail attachments that Feishu stores as links are not forwarded, and the tool names them. Also new: who has read a message, a group's announcement, editing a sent message (top tier), tasks related to the owner and task search, colleagues' email, department and manager, department search and members, writing OKR progress, file info, moving, copying and renaming files in My Space (not deleting), adding and renaming sheets, creating Base tables and fields, and reading legacy docs, slides and mind maps. 110 typed tools in total, up from 88. Existing apps need "补齐权限" and members need to connect again for the new permissions.
- "Connect Feishu" covers more everyday work (88 typed tools, up from 77; the top tier asks for 68 permissions, up from 63). Mail: reply and reply-all quote the original, take recipients and subject from it and stay in the same thread (`In-Reply-To`, `References`), and forwarding includes the original text; both work as drafts or sends through the existing mail tools. Calendar: all-day and recurring events (RFC 5545 rules), reminders, finding meeting rooms and booking them on an event, and a room's busy times. Approvals: find the forms the user can submit, read a form's fields and submit it (for example leave or expenses), recall, remind approvers, and hand a pending task to a colleague. Documents: read docx and wiki pages as Markdown (optionally with block IDs), change existing content by replacing text or blocks, deleting or inserting blocks, or overwriting, share with colleagues (top tier only, since it notifies them), and create folders. Also Markdown messages, subtasks and task reminders. Existing apps need "补齐权限" and members need to connect again for the new permissions.
- The `max` reasoning effort, above `xhigh`, for AI employees and the platform default. The model catalog gets a "max" switch next to "xhigh", and migration `0043` fills both from the vendors' documentation: Claude Fable 5.1/5, Mythos 5.1/5, Opus 5, Opus 4.8, Opus 4.7 and Sonnet 5 support both; Claude Opus 4.6, Sonnet 4.6 and Mythos Preview support `max` but not `xhigh`; GPT-6 Astra and GPT-5.6 Sol/Terra/Luna support both; GPT-5.5, GPT-5.4, GPT-5.4 mini, GPT-5.3-Codex and GPT-5.2 support `xhigh` only; Claude Opus 4.5, Sonnet 4.5 and Haiku 4.5 support neither. Models that runtimes report later get both switches filled in the same way when they are added to the catalog. The employee form greys out the levels the chosen model does not support and says so, and switching to a model that lacks the current level steps it down to the highest one the model supports, as the runtime switch already did for `xhigh`. The Claude driver passes the level to `claude --effort`; the Codex driver passes it as `model_reasoning_effort`, which Codex CLI accepts from 0.154. Requires database migration `0043`; downgrading it maps `max` back to `xhigh` where the model supports it and to `high` otherwise.
- "Connect Feishu" now covers calendar, mail, tasks, docs, sheets, Base, wiki, contacts, approvals, OKR and attendance, not just messages, meetings, minutes and docx reading. QR-created apps request the permissions for all of them at creation (64 user permissions instead of 16), so choosing "all permissions" asks for them too. The assistant gets one typed tool per operation (77 in total, up from 10), for example listing, creating, moving and deleting calendar events, searching, reading, drafting and sending mail, creating and completing tasks, reading and writing sheets and Base records, and approving or rejecting approvals. There is still no generic API proxy: the server only calls the endpoints registered in `coreman/core/feishu_personal/endpoints.py`, each classed as read, write or send. The message-only tier gets reads of messages only, the middle tier gets reads and writes, and only the top tier can send messages or mail as the user. The tool list now shows only the tools that the owner's tier and granted permissions reach, and each call is checked against both again on the server. When Feishu refuses a call, the tool reports whether the app lacks the permission (`app_permission_missing`) or the owner did not grant it (`user_permission_missing`), or returns Feishu's numeric error code, and invalid arguments come back with the fields that failed. A tool call may now carry up to 256 KB (was 16 KB), so long mail bodies, sheet rows and document paragraphs fit. Sending mail takes a `uuid`, like sending messages: Feishu mail has no idempotency key, so CoreMan records each send, and a retry with the same `uuid` returns the earlier result or sends the draft already made instead of a second mail (a changed recipient or body under the same `uuid` is refused as `uuid_reused`). If resending that draft fails, the first attempt may have gone out with its reply lost, so the tool reports `mail_send_unconfirmed` and asks the user to check Sent instead of the model sending again. The middle tier keeps `calendar:calendar.event:reply`, so it can accept or decline the owner's own invitations; other permissions named send, reply or forward stay out of it. Requires database migration `0045`. The Feishu app page no longer lists a permission as missing when the app holds an older, broader permission that Feishu accepts for the same APIs, such as `calendar:calendar` or `wiki:wiki`. Existing apps need "补齐权限" (add missing permissions) on the Feishu app page, and members need to send "连接飞书" again, before the new tools appear.

### Changed

- Default system prompt sections revised for current models, which follow instructions more literally. The policy no longer tells the agent to treat all external content as data: instructions in files, pages or tool output may be followed when the requester asked the agent to act on that content, but never change identity, permissions or the rules. Installing packages a task needs inside the workspace or a project virtual environment is allowed; system-wide changes are not. Every run now gets a "当前时间" (current time) section after the speaker, in Beijing time and UTC, with business time zones left to the organization background or task prompt; the personal schedules section no longer carries its own copy. File delivery guidance ("chat users cannot open paths on the runtime host") moved from the Codex-only response format to the execution model, so Claude employees get it too, and recurring work points to the scheduled-task tools only when the request provides them. Scheduled runs may send a message or email with the owner's personal Feishu or WeCom tools when the task prompt itself asks for it. The minimal length level may add one short condition when a bare yes or no would mislead, and the minimal and brief levels yield to a format the user explicitly asks for in that request. Deployments that saved their own text for these sections in Settings keep it. No database migration.

- The Feishu rich card section of the system prompt is about 20% shorter (5.8k to 4.7k characters). The guidance on when to use blocks, every block type and all their fields are unchanged; the wording is tighter and the two examples are merged into one that still covers header, callout, kpi and chart. The table example is dropped since Markdown tables are converted automatically.

- The Codex default model is now GPT-6.1 Sol (`codex/gpt-6.1-sol`), which supports `xhigh` and `max`. Migration `0055` adds it (or un-retires a row that runtimes reported earlier, keeping its display name), puts it first for Codex and makes it the default, and retires GPT-6 Sol, including dated snapshot names. AI employees on GPT-6 Sol move to GPT-6.1 Sol and reload, keeping their reasoning level, and runtimes with an explicit model list get GPT-6.1 Sol in its place. Chat logs and prices keep the old name. Downgrading the migration leaves the catalog and employees as they are.

- Response detail levels now match their labels and take effect on Claude. Level 1 (minimal) answers in as few words as possible, so a yes-or-no question gets only yes or no; 2 (brief) replies like someone of few words; 3 (standard) gives the answer and a short explanation of the key points; 4 (detailed) adds no instruction, which is the model's own default and now the default for new AI employees. Previously the levels ran the other way (1 added nothing and 4 asked for a minimal answer), and on Claude levels 2–4 did nothing at all: the runtime wrote output style files whose `name` differed from the style CoreMan selected, so Claude Code silently used its default. Both backends now get the level as a section of the system prompt, editable in Settings as "Response detail 1–3"; the runtime no longer writes `.claude/output-styles/` into workspaces, and no runtime upgrade is needed. When a long run continues in the background, levels 1 and 2 send only the final result and levels 3 and 4 send progress. Requires database migration `0053`, which turns every AI employee's level n into 5 − n so its replies stay as they were, moves the platform default from 1 to 4, and moves edited prompt sections along with their level, dropping those still equal to the old factory text.
- Security constraints are now optional for skills that require approval. Many such skills already enforce their limits in the skill itself, so a request and an approval may leave the field blank; a blank field adds nothing to the AI employee's system prompt. Clearing the pre-filled catalog template now really submits no constraints instead of silently falling back to the template, and a reviewer can clear the requested text the same way. A database scope is still required when the skill offers one. No database migration.
- The Feishu gateway finds a dead long connection and replaces it faster. Feishu does not resend card callbacks, so a click that lands while the connection is down fails with "目标回调服务当前未在线" (callback service offline). WebSocket keepalive now pings every 10 seconds and gives up after 10 (was 20 and 20), the random wait before reconnecting is at most 2 seconds and retries come every 10 seconds (Feishu sends about 30 and 120). Each reconnect is logged as `feishu_ws_reconnecting` and `feishu_ws_reconnected` with the app ID and `offline_s`, the time the bot was offline; the SDK's own log stays at errors only.

- The "Connect Feishu" selection card is much shorter: four full-width buttons with short tier names and one grey line (valid for 10 minutes, private chats only, records visible only to you, revoking does not delete them). The shared retention notice returned with the authorization status is shortened to match, and the card shown after choosing drops the extra explanation.

- The model catalog now defaults to Claude Opus 5.5 (`claude-opus-5-5`) and GPT-6 Sol (`codex/gpt-6-sol`); both support `xhigh` and `max`. Migration `0051` adds them (or un-retires rows that runtimes reported earlier, keeping their display names), puts them first for their provider and makes them the default, and retires the models they replace: Claude Opus 5 and GPT-5.6 Sol, Terra and Luna, including dated snapshot names. GPT-6 Astra, Sonnet 5, Haiku 4.5 and Fable 5.1 stay available. AI employees on a retired model move to the new model of the same provider and reload; their reasoning level is kept, since both new models support every level. Runtimes with an explicit model list get the new model in place of the first retired one. Chat logs and prices keep the old names. Downgrading the migration leaves the catalog and employees as they are; change them back in the model catalog if needed.

- Feishu rich card replies now stream block by block. Text still types out, now at about 50 characters a second (was 14, which fell behind the model and then jumped), and each chart, table, metric row or other block appears in place the moment its JSON is complete instead of only when the reply ends; two half-width blocks join one row as soon as both exist. The gateway computes the reply as a list of units, compares it with the layout it recorded for the card (`feishu_deliveries.layout`, migration `0050`), and sends one CardKit `batch_update` for structural changes plus streaming text updates for the growing paragraph; if the card and the recorded layout ever disagree it rebuilds the card in streaming mode. The thinking panel is only pushed when it changed, and calls per AI employee are spaced 0.125 s apart (was 0.3 s), so concurrent replies refresh about once a second. Replies longer than ten minutes keep typing: the gateway renews Feishu's streaming mode at nine minutes and reopens it if Feishu closed it, instead of switching to whole-card updates. Sequence conflicts (300317) raise the local sequence, and card updates blocked by a user's click (200810) retry without counting as failures. `coreman feishu-cards preview --stream` uses the same path.

- Saying "连接企业微信" (Connect WeCom) in a WeCom private chat before binding now replies with a one-tap authorization link instead of pointing to the page. Opened inside WeCom on a phone, the link signs in and jumps straight to WeCom's "confirm creation / confirm authorization" page, so there is no QR code to scan on the same screen; opened on a computer it shows the QR code. When binding finishes, the assistant announces the result in that private chat and sends the tier card; failures such as someone else confirming are explained there too. The link carries no WeCom scan code: that code can fetch the authorization bot's secret, so it is only handed to the signed-in member. Requires database migration `0042`.
- Chat logs record each turn as soon as it starts, with the status `running` (shown as "In progress"), and that same row is updated when the turn ends, in the transaction that sets the task's final state. Scheduled runs follow the same lifecycle. The session viewer can therefore tell whose session it is during the first turn of any chat, so private-chat links no longer carry a signed token; links issued before the upgrade keep working. The chat log page lists and filters in-progress turns, which count as neither succeeded nor failed and are left out of the average duration; message counts on the statistics page include them. Writing the log never fails a turn: if it cannot be written in the turn's transaction it is written right afterwards, and a row still in progress two minutes after its task ended (for example when an AI employee is deleted mid-turn) is closed by the scheduler with the task's final state. Requires database migration `0044`; to roll back to an earlier release, downgrade it first, which marks turns still in progress as errors (earlier releases never close them).

### Fixed

- A Feishu AI employee answering another AI employee's collaboration request no longer gets the rich card, response length, Codex output and reply image sections in its system prompt. The answer must be a bare JSON object that the platform parses, and those sections asked for Markdown or card blocks instead, so a model that followed them made the collaboration fail with "协作伙伴未提交完整结果".

- Quoting a message on Feishu now gives the model what the message says. Since replies became Card JSON 2.0 cards, quoting a reply older than an hour showed the model only Feishu's "请升级至最新版本客户端，以查看内容" (upgrade your client to view this) placeholder: the streamed reply state that held its text is dropped an hour after the reply ends, and Feishu's message API returns that placeholder for 2.0 cards unless asked for the original card. The gateway now keeps the text of every message a bot sends in `feishu_sent_messages` (a streamed card when its reply ends), kept 90 days like inbound events, and the worker reads quotes of the bot's own messages from there. Other messages are read with `card_msg_content_type=user_card_content`, and the placeholder is never passed off as content. Quotes now cover cards (1.0, 2.0 and template cards, including table rows, chart data and button labels; table cells read back this way come in Feishu's rendered form, not as sent, and are read as text), rich text with its title, mentions by name, files, merged forwards (one line per message with the speaker's name where the directory knows it), calendar events, tasks, votes, locations, contact cards and system messages; voice, video and stickers get a one-line note. Pictures and files in the quoted message are now downloaded like the current message's attachments, through the official resource API with the quoted message's ID, which the fetcher allows only after checking that it is in the same chat. When the API refuses, for example in a group without the `im:message.group_msg` permission (not requested by QR-created apps), the text comes from the inbound event if the bot received the message. A recalled message is marked "[引用的消息已撤回]" (quoted message recalled) and anything else unreadable "[引用消息内容不可用]" (quoted content unavailable). Requires database migration `0052`. See "引用消息" in `docs/feishu.md`.
- Replies ran every message of a turn together into one paragraph. When the model writes a few words, runs a tool and writes again, the relay streams the texts back to back with nothing between them, so a Feishu card or WeCom reply that spanned several tool calls read as one block with sentences glued end to end. Text that resumes after a tool call now starts a new paragraph (a blank line, counting any line breaks already there), in chat replies, background progress pushes and scheduled-run results alike.
- Signed-in administrators could no longer save anything seven days after logging in: every write request failed with "CSRF 校验失败" (CSRF check failed) while pages still loaded. The console session is renewed on use, but the CSRF cookie was only set at login with a fixed seven-day lifetime. It is now renewed together with the session, keeping its value, and a live session that has lost it gets a new one on its next request, so people already affected only need to reload the page instead of signing in again.
- "Add partner" on Collaboration partners showed nothing at all when there was no other Feishu AI employee to choose, which looked like a broken search. The drawer now says so, and that this list only holds AI employees (colleagues are added under Colleagues); the wording no longer says "Feishu partners", which read as directory members.
- Skill sources on Git services that check the username, such as Alibaba Cloud Codeup, can now be synced and installed with an access token. The username was always `oauth2`, the GitLab convention, and Codeup answers 401 unless it is the account that owns the token. Sources get an optional "Git username" field; left blank it stays `oauth2`, so existing GitLab sources are unchanged. Catalog sync and skill installation both use it; installation needs the runtime nodes upgraded, since older nodes keep sending `oauth2`. A failed clone that ends in Git's "could not read Username … terminal prompts disabled" is now reported as an authentication failure that points to the token and the username, instead of the generic "cannot sync source" message. Requires database migration `0047`.
- "Connect Feishu" could not create an authorization link on the two "all permissions" tiers for an app with many permissions enabled. Those tiers requested every user permission the app had, and Feishu refuses a request with too many permissions (error 20084); one production app has 638. They now request only what the personal tools use: for each API, one permission the app has (the most specific first), plus the message-read set, about 60 in all. When Feishu still refuses, the worker logs Feishu's reason and code (`feishu_personal_authorization_refused`, `personal_authorization_unavailable`) instead of dropping them.
- Opening "查看完整思考过程" (View full thinking) while the first turn of a new group chat was still running showed "会话不存在" (Session not found), even to administrators, because the session viewer judged ownership from chat logs that were only written when a turn ended.
- The `xhigh` reasoning effort can now be chosen for the models that support it. The model catalog never marked any model as supporting `xhigh`, so the option stayed greyed out even for Claude Opus 5. Migration `0043` sets the flags from Anthropic's and OpenAI's model documentation (listed under Added); models not in those docs keep the administrator's setting. Employees set to `xhigh` on a model that is switched off drop to `high`, which is what Claude Code already ran them at. Requires database migration `0043`.

### Security

- Service logs no longer contain live platform credentials. httpx wrote one INFO line per outbound request with the full URL, and WeCom takes `access_token`, `corpsecret` and the OAuth `code` as query parameters, so every API call put a working token into the API, worker, scheduler and gateway logs. The `httpx` and `httpcore` loggers are now held at WARNING in every process, including when `LOG_LEVEL=DEBUG`. As a fallback, every log line, traceback and uvicorn access log line has credential-style query values (`*token`, `*secret`, `*ticket`, `code`, `key`) replaced with `***`; this also covers the request URL that `raise_for_status()` puts in its error message. ### Changed

- Creating a WeCom AI employee with a manually entered Bot ID and Secret now verifies them with one long-connection subscription before saving, just like QR-created bots, and rejects credentials that WeCom refuses (HTTP 422) or cannot be checked (HTTP 502). Editing an existing employee's credentials is not verified, so the live connection is not kicked off.
- "Test as myself" on business systems no longer reports a failure just because the home page redirects after sign-in. It now requests the address once without the token and once with it: a 2xx, or a redirect to somewhere other than the unauthenticated destination and not a login page, counts as the token being recognized, and the message names the path it landed on. Redirecting to the same place or to a login page counts as not recognized, and a home page that opens without a token is reported as inconclusive. The response adds `baseline_status_code` and `redirect` (host and path only).
- Business system tokens now use the speaker's email prefix (lowercased) as `sub`, which is how business systems usually look up their own accounts. A login name is generated only on the first contact sync and falls back to the platform user ID when no email was available then, so Feishu members synced without the `contact:user.email:readonly` permission got tokens that business systems could not match. A user without an email, or whose email prefix another account also uses, gets no business system tokens, and the assistant is told to ask them to add an email or contact an administrator; falling back to the login name could give two people the same `sub`. `bot_token` sign-in looks users up by the same rule. The access test reports the token user it used.

### Fixed

- Runtime session history no longer records a request's environment variables. They carry bot secrets and access tokens, and until now they were written to the node's session logs and streamed to the session page. Runtime nodes need an upgrade; logs written before then expire within the usual 72-hour cleanup.
- A failed skill installation now says why in the skill management dialog instead of always showing "安装未完成". Runtime nodes return the Agent's fixed error message (for example "工作目录不存在", or "Git 来源不在白名单内" from nodes that predate the change above, shown with a hint to upgrade the node or add the host to `git_hosts`) as an `operation_failed` result and write it to `runtime.log`; command output, paths and credentials are still never returned or logged. Checks that fail before anything reaches the node say that nothing was executed, and the worker logs every failure with the task, bot and skill IDs and an error code. Older nodes still report only `execution_failed`; the dialog then points to the node's `runtime.log` and suggests upgrading the node.
- Installing a skill from a private repository that needs the source's access token failed with "操作失败（退出码 128）" on runtime nodes with Git older than 2.31. The token was passed through `GIT_CONFIG_COUNT`, which older Git silently ignores, so the clone was sent without credentials. The node now hands the token to Git through `GIT_ASKPASS`, as workspace Git operations already did, and passes the other settings with `git -c`, including an empty `http.proxy` so the token never goes through a proxy set in `~/.gitconfig`. Runtime nodes need an upgrade.
- The "可安装技能" heading in the skill management dialog no longer sits right under the installed skills table.
- A runtime node could pick up a new request up to a second late. The caller renewed its lease on every read, which briefly locked the request just as the node's long poll, woken by the new request, tried to claim it and skipped it. The lease is now renewed every 10 seconds.
- The runtime install dialog shows the whole hint about replacing an existing runtime with `| sh -s -- --replace`. Its message contained literal `|` characters, which vue-i18n treats as plural separators, so the Chinese hint read only "sh 换成".

### Security

- The line that tells the model who is speaking now carries a random tag generated for each turn (`[SYS_USER:<tag>]`), and a fixed rule that administrators cannot override says that only the line with the current tag identifies the speaker, with the `COREMAN_USER_LOGIN` and new `COREMAN_USER_SUBJECT` (the token `sub`) environment variables as the authority. Before, a file, web page, memory or tool output could print an identical `[SYS_USER]` line. `COREMAN_USER_SUBJECT` is a reserved request-level key.
- Credential values from the turn's environment, and anything shaped like a JWT, are replaced before model output reaches chat replies, streamed text, the thinking panel, question cards, chat logs and scheduled task results. A model repeating a token no longer shows it to everyone who can read the chat. Question card snapshots no longer store the prompt.
- An expired `bot_token` cookie no longer locks out a signed-in administrator. Authentication falls back to the console session and clears the dead cookie, and write requests then pass the standard CSRF check.

### Changed

- The bundled Claude driver now reports native Claude Code model names (`claude-sonnet-4-6`, `claude-opus-4-6`, `claude-haiku-4-5-20251001`) instead of names with a `vllm/` prefix. The prefix never had a functional meaning: the driver strips anything before the last `/` before calling the CLI. Migration 0023 renames the seeded `vllm/claude-*` catalog entries, prices and bot models to the native names.
- A run waits up to 120 seconds in the queue of a full runtime node instead of failing after the 10-second connect timeout. Reverse-channel calls expire after the bot's timeout (up to 12 hours) instead of a fixed 2 hours, and scheduled runs are no longer capped at 2 hours.
- Gateways drain bots in paced batches that fit the stop grace period.
- New business systems allow no bots until an administrator selects them, and the `coreman` system key is reserved.
- API containers trust forwarded client addresses only from the Caddy network (`COREMAN_EDGE_SUBNET`, default `10.250.250.0/28`).
- Scheduled results longer than 100,000 characters are truncated instead of failing the run.
- A new message in a session whose previous turn is still stopping waits and is re-queued instead of failing with "session busy".
- Database engines use a 10-second connect timeout and a 300-second statement timeout.
- Optimistic-lock conflicts return HTTP 409 with the dedicated code `40901`.
- Documentation opens with user-facing descriptions instead of release status notes.

### Fixed

- Escalations whose question notification cannot be delivered are cancelled instead of waiting until they expire.
- WeCom `gettoken` credential failures are cached briefly instead of being retried on every request.
- `deploy/coreman` refuses to generate new secrets when a PostgreSQL data volume already exists.
- The users page still loads when the team list request fails.
- Audit entries for skills, memories, the skill catalog and runtime nodes record the client IP.
- Listing a bot's skills no longer locks the bot row.
- Claude Code context compaction no longer trips the resume watchdog on long sessions.

### Security

- Bot, environment preset, skill and MCP environment variables can no longer set runtime control variables such as model endpoints, loader hooks, proxies or CLI configuration directories. The Runtime Daemon enforces the same list.
- The application refuses to start with a template or short bootstrap administrator password.

### Removed

- The generated `docs/environment-creation/manual.html`; use `docs/environment-creation/README.md`.
- Unused compatibility routes `/api/robot/memories/*`, `/api/robot/wework-notify`, `/api/robot/organization/tree`, `/api/organization/full`, `/api/push` and `/api/test/bot-token-access`. The remaining escalation compatibility routes require signed requests and no longer accept a plain `X-API-Key` secret.
- The `cron` infrastructure API scope, which no route used, and the `ETEAMS_` reserved environment prefix.
- The `RELAY_NETWORK_MODE` and `TIMEZONE` settings.
- `system_grant_audit` is no longer written (grant changes are recorded in `audit_logs`) and `bots.custom_command_modules` is no longer read. Both will be dropped in the next release.

# 飞书接入与验证

CoreMan 使用企业自建应用。为同一企业部署：平台身份以 `user_id` 为键，不支持将不同企业中相同 user_id 当作不同员工。登录应用建议填写企业 tenant_key（平台应用的 corp_id 字段），登录返回的 tenant_key 必须匹配；跨企业部署应使用独立实例和数据库。

## 应用配置

在飞书应用中开启机器人能力并发布版本，配置可用范围。按实际使用功能申请消息接收、发消息、消息资源、CardKit 写入、通讯录及用户 user_id/邮箱/手机号权限。用户 user_id 权限是卡片归属与员工身份校验所必需，缺失时不能改用另一应用的 open_id 猜测身份。

事件订阅使用长连接：

- `im.message.receive_v1`
- `im.chat.member.bot.added_v1`
- `im.chat.access_event.bot_p2p_chat_entered_v1`
- 卡片回调 `card.action.trigger`

登录重定向地址为 `{PUBLIC_BASE_URL}/api/auth/feishu/callback`。管理台的平台应用启用对应能力，先完整同步通讯录再使用员工登录。通讯录同步先读取应用的授权范围，仅个人授权时直接获取该成员，不读取无权访问的根部门。需要 contact:contact.base:readonly（授权范围查询）、contact:user.base:readonly、contact:user.employee_id:readonly；部门范围还需相应部门读取权限。要把邮箱同步进来还需 contact:user.email:readonly（启用飞书邮箱时企业邮箱需 contact:user.employee:readonly）：没有邮箱时登录名退回飞书 user_id，业务系统令牌的主体也只能用它，按邮箱前缀认人的业务系统会找不到用户。当前不支持基于用户组的通讯录范围，遇到此类范围会中止同步，避免误停用成员。邮箱与手机号若分别匹配不同账号，同步整体中止，需先处理冲突。

员工扫码时若还没有同步进来，CoreMan 会用具备通讯录同步能力的飞书应用（优先登录应用本身）按 user_id 只补这一个人再登录：不建部门、不停用任何人，部门只关联已同步过的部门，团队规则照常生效，审计记为 `user.login_sync`。此人不在应用通讯录范围内、已离职或归并冲突时，登录页仍提示「未找到匹配的账号」，API 日志 `feishu_login_unknown_user` 带 `user_id`，飞书返回的错误码见 `feishu_login_sync_failed`。新部门与离职停用仍靠完整同步：scheduler 默认每 24 小时自动全量同步一次（`CONTACT_SYNC_INTERVAL_HOURS`，0 关闭），也可以在管理台点「同步」或运行 `./deploy/coreman contact-sync --app <应用名称>`，规则见 [企业微信接入](wecom.md) 的「在 CoreMan 中配置与验证」。

新建飞书员工默认扫码创建应用（见下文「扫码创建与管理飞书应用」），也可以在「更多设置」中打开「手动填写凭证」使用已有应用。一个应用只能绑定一个 CoreMan 机器人。需要人工求助回复时，通知/回调平台应用必须与唯一启用机器人的 app_id 一致。求助接收人引用当前通知回复；普通聊天不被求助流程截取。

机器人工作目录必须位于所选运行时节点的项目主目录之下，并允许节点运行用户读写。缺失目录时，Go 子进程启动错误可能表现为 `fork/exec .../claude: no such file or directory`；应同时核对工作目录和程序路径，不能只根据报错认定 CLI 缺失。

## 扫码创建与管理飞书应用

新建 AI 员工时平台默认为飞书，只需填写标识、名称并选择运行时，其余配置都有默认值并收在「更多设置」里。点击「扫码创建飞书机器人」后：

1. 先按真实创建流程校验员工配置（标识、团队、运行时、模型、工作目录），不落库；校验不通过不会出二维码，避免飞书侧留下用不上的应用。
2. 管理台展示二维码与「在飞书中打开」链接。协议与官方 SDK `register_app` 一致（OAuth 2.0 设备授权），CoreMan 把 init/begin/poll 拆成服务端会话：设备码和确认链接加密保存，多个 API 副本通过行锁串行轮询，并遵守平台返回的轮询间隔与 `slow_down`。二维码约 10 分钟有效，只有发起人能查看结果。
3. 扫码人在飞书确认后，App Secret 只保存在服务端（加密，最长 24 小时），浏览器只拿到 App ID；随后由同一次操作创建员工并一次性消费凭证。若创建员工失败，本人下次新建员工时可以直接复用这个应用，不必重复扫码。
4. 确认页只允许新建应用（不提供「选择已有应用」）。国际版 Lark 租户暂不支持。每人每小时最多发起 10 次扫码。

扫码时按以下清单申请，均在平台智能体模板之上增量叠加：

- 应用身份：员工 user_id（身份识别所必需）、通讯录基础信息、收发消息、表情回复、消息资源、群信息、CardKit，以及管理应用自身、修改应用信息、机器人菜单和斜杠指令。
- 用户身份：「连接飞书」全部档位所需的权限（含第一档以用户身份发送消息）。应用侧一次开通，个人授权时仍由本人在私聊选择档位，CoreMan 按档位收窄实际范围，发送等操作仍由服务端独立校验。
- 事件与回调：`im.message.receive_v1`、`im.chat.member.bot.added_v1`、`im.chat.access_event.bot_p2p_chat_entered_v1`、`card.action.trigger`，长连接订阅。

清单在 `coreman/core/feishu_apps/manifest.py` 中维护。CoreMan 以后新增需要的权限时，已创建的应用可在员工详情「飞书应用」页点「扫码补齐权限」：确认页只针对当前绑定的应用，若飞书轮换了密钥会自动写回，密钥未变时不会让网关重连。

员工详情的「飞书应用」页（仅机器人管理员可见）以应用自身身份调用飞书开放接口：

- 查看应用名称、头像、线上与审核中版本、全部权限及企业管理员审批状态、CoreMan 仍缺少的权限、「连接飞书」各档位是否可用以及已连接人数；可向企业管理员申请授权。
- 修改基础信息（名称、描述、帮助链接、头像）、机器人使用说明与菜单，并提交发布版本。这些修改都要发布新版本并审核通过后才生效。
- 管理可用范围：查看飞书线上实际生效的可用名单和禁用名单（含在企业管理后台的修改），按 CoreMan 成员和飞书通讯录部门增删，或切换全员可用，立即生效、不需要发布。用的是应用管理接口（`GET /open-apis/application/v2/app/visibility`、`PATCH /open-apis/application/v6/applications/:app_id/visibility`），需要「获取应用信息」（`admin:app.info:readonly`）和「管理应用可见范围」（`admin:app.visibility`）两个企业管理员权限。这两个权限也能读改企业内其他应用的可用范围，所以不在扫码创建时申请。这两个接口能读写企业内任意应用的可用范围，所以推荐只给**飞书登录应用**（平台应用里具备登录能力的那个）开通这两个权限并发布一次：CoreMan 优先用它读写所有机器人的可用范围，不必逐个扫码；登录应用没有权限时才用机器人自己的应用，这时可在「可用范围」里点「扫码补齐权限」为这个机器人单独申请。面板和 `coreman bots visibility` 会写明用的是哪个应用。命令行见 `coreman bots visibility`（[管理命令](admin-cli.md)）。
- 管理斜杠指令，无需发布，约 5 分钟后在客户端生效（飞书 7.70 及以上）。扫码创建的智能体会自动添加 CoreMan 内置指令 `/new`、`/stop`、`/sessions`、`/connect`、`/help`；手动填写凭证的应用可在该页点「添加内置指令」补齐，已有的同名指令不改动。飞书把所选指令作为普通文本（例如 `/help`）发给机器人，CoreMan 的内置命令去掉一个前导 `/` 后仍按整句匹配，`/help 写代码` 这类带参数的内容照常交给 AI。`/connect` 等同于发送 `连接飞书`，必须带 `/`，单独发 `connect` 仍按普通对话处理。

权限核对说明：`offline_access` 与 `auth:user.id:read` 属于用户授权协议项，会随个人授权令牌下发，但不会出现在应用的权限列表里，因此不计为缺少。获取会议详情接受 `vc:meeting:readonly` 或 `vc:meeting.meetingevent:read` 任一，扫码实测前者未被开通，所以两者都申请。清单新增权限后，已创建的应用需要在「飞书应用」页扫码补齐。应用已开通飞书接受的旧版大权限（如 `calendar:calendar`、`wiki:wiki`、`docx:document`）时，被它覆盖的细分权限不计为缺少；第三档按名称申请的消息权限和以本人身份发送所需的权限必须原样开通。

飞书的限制：修改与发布接口只允许应用改自己，并且只支持在开发者后台创建的自建应用；扫码创建的应用是否属于此类，官方文档未说明，请在测试租户实测。不支持时管理台会提示改到开发者后台操作。应用有版本在审核中时不能修改或再次发布。菜单中的「推送事件」类型会产生 `application.bot.menu_v6` 事件，CoreMan 目前不处理该事件。飞书没有删除应用的接口，删除 AI 员工不会删除飞书应用，如不再使用请到开发者后台删除。

## 已实现的行为

网关父进程持有数据库租约，每应用一个子进程连接 SDK。入站数据库提交后才应答；超过两秒或失败要求平台重投。群聊只接受明确 @ 当前机器人的人类消息。进入聊天事件可以触发欢迎语，但不视作员工已发言或建立私聊可达关系。

卡片采用 JSON 2.0，流式 70ms/1 字符/fast，300ms 最小 API 调用间隔；九分钟转静态并继续更新同一卡片，不受旧 Agent 超时配置影响，接管沿用卡片与递增序号。连续失败六次或永久拒绝后，最终答案通过持久出站箱改用普通消息投递。长期卡片也转普通消息。出站永久失败留在管理台，未标成送达。消息 UUID 支持平台去重；平台的去重窗口与创建卡片后进程崩溃的窗口仍受外部接口约束，不承诺端到端恰好一次。

选择题复用公共逐题状态机，支持单选、多选与其他答案；提交后改为只读卡片。回调必须匹配实际发出的卡片消息、机器人、聊天与发起员工。没有将全部问题合并为一张表单。

图片和文件仅通过当前消息（或下文核对过同会话的被引用消息）的官方资源接口下载，不接受外部 URL；大小上限 100 MB。

### 引用消息

用户引用一条消息提问时，飞书事件只带被引用消息的 ID。worker 按下面的顺序补出内容，交给模型时写成「[引用消息: …]」：

1. 机器人自己发过的消息：网关每发出一条消息就把正文存进 `feishu_sent_messages`（流式卡片在回复结束时存终稿），保留 90 天。存档上线前发出的回复，再看流状态（回复结束后留一小时）和出站队列（留七天）。
2. 其余消息调用「获取指定消息的内容」，带 `card_msg_content_type=user_card_content`。不带这个参数时，Card JSON 2.0 卡片只返回「请升级至最新版本客户端，以查看内容」；这句占位不会被当成引用内容。支持文本、富文本、卡片（1.0、2.0、模板卡片，含表格、图表数据、按钮文字）、图片、文件、合并转发、日程、任务、投票、位置、名片和系统消息。合并转发逐条写成「发言人: 内容」，同事按通讯录里的 open_id 认名字，认不出的按出场顺序叫「用户 N」。语音、视频、表情包只给一行说明。被引用的图片和文件用被引用消息的 ID 走官方资源接口下载，与当前消息的附件同样处理。
3. 接口读不到时，用机器人收到过的入站事件原文兜底（私聊消息、群里 @ 过机器人的消息，保留 90 天）。

被引用消息必须与当前消息在同一会话。撤回的消息标成「[引用的消息已撤回]」，其余读不到的标成「[引用消息内容不可用]」，不猜测原文。

权限：私聊消息和机器人自己发的消息不需要额外权限。群里引用**别人没有 @ 机器人**的消息时，接口要求应用额外开通「获取群组中所有消息」`im:message.group_msg`（飞书定为高级权限，按飞书推荐的审核规则需要企业管理员审核）。扫码创建的应用默认不申请它；缺少时接口返回 230027，worker 只记错误码，再按第 3 步兜底。开通后飞书会把群里所有用户消息都推给机器人；没开「群聊旁听」的机器人，网关照旧只处理 @ 机器人的消息，其余在落库前丢弃。

回复里的 Markdown 图片 `![说明](https://...)` 飞书客户端不会渲染外链。网关在终稿时由服务端取回图片（只访问公网地址，每一跳重定向都重新解析并固定 IP；10 秒、10 MB 以内，按文件头识别 PNG/JPEG/GIF/WEBP/BMP/TIFF/ICO），用机器人的 `im:resource` 权限上传换得 `image_key`，卡片内嵌原生图片，下一行保留「查看原图」链接（正文已链过同一地址就不重复）。普通消息兜底和超长分片里的图片作为富文本 `img` 节点单独成段。流式输出期间、下载或上传失败、超过每条 9 张时，图片显示为链接而不是裂图；失败的地址 5 分钟内不重试。签名地址带凭证，日志只记失败原因。内网地址不会被抓取，内网图床的图片只显示链接。飞书不做语音转写，明确提示暂不支持语音消息。长文本分片按 JSON 转义后字节数计量。通知应用发送限速与机器人流式发送分别留有余量。

### 群里的话题

飞书群里的每个话题有自己的会话（会话键 `<chat_id>#topic:<thread_id>`），主聊天区仍是 `chat_id`。话题里的消息、`/new`、`/stop` 只作用于这个话题；话题之间、话题与主聊天区互不排队，各自串行。

话题里第一次 @ 机器人、而这个群的主会话还在（没过期、没被清）时，这条消息先挂起，机器人引用它在话题里发一张卡片，只有发消息的人能选：

- 「独立开启新会话」：话题从空会话开始。
- 「继承主群会话」：话题的新会话从群主会话分叉出来，带着群里到此为止的上下文；之后话题和主聊天区各聊各的，互不影响。

5 分钟内没人选，或者话题里又来了消息，都按独立处理，挂起的消息照常处理。群主会话不存在时不问，直接独立。选过以后话题里不再问；话题会话超过 `session_ttl_hours` 被清掉后，再次找机器人时会重新问。

分叉由运行时原生完成（节点上报 `session_fork_v1`），只带群主会话**已经做完的轮次**：群里正在处理的那一轮不会以「做到一半」的样子进入话题。

- Claude：驱动在每轮结束时记下这一轮最后一条主线消息的位置；话题首轮直接 `--resume <群会话> --resume-session-at <位置> --fork-session --session-id <话题会话>`。`--resume-session-at` 是 Claude Code 的隐藏参数，被拒绝时退回不带位置的分叉；话题会话已经存在时改为普通续接。
- Codex：经 `codex app-server` 的 `thread/fork`；群会话正在跑时用 `lastTurnId` 停在它之前的一轮。app-server 不可用时退回 `codex exec fork`。群会话连一轮都还没做完时，话题从空会话开始。
- OpenCode：命令行只能从最新处分叉，所以群会话正在跑时，话题先回一句「群里的上一件事还在处理」，等那一轮做完再 `run --session <群会话> --fork`。
- 用量：分叉出的会话带着群会话的累计用量，Claude 与 Codex 都从群会话的计量基线起算，话题首轮只计自己。

群会话在这台节点上已经不存在时，话题会话从空会话开始，首轮本轮块附上群主会话最近的对话（与换运行时的续接相同）。未升级的节点直接附上这段对话。首轮成功后不再分叉。

求助同事的答复、机器人协作都留在发起它们的那段会话里：在话题里发起的，回到话题。

## 群聊旁听

按机器人开关（编辑机器人 → 交互与通知 → 群聊旁听），默认关闭：

- **关闭**：只处理 @ 机器人的群消息，与以前一样。
- **试运行**：能看到群里所有消息，每次判断都记录，但从不主动发言。
- **开启**：没被 @ 时由判断模型决定要不要主动说话；@ 它照常回答。

开启前要做三件事：

1. 填写「旁听职责说明」：它负责什么、什么时候该说话、什么时候不该。判断模型只看这段说明和最近的群消息，不看系统提示。
2. 飞书应用要有权限 `im:message.group_msg.include_bot:read`（获取群组中用户和机器人发送的消息，高级权限，需企业管理员审核），否则飞书不推没 @ 机器人的群消息。编辑页的旁听开关下会直接显示权限状态：缺少时点「扫码补齐权限」，用应用所有者或管理员的飞书账号扫码确认，就会连同这项权限一起补齐，不用去飞书开发者后台；已补上但还在等审核时可以「向管理员申请授权」。从关闭切到试运行或开启时，后端会向飞书确认这项权限已授权，未开通或待审核都会拒绝（409）。已经开着的机器人缺权限只提示、不强制关闭。「飞书应用」页签只对开了旁听的机器人把这项权限列为缺失。
3. 部署配置 `OPENAI_API_KEY`（可选 `DECISION_MODEL`，默认 `gpt-6-luna`）。判断由平台进程直接调用 OpenAI Decisions API，不经运行时节点；没配密钥时不能开启。

工作方式：

- 没 @ 的群消息落库后不建对话任务（群聊会话按群共用，建任务会替代正在进行的回复），只更新这个群的旁听状态，并排一个延后的判断任务。群里安静 `group_observe_quiet_seconds`（默认 15 秒，给同事之间的问答留出打字时间）后，只有最新那条消息的任务真正判断；一直有人说话时最长等 `group_observe_max_wait_seconds`（默认 60 秒）。上次判断之后来的消息算一批，一起判断、一起处理，不逐条处理。
- 判断输入是旁听职责说明和最近 30 分钟内的 20 条群消息（别人发的入站消息加它自己发过的话），发言人按通讯录名字，认不出的叫「同事 N」「机器人 N」。这一批消息标为 `new`，判断题问的是这一批里有没有需要它回应的。概率高于 `group_observe_threshold`（默认 0.3）才插话；请求失败、超时（3 秒）或模型拒答一律不说话。
- 说多说少不设冷却和次数上限，交给模型（它能看到自己刚说过的话，判断指令要求不重复自己）。代码只管三件事：这个群里有回复在排队或在跑时先不判断，等它做完再把这期间来的消息作为一批判断（它刚发的回复写的时候没看到这批消息，不算已经回答；最多等半小时）；`@机器人 安静`（或「别说话」「闭嘴」）让它在这个群静音 2 小时，`@机器人 可以说话了` 解除；最近一条人类消息之后机器人消息（含所有机器人）连续达到 `group_observe_bot_streak_limit`（默认 3）条就暂停主动插话，直到有人说话，防止机器人之间无限接话。
- 同一个群里有几个机器人开着旁听（开启）时，同一条消息可能都判断该说话。这时不马上开口，先等 3 秒让其他机器人也判断完，再由概率最高的那个接话（并列取先判断的）；其余记为「让给同群更合适的机器人」，不进入 agent 回合，所以没说话的机器人也不会在后台做事。判断得晚、别的机器人已经接了这条消息的，也让开。被选中的机器人看完上下文仍可能输出 `<NO_REPLY>`，这时这条消息没有人回应（宁可漏答）。只有一个机器人旁听时不等待。
- 其他机器人的消息（插话、答复、AI 员工之间的求助，带不带 @ 都一样）不触发判断，只记进上下文和机器人连发计数；人说的那条还没判断时照旧等着，机器人说完、群里安静下来再判断。该不该接话只看人说了什么。白名单不为空的机器人，只有白名单里的人说的话能触发插话。
- 群里有开着旁听的调度员（试运行或开启）、且它也收到了这一批消息时，其他员工在这个群不判断（任务结果记 `skipped: dispatcher`，不写判断记录），被 @ 照常回答，在别的群照常旁听。调度员还在试运行时，这样的群里没有人主动接话。
- 插话像一位旁听的同事：**只答不做**。插话回合可以做只读查询来回答，只说结论、一两句话；不改数据、不提交发布、不建定时任务、不索要凭证、不找同事求助，也不开始要花几分钟的工作——这些能力在插话回合里根本不挂（求助同事、个人工具、本人定时任务、个人凭证都不注入）。确实需要它动手时，它用一句话认领并说明要做什么（如「这个我可以处理：把这 3 笔订单取消。需要的话 @我 确认就开始」），等对方 @ 它，再走正常回合，执行人和执行内容在群里都看得见。
- 插话回合不推流式卡片、不加「敲键盘」表情，终稿出来再整张发，不带「✅ 回复已生成」；agent 看完上下文觉得不需要说话时输出 `<NO_REPLY>`，什么也不发，出错、被停也不出声。跑了 10 秒还没说完，先引用触发消息回一句「我看一下。」，免得大家以为没人管、各自去做；之后改主意或出错也会补一句交代，不会没有下文。插话最长 90 秒，超时就停下，改发「这个要多花些时间，需要的话 @我，我接着处理」。插话回合从不替代别的回合：判断后有人 @ 了它，就让给那一轮。
- 机器人在一个群里第一次主动说话时，末尾附一句说明：它会留意群里的消息、和职责相关的会主动回答，不需要时 @ 它说「安静」。
- 群里同一个机器人只有一条会话。以前谁 @ 它都会停掉正在做的那一轮（「⏹ 已收到新消息，上一个任务自动停止」），别人交代的事会被打断。现在**换了一个人 @ 它时排队**：等手上的事做完再处理，飞书上会引用这条消息回一句「收到，我先把手上的事做完，接着就处理这个」；同一个人接着发的消息仍替换自己上一条（前面有别人的事在排时一起排队）。主动插话不算，谁 @ 它都让给谁。企业微信群同样排队，但不回排队提示。
- 开了旁听后，@ 它的回合也带上最近的群聊记录（以前只看得到 @ 它的那条）。记录只作背景：本轮块里写明只处理本轮这条消息，记录里更早的问题和请求不是本轮任务，除非这条消息是在接着记录里的内容说（如「上面那个」「你看下」）；插话回合则写明回应最后一条消息所在的话题；这一批有好几条时，记录里把它们标为【新】，要求这一批里需要回应的在这一轮一并处理（调度回合同样）。本轮这条消息只在正文出现，不在记录里重复。
- **调度员**：在编辑页把「群聊角色」设为「调度员」，它在群里只负责安排，不自己回答或干活。第一段判断题换成「新来的这批消息里有没有在请人办一件具体的事、还没人接」，输入是「团队简介」（调度员的旁听职责说明）和最近的群消息；判断为是时排一个调度回合（会话键 `dispatch:<群>`，每个群一条）。调度回合的本轮块列出这个群里能接任务的 AI 员工（已启用、在群里、发起人在它的白名单里，附各自的旁听职责说明）和这个群最近 10 个任务，调度员按固定格式输出一个 JSON 决定：建任务（最多 3 件）、追加到已有任务、先问一句澄清，或不用安排。调度回合不挂业务系统令牌、求助同事、个人工具、定时任务和凭证，最长 60 秒。试运行时，决定校验通过后记成状态为「试运行」的任务（`work_tasks` / `work_task_events`），原始输出和校验结果写进判断记录的 `dispatch`，群里什么也不发，也不真的交给员工。开启后同样落库，但任务直接交给执行员工：平台在原消息上排一轮它的对话（会话键 `work:<编号>`），调度员回原消息一行「@员工 标题（T-n）」（追加时「补充给 @员工 了（T-n）」，澄清时发它问的那一句）；一问一答这类不跟进的任务也回一行「交给 @员工 了：标题」，不带编号。调度员等群安静的时长比旁听默认值短：多人群 8 秒，单人群 3 秒（旁听安静时长设得更短时以设置为准）；开启时调度回合一开始就在原消息上打「处理中」表情，安排的那一行发出或决定不说话时撤掉，试运行不打；单人群里网关收到消息就打（约 1 秒），调度回合结束时撤掉这一批几句上的表情，没排出调度回合的 3 分钟后自动撤掉。群里只有一位真人时（按飞书群信息里的真人数，按群缓存 5 分钟），不问判断模型，每批消息都排调度回合（判断记录为「单人群」），调度员每条都回应：要办的事照常分派，闲聊、致谢这类不需要安排人的话直接回一句。执行员工以发起人的身份做，回复挂在原消息上，第一行写「T-n 完成：」或「T-n 卡住了：」，有后果的操作先请发起人确认；这一轮结束后任务记为已完成、等确认或未完成。之后 @ 执行员工并带上编号，或回复它的任务回复并 @ 它，会接着这个任务做。管理台「任务」页列出所有任务，所有登录成员都能看；详情里给人看的部分直接显示，给执行员工的要求、调度依据和当时的群聊逐项展开。设计见 `docs/superpowers/specs/2026-11-02-group-dispatcher-and-work-tasks.md`。
- 每次判断（含跳过的原因）都写进 `group_observe_decisions`，保留 30 天。机器人详情的「群聊旁听」页签按群列出记录，「会插话」的可以展开当时的群消息，并标注「该说 / 不该说」。建议先试运行一段时间，确认没有乱接话再开启。
- 判断服务和机器人所用的模型服务都会收到最近的群消息，开启前请确认符合企业的数据要求。

## 定时任务通知设置

通知目的地在「定时任务 → 新建／编辑 → 通知设置」中配置，AI 员工编辑页只保留欢迎语。

- 私聊和群聊使用当前 AI 员工所属平台；飞书员工直接发飞书消息，无需 Webhook。接收人必须绑定相应平台身份。私聊未建立时，系统仅在存在唯一可用通知应用时尝试应用通知，否则展示失败原因。
- 群聊下拉展示该员工已收到过事件的群聊 ID，也可输入其它可达群聊 ID；选择记录不保证机器人当前仍在群内。
- 邮件继续使用平台配置的 SMTP。
- 「附加通知：企微群机器人」可用于跨平台同步。例如飞书员工向飞书群发送，同时同步到企微群。仅支持官方企微群机器人 HTTPS 地址，并且必须带非空 key。
- 新任务默认关闭企微群 Webhook。每个任务独立加密保存地址，页面只显示是否已配置。编辑时留空保留原地址；「移除已保存的地址」会关闭该渠道并在保存后清除地址。
- 保存后，在任务列表点击「发送测试通知」，向已保存的接收人发送固定测试消息，不运行 AI 任务。测试记录可刷新，待发送不代表已送达。正式运行的投递记录仍在执行记录中查看。
- 测试通知仅允许任务创建者发起；需要当前版本号。通知记录仅对有权操作该员工的用户开放，不返回 Webhook 或密文。

从通知 Webhook 仍配置在 AI 员工上的早期版本升级时，数据库迁移会把每个旧任务对应的员工 Webhook 复制为任务自己的加密地址，保持原开关；没有地址的任务关闭空开关。迁移需要原 MASTER_KEY，必须先完成数据库迁移再启动新版 API、调度器和 Worker。旧员工数据库字段保留用于兼容升级前已入队的任务，新任务不再继承它。


## 临时表情与思考过程

接管用户消息后，网关以当前机器人的身份添加 `Typing`（敲键盘）表情。
需要应用权限 `im:message.reactions:write_only`；缺少权限不会阻断正常回复。
只有首段可见正文成功送达后才移除表情，思考增量、空占位和新会话链接不触发移除。
结束、失败或取消后也会收尾；清理失败独立重试，状态持久化以支持网关接管。

思考区使用带文字标题的折叠面板，预览最近五个非空逻辑行（每行预览最多 240 字，客户端可能自动换行）。
飞书 Markdown / 折叠面板没有网页式固定高度滚动属性；完整内容通过受权限保护的会话页查看，
思考文本使用五行高度的滚动区域，向上阅读时不强制追随最新内容。没有底层会话链接时不显示入口。

会话页的访问规则：

- 私聊（飞书、企微）会话归发言人本人：本人登录后即可查看，不要求管理角色，也不受链接有效期限制。转给别人、用机器人 bot_token 登录或会话里出现他人记录时都打不开。未登录时先跳到登录页，登录后回到原链接；在飞书客户端内打开会直接走飞书登录。
- 对话记录在机器人开始处理这一轮时就写入（状态「进行中」），第一轮还没回复完也能按记录判断会话属于谁，链接本身不带凭据。升级前发出的私聊链接带本人凭据（24 小时有效，绑定发言人、会话与运行时节点），仍然可以打开。
- 群聊会话仍只允许管理角色查看；企微私聊管理角色也可查看；飞书私聊管理角色不能代看。
- 每次打开会话页都记审计 `runtime.session_view`，注明放行依据：链接（`link`）、本人（`owner`）或角色（`role`）。
- 发言人没有绑定员工身份的飞书私聊不显示入口（没有人能打开）。
- 非管理角色查看需要节点的 Runtime 已升级（心跳上报 `owner_session_view_v1`）；旧 Runtime 的会话记录里还带着环境变量，升级前只有管理角色能打开，其他人会看到「请联系管理员升级运行时」。
- Runtime 记录会话时不再保存请求里的环境变量（机器人密钥、访问令牌），会话页和节点磁盘上都没有这些值；升级前落盘的记录在 72 小时清理周期内自然过期。

CoreMan 不再只保留最后 200 字；Daemon 的 Claude 流式翻译器传递上游实际提供的思考增量、
工具参数及工具结果，Codex 传递其提供的 reasoning 文本及命令、文件修改、网页搜索、MCP 工具等执行详情。
上游未返回的推理不会补写。新过程日志写入 Daemon 会话记录，旧会话不回填。

发布需要先执行数据库迁移 `0025`，再更新服务镜像及运行时 Daemon 驱动。
旧驱动仍可工作，但不会产生本次新增的工具详情与过程日志。仅更新网关不能补齐旧驱动未发送的内容。

本轮验证：隔离 PostgreSQL 覆盖表情跨重启恢复、首段正文投递失败、清理重试和权限降级；
飞书测试应用实际接受 `Typing` 添加/删除、新思考面板及完整过程按钮。
示例正文更新成功后才调用删除表情接口，客户端已确认表情消失。

思考标题在尚未输出正文时每约 3 秒循环显示 `🤔 思考中.`、`..`、`...`，
工具等待期间仍更新；正文开始或任务结束后显示静态标题 `🤔 思考过程`。标题单独局部更新，
不重置面板展开状态；标题更新失败不阻塞正文投递。

回复默认用飞书卡片 JSON 2.0 呈现：模型在 Markdown 里写 ```` ```card:<类型> ```` 块，就能显示图表、表格、指标块、图文、时间线、提示条和彩色标题栏，深浅主题下都清楚。回复结束时整卡替换成富卡片；飞书拒绝时原地退回只有 Markdown 的简化卡。每个 AI 员工可在编辑页「富卡片回复」关闭。块语法、投递细节和真机预览命令见 [飞书富卡片回复](features/feishu-rich-cards.md)。需要数据库迁移 `0049`。

## 个人助理应用

平台应用（`platform_apps`）勾选 `assistant` 能力后，飞书网关把它当作个人助理应用：

- **一个应用一条长连接。** 连接租约在 `app_leases`，由飞书网关的 supervisor 认领，每个应用起一个子进程；应用下还没有任何人开通时也保持连接。应用停用、去掉 `assistant` 能力或删除时断开；密钥变更时自动重连。
- **只接私聊。** 私聊消息、进入私聊、卡片回调按当事人的 `user_id`（来自通讯录同步）找到他本人的助理记录，之后的处理与普通机器人相同。还没开通的人私聊（或打开与应用的私聊）时，平台私信他一张开通卡片（见本节「开通与停用」）；通讯录里认不出的人只记一条日志。
- **群消息丢弃、不入库。** 被拉进群时应用会自己退群，退成功后私信拉群的人说明只支持私聊；退群失败只记日志（`assistant_leave_failed`），不发说明。
- **卡片只认所有者。** 回调按操作人路由，并且卡片必须在操作人与自己助理的私聊里：有他与助理的私聊记录且会话一致，或者这张卡片就是他本人的助理发出去的（所有者还没给助理发过私聊时靠后者，比如助理主动发来的卡片）。两样都对不上的点击按「不是提问人」拒绝。回复按钮的点击一律按私聊处理。
- **出站。** 同一个子进程发送该应用下所有助理记录的回复与通知。记录停用后，子进程下一轮就不再为它发送，并放掉它的出站锁。
- **内容加密。** 助理的消息内容按所有者的数据密钥加密存放。回复上下文（`inbound_events.reply_context`）里只有路由用的键留明文（会话、被回复的消息、时间等），卡片回复按钮的文字在密文里；流的回复上下文只保留路由用的键。所有者的数据密钥销毁后，读不出来的出站消息标为 `skipped`（`content_locked`），读不出来的流式回复直接收尾，都不再发送。
- **个人知识库。** 每位助理有一个只属于所有者的知识库（表 `assistant_pages`）：页面按路径存取，路径、标题、摘要、正文都用所有者的数据密钥加密，库里另存一个路径的带密钥摘要用来保证同一路径只有一页（路径不分大小写，首尾与重复的斜杠忽略）。助理用 `notes_index`、`notes_read`、`notes_search`、`notes_write`、`notes_delete` 读写，这些工具不经审批；`notes_write` 是整页替换，带版本号做乐观锁，两处同时改同一页时后写的一方收到 `version_conflict`。上限是每人 2000 页、合计 20MB、单页 200KB；检索是把这位助理的页面解密到内存后按关键词匹配，没有密文索引。标为置顶的页面（口吻、判断原则这类每轮都用得上的短规则）和全部页面的索引，由平台在主会话每个会话的第一轮放进本轮块（随用户消息传给 CLI，不进命令行）；之后的轮次只在置顶页有更新时补一条变更说明。页面内容进本轮块时一律当引用：正文逐行加「> 」前缀（回车、Unicode 行分隔符等都算换行）；索引每页一行，路径、标题、摘要压成一行后同样加「> 」前缀；置顶页的路径与变更说明里的路径清单也在引用行里。其中的「【」「】」换成「〔」「〕」。平台自己写的行里没有页面的任何文字，页面里自己写的块结束标记或「平台规则」冒充不了平台的话。置顶、取消置顶、改写或删除已置顶的页只能在所有者发起的轮次里做：平台自己发起的轮次与子任务里这些操作返回 `pin_requires_owner`，不置顶的页照常可写。置顶页正文合计超过 24KB 时只给索引，索引本身超过 16KB 时只列出置顶的与最近更新的。已知限制：置顶页被删除或取消置顶后，同一个会话里不会收到说明，最迟第二天换新会话时纠正；助理自己上一轮改过的置顶页，下一轮会再收到一次全文。所有者的数据密钥销毁后知识库读不出来，工具返回 `content_locked`。
- **待跟进。** 助理替所有者记着跨天的事：等他决定的、他答应了别人的、在等别人的、到日子要提醒他的，共四类。每条在这位助理内有一个递增的编号（显示为 `F012`），带一个可选的期限和一个可选的回看日期；日期按所有者的时区（助理设置里的 `timezone`）算。助理用 `followup_add`、`followup_update`、`followup_snooze`（推到之后的某一天，到那天重新出现）、`followup_close`、`followup_list` 读写，这几个工具不调飞书、不过审批、不依赖飞书授权，每个结果都带所有者时区的今天（`today`）。标题与备注按所有者的数据密钥加密存放（表 `assistant_followups` 的 `title_enc`、`notes_enc`）；分类、状态、日期、编号是明文，运维只看得到这些。同一位助理未结的条目最多 500 条，标题最长 200 字、备注最长 4000 字。条目记了起因消息的，那条消息被撤回时自动关闭（状态 `dropped`、`close_code` 为 `origin_recalled`；发现撤回并触发关闭在盯消息那一层）。所有者的数据密钥不可用时，写标题或备注返回 `content_locked`，不会存下空内容；只改日期、推后、关闭不受影响。需要数据库迁移 `0096`。
- **告警。** 连接异常按应用告警（键 `gateway:app:<应用 id>`），不按每个人的助理记录告警。
- **写操作要审批。** 助理调用任何会改动飞书内容的个人工具（发消息、改文档、处理审批、日程、任务、邮件等）都不会直接执行，而是向所有者提交一张 Tower 审批单，批准后由平台执行。唯一的例外是在别人发来的消息上打「处理中」表情。带文件的操作（发文件、存入云空间、邮件附件）同样过审批，需要部署方另配一个临时桶，没配时这类操作不可用。部署要求见 `docs/tower-approval.md`「个人助理的审批闸门」。
- **在节点的沙箱里运行。** 助理只在助理专用实例上跑（见 `runtime_daemon/README.md`「个人助理的沙箱」）：要跑助理的机器上以专用的系统用户、带 `--assistant-only` 再装一份守护进程，普通员工那份不动。只有这样的实例自检通过后声明沙箱能力，它只跑沙箱里的轮次和少数几种节点命令；不是助理专用实例的守护进程从不跑助理。助理绑在助理池（管理员用 `PUT /api/admin/relay-servers/{id}/assistant-pool` 加入）或所有者本人的私有运行时上；所有者想用自己的机器，也要在那台机器上装一份助理专用实例。
- **跑助理的节点不承载普通员工。** 不论助理池还是私有运行时：节点上没有普通员工（含停用的、正在迁过来的），与它同机同 uid 的节点上也没有，节点上报了本机指纹与 uid 且不是 root。每一轮开轮前都核对，不满足时助理暂停并在私聊里说「绑定的运行时没有与普通员工隔开」，不带节点或主机的信息；助理换运行时同样核对；普通员工绑定或换运行时选不了跑着助理、正在迁来助理、声明了沙箱能力的节点，以及它们同机同 uid 的节点。
- **暂停与转录。** 所在节点离线、排空、不能隔离运行或不满足上一条时，助理暂停并在私聊里说明，不会换到别的节点；助理池开关被关掉时，绑在那里的助理同样暂停，直到管理员改绑。CLI 的转录每轮结束后加密存进平台、节点上删除，续聊前再下发；转录超过 50MB 或没能传回来时，下一轮从新会话开始（排队超时、确定没有节点领到的那一轮除外，下一轮照旧续上）。每个节点同时跑的助理轮次由设置 `assistant_node_concurrency`（默认 2，范围 1–32）限制，超出的排队。
- **聊天之外对助理关闭的功能。** 装技能、MCP 登录、管理台里的工作目录文件与 git 管理、规则文档备份、运行环境检查、定时任务、告警来源、审批人设置。换运行时只落到目标上一个全新的空目录：工作目录里的文件、会话与记忆都不带过去，换完后的第一轮带上平台保存的上下文说明；目标目录已存在就拒绝；换走后旧目录由平台登记、经原来那台节点删掉（节点离线就等它回来再删），删掉之前助理回不到那台节点；还没开通好、正在停用或已停用的助理不能换运行时（预览同样拒绝），换的过程中停用开始了，这次换就作罢、刚建的新目录登记待删；没开通好或已停用的助理也不能初始化工作目录；还有助理的工作目录等着删的运行时实例不能删除（409）。换运行时与换运行时的预览只有所有者本人能做，也不能自选目录。助理记录不能用启停开关启停，也不能在停用完成之前删除；平台管理员可以在助理列表里停用某人的助理（只回状态，不回任何内容）。
- **助理设置。** 每位助理在 `assistant_settings` 里有一行：授权完成、助理开通好的同时，平台记下所有者在飞书里的身份（`open_id`、`tenant_key`、飞书用户编号）与他和助理的私聊，取自点「开通」时飞书给的操作人与开通卡片所在的私聊，不来自任何请求内容；另有时区（默认 `Asia/Shanghai`）、工作时段（默认 `09:30`–`19:00`，不跨午夜）、工作日（默认周一到周五）、重点群与忽略的会话（按所有者的数据密钥加密）、每日轮次预算与「上班」「下班」的临时切换。需要数据库迁移 `0094`：已开通的助理从最近一条完成的开通流程回填身份；更早建的助理（迁移 `0093` 之前）没有可回填的记录，重新开通后才有。
- **平台自己发起的轮次。** 交回事项、子任务及其结果这几类任务（`assistant_handover`、`assistant_subtask`、`assistant_job_result`；下班编译是一个子任务）不由所有者的消息触发，没有入站事件。它们只能由平台代码经同一个入口入队，网关与任何接口都产生不了：任务入队处另有一道运行时的闸，没有入站事件的这几类任务（以及没有入站事件的审批结果回合）不是从那个入口来的就抛错。跑的时候发言者固定为所有者，回复发到所有者与助理的私聊。这样的一轮要用所有者的个人工具时，平台不凭请求里的任何身份，而是逐项核对：记录是开通好、启用中的助理，任务归所有者、会话是这位助理的，所有者账号启用，通讯录里的飞书身份与授权行都还是开通时记下的那个；任何一项对不上就拿不到个人工具。没有记下身份的助理入不了这类任务。在这样的轮次里提交的审批单，结果同样投回所有者的私聊；所有者私聊那一轮里提交的审批单，等到有结果时那条入站事件已被清理的，也走这条路投回。助理暂停期间这类任务直接记为失败（`assistant_paused`），不再私信所有者。任务在认领后才遇到暂停的，同样不私信。这样的轮次没有人在场，输入可能来自别人发给所有者的消息，所以比所有者亲自私聊的一轮收得更紧：不挂云签名代理、业务系统操作目录和所有者的个人凭证（个人凭证的规则仍在提示词里，本轮块说明这一轮用不了）；不下发以所有者身份签发的业务系统令牌（`BOT_TOKEN_*`）、业务系统账号与令牌配置，业务系统的 MCP 服务也不挂（「业务系统访问」段仍在提示词里，本轮块说明这一轮用不了；机器人自己配的环境变量照常下发）；授权工具只有 `feishu_authorization_status`，`feishu_authorize` 与 `feishu_revoke_authorization` 不列出，调用返回 `owner_turn_required`；置顶页动不了（见上面「个人知识库」）；不记所有者触达（`user_reached`），worker 失联后由看护补写的记录也一样。所有者优先：开轮时不取消同会话的其它任务，同会话有别的任务在跑、或所有者的消息在排队时，自己放回队列稍后再认领（等待从 15 秒起逐次加倍、最长 5 分钟，认领满 10 次仍轮不到就记失败 `platform_turn_yielded`，不私信）；反过来所有者一发消息，正在跑的这类轮次被取消（`superseded`）。「无人在场」按任务类型判断，不看有没有入站事件：审批结果回合（`assistant_approval_result`）即使沿用提交那一轮的入站事件，也同样让路、同样收紧（上面各项与置顶页的限制都适用），只是身份仍按那条入站事件核验。
- **盯消息。** 平台以所有者的身份轮询飞书，不经模型：scheduler 单独的一条循环每 5 秒认领到期的助理，每位助理在所有者的工作时段内每 60 秒轮询一次，各人的时刻错开。只有记录启用且开通好、记下了身份、冷启动已完成、在上班时段、运行时没暂停时才轮询。一轮只列一次会话（单聊与群，按最近活跃倒序，前 50 条），与上一轮的顺序对比：排到前面的会话都读；顺序没变的从第一个开始逐个读，读到一个没有新消息的为止；所有者标记的重点群（最多 5 个）每轮直接读，连同最近的 3 个话题。所有者与助理自己的私聊、他设为忽略的会话不读。第一轮只记下顺序，不读历史。之后第一次读到的会话（所有者刚被拉进一个有历史的群、很久没动静被挤出游标的会话又活跃了）只回看 30 分钟，轮询停得更久（下班一夜、退避）时回看到上一次成功轮询为止；从忽略名单移出的会话从移出那一刻读起；发出超过 24 小时的消息不入箱。读到的消息只在内存里分级：私聊、群里 @ 本人、重点群里的消息立即交回；其他群里真人的消息、私聊里机器人发来的通知（如审批待办）每 5 分钟攒一批；所有者 10 分钟内在这个会话里亲自发过言的先压着，等他停下满 10 分钟；所有者自己发的、群里没 @ 他的机器人消息、忽略的会话不要。要交回的条目写进 `assistant_inbox`，摘要按所有者的数据密钥加密，库里另有会话、消息、话题的编号与时间；同一条消息只入箱一次。盯消息自己的状态（各会话读到的位置、上一轮的会话顺序）同样按所有者的数据密钥加密。对方撤回了还没交回的消息时条目作废，由那条消息引起的待跟进自动关闭。把条目交回给助理由投递层负责。不轮询的时候（下班、暂停）平台每 24 小时刷新一次令牌，授权不会因此过期。飞书按应用限频（列会话与读历史各每分钟 1000 次，全员共用）：平台记下助理的这两类调用，用量到六成时所有人的间隔翻倍、到八成时变四倍并打告警日志 `assistant_watch_budget_tight`，满了或被飞书限频（HTTP 429 或错误码 99991400）时按应答头给的秒数退避；助理工具自己的调用只计数不拦，撞上限频时工具返回 `rate_limited` 与等待秒数（普通员工的个人工具同样返回它，而不再是笼统的失败；刷新令牌时被限频不再把授权当成过期清掉）。一轮里读到一半出错时，已入箱的条目、已读完的会话的进度与这一轮里换到的新令牌照常保存，下一轮接着来。同一个会话连续 3 轮被飞书拒绝读取时先放下它 1 小时（日志 `assistant_watch_chat_parked`），别的会话照常盯；一个会话一轮最多读 100 条，积压多时下一轮接着读；缺编号或读不出时间的消息跳过，只记个数（日志 `assistant_watch_messages_skipped`）。停用助理的第一步就是停止盯消息并作废没交回的条目。平台管理员在 `GET /api/admin/assistants` 的每条记录里看到 `watch`（`state`、`last_ok_at`、`last_error` 的代码）。需要数据库迁移 `0097` 与 `0101`。已知限制：每个会话只跟最近 3 个话题；顺序没变的会话一轮最多逐个读 10 个；没记下身份的助理（迁移 `0093` 之前建的）不轮询，重新开通后恢复；经审批由平台代所有者发出的消息在飞书里也是所有者本人发的，同样会让那个会话压着 10 分钟。
- **交回事项。** 盯消息攒下的条目由平台排成助理主会话里的一轮（任务类型 `assistant_handover`）：立即交回的最多 5 秒后入队，攒批与压着的到点才交回，一轮最多带 30 件。同一位助理同一时刻至多一轮在途；这一轮正常结束，条目才记为已交回，被所有者的消息打断、让路放弃、运行时暂停或失败时条目回到待交回，至少一分钟后由下一轮带上（真失败满 3 次的条目作废）。任务载荷里只有条目编号，消息摘录在开轮时才解密；整理稿里别人写的字都在以「> 」开头的引用行里。下班、冷启动没做完、运行时暂停或有公告时不入队，条目留在收件箱，恢复后一并交回，期间不发私信。交回的这一轮无人在场：不挂云签名代理、业务系统目录与个人凭证，授权工具只能查询。
- **每日预算、每天换新与顺带检查。** 每位助理每天（所有者时区的自然日）的轮次预算由设置 `assistant_daily_turn_budget`（默认 200，范围 10–2000）决定，所有者的设置里另有数时以那个为准；数的是当天真正开了轮的次数。用完后只有立即交回级别的事项照常交回（至多再透支 20 轮），其余留到次日，并在私聊里告知一次。助理与所有者的主会话每天换新：当天第一轮从新会话开始，置顶页与索引重新注入；跨天的连续性靠待跟进与知识库。平台另外每 5 分钟为每位在上班的助理做一次检查，不经模型：待批的发消息类审批单（发送、回复、转发、发文件）在所有者已亲自回复、被回复的消息被撤回或会话又有新消息时自动撤回（审批单的 `error_code` 为 `owner_replied` / `anchor_recalled` / `anchor_moved`）并告知助理；已交回的消息在 24 小时内被对方撤回的，关掉它引出的待跟进并告知助理；「处理中」表情挂了 4 小时、当天到期的待跟进，各自每天提醒助理一次。飞书要求授权满 365 天重新授权：到期前 14 天起平台每天在私聊里提醒所有者一次。
- **上下班与设置。** 助理只在所有者的工作时段里看他的飞书消息、交回事项；下班后所有者在私聊里说话照常回应。默认周一到周五 09:30–19:00、时区 `Asia/Shanghai`，工作时段不支持跨午夜。私聊里发「上班」「下班」（或 `/上班`、`/下班`）临时切换，平台直接处理并回复，不经模型：「上班」到当天的下班时间为止（当天不是工作日或已过下班时间则到当地次日零点）；「下班」到下一个工作时段开始。到点自动恢复按工作时段。只有所有者在私聊里发、整条消息就是这个词时才生效。要改工作时段、工作日、时区、重点群或不想看的会话，所有者直接在私聊里告诉助理。助理用 `assistant_settings_get`、`assistant_settings_update` 读写；这两个工具只在所有者发起的轮次里可用，交回轮次、审批结果回合等无人在场的轮次里返回 `owner_turn_required`。重点群至多 5 个、忽略的会话至多 50 个，名单加密保存。改了时段、工作日或时区会清掉当时的临时切换。下班时（按工作时段自动下班，或发了「下班」）平台给助理派一个「下班编译」子任务（见下面「子任务」；平台派出，不占助理每天 20 个的名额，做完不投回主会话，也不往私聊发东西）：把当天的进展、被拒与已执行的审批、有变化的待跟进整理进知识库。子任务没有审批工具，被拒与已执行的审批单的摘要和所有者写的拒绝原因由平台写进交代（放在引用行里，交代至多 8000 字，放不下时略去最早的并注明张数）。每位助理每个自然日（所有者时区）至多一次；当天没有任何活动、当日轮次预算已用完、进行中的子任务已满 3 个时不派。它无人在场：改不了置顶页（想改的规则写进普通页面 `inbox/pinned-suggestions.md`），不带云服务与业务系统的凭据。任务类型 `assistant_compile` 不再入队。
- **冷启动。** 飞书授权完成后助理即可在私聊里使用；盯消息要等冷启动做完。①平台以所有者身份读他最近 7 天、最近活跃的至多 8 个会话，只留他自己发出的文本消息（至多 200 条、每条截到 300 字），交给助理归纳成置顶页 `profile/voice.md`（口吻样本）。这一轮（任务类型 `assistant_cold_start`）跑在独立会话里，除了保存这一页的 `assistant_voice_save` 之外没有任何工具，读不到别人的消息与知识库。自己发出的消息不足 5 条时跳过这一页；读不到时每 10 分钟重试，满 1 小时放弃这一步。②助理在私聊里依次发四张卡片：上级与主要协作人、负责的事（各存成置顶页 `profile/people.md`、`profile/duties.md`）、重点群（从最近活跃的群里选，至多 5 个；列不出群时自动跳过这一题）、工作时段与时区。每一题都可以点「跳过这一题」；发「跳过」整个跳过。卡片上读不到的填写项按没填处理，照样进入下一题。③四题答完、跳过，或开通满 24 小时仍没做完（按默认设置完成，并私信告知）之后，助理开始在工作时段里盯消息。本功能上线前已开通的助理不会自动开始盯消息：所有者下一次在私聊里发消息时才开始冷启动。在引入助理设置（迁移 `0094`）之前开通、没有记下身份的助理需要重新开通。
- **平台代发的消息不算所有者亲自发言。** 审批通过后由平台以所有者身份发出的消息（发送、回复、转发、发文件），平台记下它的编号（表 `assistant_sent`，只有编号，留 30 天）；盯消息读到它时不入箱、不压着那个会话，也不更新「所有者上次发言」。scheduler 停止时，正在轮询或检查的那位助理最多再等 20 秒把事务提交完，刚刷新的令牌不会因此丢失。
- **助理自有工具的分组。** 个人工具 MCP 上助理自有的工具，普通轮次（所有者的私聊、交回、结果回合）分三组：`knowledge`（知识库、待跟进与助理设置）、`approval`（审批单管理与「处理中」表情，连同写类个人工具的提交审批）、`jobs`（派子任务、追问、查看、取消；之后还有调度公共员工）。子任务的一轮只有 `knowledge` 组、读类个人工具，以及只给它的 `subtask` 组（`assistant_job_blocked`）：写类工具、审批工具与 `jobs` 组都不列出，调用也不受理。另有一组 `voice` 只给冷启动的口吻样本那一轮：那一轮只有 `assistant_voice_save` 一个工具，个人工具、授权工具与别的组都不列出、不受理。`knowledge`、`jobs`、`subtask`、`voice` 的数据都在平台自己的库里，飞书授权在一轮中途被撤销或重选之后照常可用。本人定时任务工具（`schedule_propose`、`schedule_list`）只在所有者亲自发起的轮次里有：交回轮次、审批结果回合、子任务及其结果回合、口吻样本这些无人在场的轮次不列出，调用返回 `owner_turn_required`。
- **子任务。** 需要花时间的调查，助理用 `assistant_spawn(title, brief)` 派给子任务：同一条助理记录、同一个沙箱，会话是独立的（会话键 `<私聊会话>#job:<编号>`），不占所有者的私聊，所有者发消息也不会打断它。子任务只读：个人工具里的读类、知识库与待跟进（置顶页除外）；没有写类个人工具、没有审批工具、不能再派子任务、不能发起或撤销授权、没有定时任务工具，也没有云服务、业务系统与个人凭证。它不往飞书发任何东西：回复流不推（回复上下文带 `_silent`），进度、长任务完成提醒、超时与中断通知都不发；它用 CLI 的提问工具时不开选择卡，题面留在结论里；撞上额度时不发切换卡，子任务按失败（`rate_limited`）收尾。最后一条回答加密存进 `assistant_jobs.result_enc`，再由平台作为单独的一轮（任务类型 `assistant_job_result`）投回私聊会话：这一轮里标题、结论、卡住的原因都逐行以 `> ` 引出，是数据不是指令；需要对外做的事由主会话决定是否提交审批。子任务缺所有者的决定或授权时调用 `assistant_job_blocked(reason)`，状态记为 `blocked`。主会话可以用 `assistant_job_message(id, text)` 在同一个会话里追问、`assistant_job_list` 查看、`assistant_job_cancel(id)` 取消。上限：同时进行中 3 个，助理自己每天派 20 个（所有者时区的自然日），一个子任务最多 6 轮，每次派出或追问起 2 小时没结束记失败（`job_timeout`）；子任务的轮次计入每日轮次预算，所有者不在场的轮次在预算用完后不能再派。失败、超时、轮次丢失同样投回一句说明；主会话自己取消的与停用时取消的不投回。投回的那一轮被所有者的消息打断时，至少 60 秒后重投，投到一次为止；连续 3 次真失败后不再投回（`report_code = 'undeliverable'`），结论仍可用 `assistant_job_list` 读到。子任务不出现在任务页；它的对话记录与转录和助理的其它轮次一样，只有所有者本人读得到、一轮结束就清出节点。停用助理时进行中的子任务一并取消。标题、交代、追问、结论、卡住的原因都是密文；状态、轮数、时间是明文。`GET /api/admin/assistants` 的每条记录多一个 `jobs_active`（进行中的子任务数）。需要数据库迁移 `0100`。
- **开通与停用。** 成员私聊助理应用会收到一张开通卡片，本人点「开通」后，平台按设置 `assistant_eligibility`（全员，或名单里的人与部门，含下级部门；存着的值通不过校验时谁都不放行）核对范围，要求账号启用且有登录名，在助理池里按设置 `assistant_backends` 的顺序挑一个能隔离运行的节点，建助理记录、数据密钥与一个全新的工作目录，再私信一张飞书授权卡片（全部权限、带离线访问）；授权完成后助理才开始处理消息，在那之前发来的消息只得到一句「还没开通完」。刚停用过的人马上重新开通，要等约一分十五秒（各进程缓存的旧数据密钥都过期）才建新记录，期间自动重试；应用密钥暂时解不开（例如主密钥轮换中）也是稍后重试，不会放弃；助理名字被别人的记录或普通员工占着时，开通失败并私信说明，请联系管理员。没有配置任何 AI 后端（`assistant_backends` 为空）时开通当场放弃并私信说明；暂时没有能隔离运行的池节点则继续重试。只要一个人名下还有没完全停用的助理记录，就算已经有助理，不能再开通。审批系统的账号平台事先查不到：开通卡片与欢迎语都提醒先登录一次审批系统，没有账号时第一次提交审批会如实告诉所有者。
- **停用。** 所有者在私聊里发「停用助理」（或「/停用助理」）并在确认卡片上点「确认停用」即停用。这条命令只在私聊里、平台一认出发送人就截下，不经过模型，也不会并进排队中的一轮：运行时被停用、有公告、或助理正等着回答某个问题时同样有效；不是所有者发的，什么都不回。停用的顺序是：停下在跑的轮次（已批准、还在排队的写操作也等它执行完，一共最多等 15 分钟），撤回待批的审批单，撤销飞书授权，销毁数据密钥并停用记录，再经节点删掉工作目录；之后可以重新开通，以前的内容读不出来。一旦助理不再是可用状态（已要求停用，或所有者账号停用满 24 小时进入停用），之后才送达的审批决定不再执行，这张单按「已撤回」收口，也不再发提醒；停用开始之前已经批准的写操作照常执行完。飞书授权在停用的最后一步再清一次，停用开始后既不能发起也不能完成个人授权。节点这一侧的删除：节点只在确知结果时才给定论（已删除，或登记记着这个目录是别的助理的），确认不了的（共享存储没挂上或报错、登记缺失或损坏、目录被人手工还原或复制过）一律答「无法确认」，平台保留这条待删记录、最长每 6 小时重试一次，登记的错误代码是 `dir_unverified`；没有登记的目录节点从不删。处理办法见 `runtime_daemon/README.md`「个人助理的沙箱」里的 `dir_unverified`。轮次开始时工作目录已不在原处或正在删除，这一轮被拒绝（`workdir_missing` / `workdir_busy`）。已知限制：账号停用的宽限期里恢复了，宽限期内已决定或已过期的审批单已经收口，结果不会回到对话里，需要所有者重新提。成员的账号停用 24 小时后自动停用，期间账号恢复就作罢；但宽限期里所有者或管理员明确要求停用的，立即生效，账号之后恢复也不撤回。平台管理员在 `GET /api/admin/assistants` 看谁开通了、在哪个运行时、走到哪一步、还有几个目录没删掉，`POST /api/admin/assistants/{bot_id}/deprovision` 停用某人的助理（对已经停用完的旧记录什么都不做，也不影响这个人当前的助理），请求体 `confirm` 必须是 JSON 的 `true`（字符串 `"true"` 或数字 1 都不行）；只有这次真的开始了一次停用，才记一条审计。开通与停用由 scheduler 单独的一条循环每 5 秒推进一步，失败原地重试。

应用需要的权限：普通机器人的应用身份权限之外，再开通 `im:chat.members:bot_access`（收到被拉进群的事件；飞书要求 `im:chat:readonly`、`im:chat`、`im:chat.members:bot_access` 之一，缺了事件不推送，助理就不会退群）和 `im:chat.members:write_only`（退群用），见 `coreman/core/feishu_apps/manifest.py` 的 `ASSISTANT_SCOPES`。在开发者后台批量导入权限时不要带 `auth:user.id:read`，后台不接受这一项，也不需要单独申请。订阅方式要在应用登记进平台、网关连上之后才能保存为长连接。事件订阅与普通机器人相同：`im.message.receive_v1`、`im.chat.member.bot.added_v1`、`im.chat.access_event.bot_p2p_chat_entered_v1`，回调 `card.action.trigger`，订阅方式选长连接。

一个飞书应用不能同时既是个人助理应用又绑定给某个普通机器人：两者会争同一条长连接。

## 个人资料授权（仅私聊）

飞书机器人使用自己的应用凭证，通过服务端 OAuth 获取当前发言者的用户授权；无需在用户电脑安装 CLI。机器人应用需在飞书开放平台开通并发布对应的用户身份权限，并允许设备授权流程。扫码创建的应用会一次申请下面全部权限；手动配置的应用按需开通，没开通的业务域不会出现对应工具。

第三档（仅读取消息）固定申请：

```text
offline_access auth:user.id:read search:message im:message:readonly
im:message.group_msg:get_as_user im:message.p2p_msg:get_as_user im:chat:read
```

第四档（不含消息）在第二档基础上再去掉「消息与群」整个业务域：不申请任何 `im:` 开头的权限和 `search:message`，也不附带第三档的消息读取权限，私聊、群聊消息、群列表与成员、群公告都读不到，也不能建群、拉人、撤回或置顶。其余业务域与第二档相同。

第一、二、四档只申请个人工具用到的权限：每个接口从应用已开通的权限里挑一个（优先细分权限，没有才用旧版大权限），再加上第三档的消息读取权限（第四档不加），不会把应用开通的其他权限一并申请——飞书单次授权能申请的权限数量有上限，超过会报 20084。个人工具用到的权限如下（第二档会去掉带 send、reply、forward 的权限和 `im:message`；`calendar:calendar.event:reply` 只是回复本人收到的日程邀请，不算发送，第二档保留）：

使用方法：

1. 本人的飞书身份须已同步到 CoreMan，机器人绑定的 Runtime 已升级（心跳上报 `feishu_personal_tools_v1`；Claude 与 Codex 均支持）。
2. **自动授权（默认）**：用到飞书能力而本人还没授权（或授权不够）时，AI 员工调用 `feishu_authorize`，平台**私信**给本人一张「一键授权」卡片（群里触发也只发私信，绝不把链接发进群；卡片只留一张有效的，30 分钟内有效）。点一次授权，原来那条消息自动续接，不用回去说「已授权」。已连接但档位不够或缺权限时发「升级授权」卡片，点击后才替换原授权；原来是「全部权限，可代发消息」的不会被降档，卡片写明目标范围。群里触发的卡片会说明操作结果群成员可见。私信发不出去（用户未与机器人建立会话或不在应用可用范围内，飞书错误码 `230013`）时，群里会提示联系机器人管理员。自动授权按需要选档：读消息、一般操作为「全部权限，不代发消息」，需要发送为「全部权限，可代发消息」。
   **手动选择范围（可选）**：想要更小的范围时，**私聊**机器人发送 `连接飞书`，或在输入框输入 `/` 选择斜杠指令 `/connect`。系统展示选择卡片，本人点击选项后才生成链接：1 全部权限含发送消息、2 全部权限但不含发送消息、3 消息只读、4 全部权限但不含消息（不读私聊和群聊消息，也不发送）。卡片绑定本人、原私聊及当次选择，旧卡片和重复点击不能重新生成链接。选择有效期 10 分钟，每次重新连接都重新选择，模型不能代选。
   第一、二、四档从应用当前已开通的用户权限里挑个人工具用到的部分，需要应用身份 `admin:app.info:readonly` 或 `application:application:self_manage` 查询应用权限；缺少时明确提示。第一档额外要求应用已开通 `im:message` 和 `im:message.send_as_user`。第三档按固定消息读取范围申请，不依赖权限查询。
   飞书可能沿用历史同意记录而直接显示成功，CoreMan 仍按本次选择及实际返回权限交集执行。缺失权限会显示在后台；不会以历史多余权限扩大本次范围。
3. 手动选择范围的流程里，返回私聊回复“已授权”；Agent 会检查授权并核对身份（自动授权不需要这一步）。之后可直接询问“查看最近的聊天”“我明天有哪些日程”“帮我约张三周五下午开会”“看看有没有未读邮件”或“查找我参加的会议纪要”，无需命令前缀。
4. 网页「我的飞书」可以查看、断开本人在各机器人上的连接。私聊也支持直接说“撤销授权”。

断开连接会尝试在飞书端撤销访问与刷新令牌，并清除 CoreMan 保存的访问凭证、刷新凭证及待授权凭证，阻止后续访问；远端撤销失败时明确显示未确认，重试不会误报成功；已经返回的私聊消息不会被删除。令牌失效与清除飞书记住的应用许可不同。若还需撤销飞书侧的应用许可，请在飞书的授权管理中移除。授权按“本人＋机器人应用”独立保存，应用凭证更换后需要重新连接。

权限边界：

- 个人工具是**叠加**的：机器人在私聊里的人设、技能、业务系统访问（按发言人签发的 Bot Token）、记忆和会话都保持不变，授权后只是额外多出一组以本人身份使用飞书（第一档还可按明确要求发消息和邮件）的工具，由 Agent 按问题决定是否使用，无需命令前缀，也没有模式切换。待授权期间可直接回复“已授权”继续完成核验。撤销后，后续私聊不再有这些工具。
- 只有本人与机器人的**私聊**会挂载这组工具；群聊、企微、机器人协作、未绑定身份或停用的用户都没有。群里读文档和写入走另一组受限工具，见下文「群聊读文档」「群聊里以提问人身份写入」。服务端每次调用都核验原始飞书事件、聊天类型、发言者、应用、租户和任务状态；管理员身份不会代替本人授权。
- 本人创建、以本人身份执行、结果只发给本人私聊的定时任务也能使用本人授权（见下文「本人定时任务」）。任务一旦配置了群、邮件、Webhook 或其他接收人，或由其他管理员“立即运行”，这一轮就不挂载个人工具。
- 工具都是逐个定义、带参数校验的固定操作，不提供任意接口代理；服务端只放行 `endpoints.py` 登记的接口，其他路径一律拒绝。每个接口分为读取、写入、发送三类：第三档只有消息读取；第二档可读取和写入（创建、修改、删除日程，整理邮件、存草稿，建任务、改文档表格，审批通过或拒绝等），不能发送；第一档另可以本人身份发消息、回复、转发和发邮件，发送需用户明确指定接收人和内容；第四档与第二档相同但不能调用任何消息与群接口（服务端按 `/im/` 路径拒绝，不依赖授权里有没有消息权限）。工具列表只包含本人档位和实际授权够得着的工具，调用时服务端再按档位和“本次选择 ∩ 实际返回”的权限核验一次。
  覆盖范围：消息与群（搜索、读取、会话历史、已读情况、群列表与成员、群公告、发送和回复文字或 Markdown、编辑已发消息、发送文件和图片、下载消息里的文件和图片、转发、撤回、表情回复、置顶、建群、拉人）、会议与妙记、日程（列表、详情、搜索、本人/同事/会议室忙闲、创建并邀请、全天和重复日程、提醒、查会议室并预订、修改、删除、回复邀请）、邮件（文件夹、列表、搜索、读取、下载附件、存草稿、发送（可带附件）、回复与回复全部（带原文引用并归入同一会话）、转发（带原附件）、标记已读或移动、删除到垃圾箱）、任务（我负责的和与我相关的、搜索、详情、创建（截止时间、提醒）、子任务、修改与完成、删除、清单、评论）、云文档（搜索、云空间文件、文件信息、移动、复制、重命名、下载文件、上传文件、新建文件夹、按 Markdown 读取文档和知识库页面、读取旧版文档、幻灯片和思维导图、新建文档、追加段落、按文本或块修改/删除/插入/整篇覆盖、共享给同事、评论）、电子表格（工作表、新增和重命名工作表、读写、追加行、新建）、多维表格（数据表、字段、新建数据表和字段、查询、增改删记录、批量修改记录）、知识库（空间、节点、子节点、新建页面）、通讯录（搜索同事、查看资料（含邮箱、部门、上级）、搜索部门、部门详情和成员）、审批（待办、已办、抄送、我发起的、详情、通过、拒绝、转交；查找审批模板、查看表单字段、发起（如请假、报销）、撤回、催办）、OKR（周期、目标、关键结果、新增和修改进展）和本人考勤结果。
  暂不支持：删除云空间文件；假期余额、考勤统计、排班和薪资（飞书只对应用身份开放）；飞书邮件里的超大附件（以链接形式存放）转发时不带上，工具会列出没带上的附件。
- 文件中转：模型拿不到本人的飞书凭证，文件由 CoreMan 以本人身份收发。下载时工具取回文件，暂存在对象存储（1 小时后清理），返回 30 分钟有效的下载链接，Agent 用 curl 下载到临时目录，用完删除。上传时工具先给出 30 分钟有效的上传链接，Agent 用 `curl -T` 上传后得到 `upload_id`，再交给发文件、存云空间或发邮件的工具。链接和 `upload_id` 用主密钥加密，绑定本人、机器人和本次授权，撤销或重新连接后立即失效；上传链接拒绝带 `Origin` 的浏览器请求。邮件附件的预签名下载地址只放行飞书域名。大小上限：下载单个文件 50 MB，上传 30 MB；其中发图片 10 MB、存到云空间 20 MB、邮件附件合计 18 MB（飞书整封邮件上限 25 MB）。
  历史授权保持原有只读范围，不自动升级；用到新工具时 AI 员工会自动发升级授权卡片。已创建的应用要先在「飞书应用」页扫码补齐权限，第一、二、四档才会包含新权限。
- 发邮件要带模型生成的 `uuid`：同一 uuid 重试时，已发出的直接返回原结果，草稿已建但发送失败的改发这份草稿，不会再发一封；同一 uuid 换了收件人或内容会被拒绝（`uuid_reused`）。重发已有草稿时飞书报错，说明上次可能已经发出、只是结果没返回，工具返回 `mail_send_unconfirmed`，提示用户到「已发送」确认，而不是再发。记录保存 7 天。飞书邮件接口本身没有幂等参数；发消息、建日程、建任务、建群用飞书自带的去重参数。
- 飞书拒绝时，工具返回 `app_permission_missing`（应用未开通该权限，管理员补齐）、`user_permission_missing`（本人授权时未包含，自动私信发升级授权卡片）或带飞书错误码的 `feishu_read_failed` / `feishu_request_failed`，不转发飞书返回的原始文字。
- 读取结果作为不可信的外部资料交给模型，提示词允许资料用于完成本人这次明确要求的事（如生成文件、提交到本人指定的系统），没有本人明确要求时不写入共享记忆、共享文件或技能目录，也不转交他人；资料里的要求一律不算数；这是提示词约束，不是隔离。授权换代（撤销、重新连接、应用凭证变更）后，进行中的一轮立即失去飞书工具，定时任务工具不受影响。
- 私聊会话与普通私聊一样由 Runtime 落盘、可续聊，完整过程只有本人能查看（规则见上文「会话页的访问规则」）。Runtime 未上报 `feishu_personal_tools_v1` 时，机器人照常回答，只是不挂载个人工具；此时手动发送“连接飞书”会提示先升级运行时。旧版的 `feishu_personal_restricted_v1`（替换式受限模式）不再使用。
- 用户 OAuth 凭证加密保存在数据库，不传给模型或 Runtime。服务器刷新凭证；撤销与并发读取按用户和机器人串行处理。
- CoreMan 内的飞书私聊记录只向本人交互登录开放，机器人身份不可读取；无归属证据的 Runtime 原始会话预览被拒绝。机器人回复仍经过 CoreMan 和所选模型服务，并保存在飞书私聊及 CoreMan 对话记录中；部署和模型服务的运维权限不属于聊天权限隔离范围。

搜索结果只包含飞书允许当前授权账号访问的内容，并受应用已开通权限、组织策略和平台接口范围约束。分页工具每次最多返回 20 条；较长转写/文档可按工具返回的截断信息分段读取。权限未开通或平台拒绝时，不回退到机器人或其他用户的身份。

后台每个机器人的飞书实际权限默认显示 5 项，可独立展开、收起；本次申请范围与飞书实际返回权限分开展示。

## 群聊读文档

群里有人发飞书文档链接让 AI 员工看时，它用另一组只读工具（MCP `coreman_feishu_docs`）读取，与上文的个人授权分开：群聊仍然不挂个人工具。目标是尽量自己读到，不让人反复发链接、点卡片。设计见 `docs/superpowers/specs/2026-11-06-feishu-group-docs.md`。

- **先用应用身份读本群看得到的文档**：先证明本群看得到，满足其一才读：本群是文档协作者；链接分享是「组织内获得链接的人可阅读/编辑」且本群不是外部群；链接分享是「互联网上获得链接的任何人可阅读/编辑」。只是「应用读得到」不算：应用还读得到共享给它所在其他群的文档、被单独添加为文档应用的文档，直接读会把别处的文档泄到本群。注意飞书的权限接口要求应用本身能访问这篇文档，「组织内可读」也不对应用生效，所以多数情况下要把文档「分享」给群（或添加本群为协作者）这一层才读得到。
- **读不到就直接以提问人本人身份读**：提问人已「连接飞书」、档位含读取这类文档时，以他的身份只读，不再弹卡片；回答里会说明是以他的身份读的。只读他在本群发过的链接：这条消息、它引用或合并转发的消息，以及本群近 24 小时里真人消息中出现过的链接；文档正文里的链接不算。读到后，提问人有分享权限时 AI 员工可以发一个「共享给本群」按钮（可选，只有他能点，30 分钟内有效）：点了就以他的身份把本群加为文档的可阅读协作者（不发通知），以后群里谁发这个链接都能直接读。
- **提问人授权还差一步时自动续接**：他还没连接飞书、授权还没完成或档位不含文档时，AI 员工调用 `feishu_authorize` 私信发授权卡片（或提示去飞书授权页点同意），平台记下这一轮（30 分钟内有效）。看护进程替他查授权结果，授权完成就自动接着处理原来那条消息，不用回私聊说「已授权」，也不用再发链接。
- 读不到时工具返回具体原因（`reason`）：`link_not_from_chat`（不是本群有人发过的链接）、`unknown_speaker`（提问人不是平台成员）、`not_connected`、`authorization_pending`、`scope_missing`、`asker_cannot_open`（他本人也打不开：AI 员工会请他用自己的飞书打开链接、点「申请权限」，所有者通过后在群里说一声即可；飞书开放平台没有让应用代为申请权限的接口）。
- 支持新版文档（docx）、知识库里的文档、电子表格和多维表格；旧版文档、思维笔记、幻灯片、文件暂不支持。工具只收链接，不收 token。旁听插话、调度回合、机器人之间求助和定时任务都不挂这组工具；未绑定身份的提问人只有应用身份这一层。
- 应用身份需要新增的权限（已包含在扫码创建清单里，已有应用在「飞书应用」页扫码补齐）：`docs:permission.member:retrieve` `docs:permission.setting:read` `docx:document:readonly` `wiki:wiki:readonly` `sheets:spreadsheet:readonly` `bitable:app:readonly`。未补齐时应用身份读不到，以提问人身份读不受影响。
- 需要数据库迁移 `0078`（`feishu_doc_consents`，保留 30 天）与 `0079`（等待授权、已续接两种状态），Runtime 上报 `feishu_group_docs_v1`（Claude、Codex、OpenCode 均支持）；旧节点上群里照常回答，只是没有这组工具。

## 群聊里以提问人身份写入

群里有人要求 AI 员工改文档、表格、多维表、日程或任务时，AI 员工可以用 MCP `coreman_feishu_docs` 里一组固定白名单的 `feishu_*` 工具，**以提问人本人的飞书身份**写入（不是机器人身份）。设计见 `docs/superpowers/specs/2026-11-09-feishu-in-flow-auth-and-group-write.md`。

- **提问人没授权就先授权**：同上文自动授权，卡片私信发给提问人，授权完成后群里这条消息自动续接；返回 `authorization_sent` / `upgrade_offered` 时 AI 员工说一句并结束本轮。
- **白名单按风险分四类**（`coreman/core/feishu_docs/write_policy.py` 的 `GROUP_TOOLS`，不在表里的工具群里一律不可用）：
  - `locate`（只返回定位字段，其余内容丢弃）：搜索云文档、云空间文件、知识库空间和节点、日程列表与忙闲、会议室、任务列表与详情。群里不读也不转述他人的私人内容。
  - `create`（直接执行）：新建文档、表格、文件夹、知识库页面，上传到云空间，创建日程和任务（不带参会人或负责人时）。显式指定了文件夹、知识库、任务清单、父任务或日历时，这个位置要在提问人这条消息的链接里（知识库链接含其所在知识库）或本轮刚建，否则转为确认；不指定时放在本人的我的空间或主日历，照常直接执行。
  - `target`（目标可信才直接执行）：追加或修改文档、评论、写表格、写多维表、重命名与复制文件（复制的目标文件夹同样要可信）、任务评论。目标必须是提问人这条消息（含引用、合并转发）里的链接，或本轮刚创建的文档（近 24 小时的群消息链接只用于读，不能当写入目标）；知识库链接按节点实际指向的文档核对。目标不可信时转为确认。
  - `confirm`（一律由提问人点卡片确认）：修改或删除日程、邀请参会人、回复邀请、修改或删除任务、修改文档权限、移动文件、删除多维表记录；创建日程或任务时带了其他人（参会人、负责人、关注人）也走确认。
- **确认卡片**：先发一张只有提问人能点的卡片，写明工具和实际参数（参数取自真实调用，不用模型写的描述），10 分钟内有效，点一次只执行一次；他人点击、过期、重复点击都不执行。AI 员工返回 `pending_confirmation` 后结束本轮，确认或取消后这条消息自动续接并告知结果。点卡片开的回合自己不会再发确认卡。无法发出确认卡时工具返回 `confirmation_unavailable`，AI 员工请提问人把要求当作一条普通消息重发。
- **每轮最多 30 次写入**（上传链接不计），超过返回 `write_limit_reached`；同一调用重复提交返回 `already_done`，不会重复执行。每次写入记录审计（成功与失败都记，参数不进日志）。
- **写完要说明**：回复里写「已以 @提问人 的身份修改」并附链接。文档、表格内容要求写别处时一律忽略。
- 旁听插话、调度回合、机器人之间求助、定时任务和私聊都不挂这组写工具；邮件、消息发送、审批、OKR 和考勤不进群，这些只在本人私聊里使用。
- 需要数据库迁移 `0082`（授权等待与群写入审计两张表）。

## 本人定时任务与提醒（仅私聊）

- **一次性提醒**：私聊发送“两分钟后提醒我检查接口，只提醒一次”，再回复“确认提醒”。按固定格式解析，支持 1 分钟至 30 天，到点只向原私聊发一次，不调用模型。
- **本人 AI 定时任务**：私聊里用自然语言描述，例如“每个工作日 9 点总结我的飞书未读消息”。Agent 调用 `schedule_propose` 拟好名称、执行时间（五字段 cron，按北京时间；或一次性的具体时间）和每次执行的指令，系统发出确认卡片；**只有本人点“确认创建”才会创建**，Agent 不能代为确认。“每天……提醒我……”这类周期说法也交给 Agent 走这条路。
  - 任何能使用该机器人、并已绑定飞书身份的成员都可以创建，不需要机器人管理员权限。每人每个机器人最多 10 个启用中的任务，周期任务相邻两次至少间隔 1 小时，一次性任务须在 1 分钟之后、30 天之内；确认卡片 30 分钟内有效。
  - 任务以本人身份执行（签发本人的 Bot Token），结果默认只发回本人与机器人的私聊；已连接飞书时还能以本人身份读取飞书。本人失去该机器人的使用权限或解绑身份后，任务自动跳过并停用。
  - 通过 `coreman-cron` 技能还能设置接收人、执行前检查和到期时间，以及修改、暂停、删除、立即运行和查看运行记录，见 [定时任务 · 成员本人任务](cron-jobs.md#成员本人任务技能)。
  - 网页「我的定时任务」列出本人的提醒和 AI 定时任务，可暂停、恢复、删除，并查看最近一次结果。
  - 机器人管理员在后台「定时任务」里能看到成员本人任务（标记“成员本人任务”），只能停用，看不到指令和结果。以本人身份运行过的执行记录（包括管理员给自己建、只发给自己的任务）同样只给执行者本人看，对话记录页也只对本人显示。

需要数据库迁移 `0037`，并把 Runtime 升级到上报 `feishu_personal_tools_v1` 的版本。

## 告警来源

旁听不处理其他机器人的消息。要让某个告警机器人的消息直接触发排查，由平台管理角色登记告警来源（`coreman bots alert-source-add`，见 [admin-cli.md](admin-cli.md)）：机器人、群、告警机器人的 `union_id`，以及一个固定的服务用户。

- 匹配只看飞书事件的 sender 字段，消息正文里写什么都不影响身份。
- 机器人需要开启旁听。旁听为 `shadow` 时只在判断记录里写 `would_intervene`；为 `on` 时不经判断模型、不受机器人连发限制，直接开一轮排查。
- 这一轮以服务用户的身份签发业务系统令牌，服务用户必须是启用状态，其他场景不会用它。
- 同一来源的同名告警（取规则名，其次卡片标题，都没有时用内容哈希）在上一轮未结束或去重窗口内（默认 600 秒）不再开新一轮，只累计次数。
- 告警内容按外部数据放进提示词，这一轮要求只读。这是提示词层面的约束，实际能做什么取决于服务用户的授权和机器人的工具，服务用户只给只读权限。
- 这一轮不下发机器人和技能的环境变量、云服务代理令牌和操作目录 MCP，写能力不靠提示词约束。服务用户的业务系统令牌照常下发，运行时节点本机的登录态也不受影响。

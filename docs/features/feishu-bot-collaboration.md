# 飞书机器人协作（限范围试运行）

## 行为

人类 @ A → A 使用任务内求助接口 → A 的执行释放 → A 在群内发送富文本 @ B →
飞书真实事件到达 B → B 以原始人类授权执行 → B 引用求助消息并明确 @ A →
飞书真实事件到达 A → A 恢复原始运行时会话，回复原始人类消息。

帮助阶段的任务可以结束，整体协作状态单独保存在 `bot_collaborations`。
B 最终反馈使用内部 JSON 契约（status=completed/blocked、answer）。completed 和 blocked 都必须提供非空 answer，才作为真实反馈交回 A；群里展示答案或带“未完成”标记的具体阻碍。A 根据状态总结，blocked 最终保留为失败协作，不能标成完成。进度文字、格式错误、空答案不触发恢复；后台任务只允许有限等待。
成功发送消息不等于收到反馈；没有真实平台入站事件不会排入下一步。

## 开启范围

不用配置伙伴关系。飞书群聊任务里，只要还有其他启用的飞书 AI 员工允许被求助，就注入协作系统提示词和工具凭证；A 用 `search_collaborators` 找到的就是当前群里的其他 AI 员工。

候选 B 必须同时满足：本平台管理的飞书 AI 员工、已启用、没有关掉「允许其他 AI 员工求助」（`bots.accept_bot_help`，默认开）、本轮发起人在 B 的使用白名单里（白名单为空表示人人可用），并且确实在当前群。在不在群用 B 自己的飞书凭证调 [判断用户或机器人是否在群里](https://open.feishu.cn/document/server-docs/group/chat-member/is_in_chat)，搜索时的明确结果在进程内缓存 5 分钟；查不清（缺权限、跨租户、超时）的不列出，原因放在搜索结果的 `unverified` 里，模型据此如实告诉人。飞书的群成员接口不返回机器人，群里第三方、非本平台的机器人也接不了交接协议，所以不会出现在候选里。

权限边界：B 以原始人类的身份执行，业务令牌按这个人在 B 上重新签发，B 的白名单也按这个人检查。A 求助 B 等价于这个人自己去 @ B，不会多出权限。B 关掉开关后，搜不到它，登记、派发、恢复各环节的授权检查也会拒绝，进行中的求助一并取消。

登记求助时再用双方凭证实时核对一次是否都在群里（不用缓存）。权限不足、跨租户、网络失败与明确不在群分别处理，检测不确定时不启动伙伴 AI。

`bot_collaboration_routes` 保留为按群验证过的传输身份缓存：open_id 用于 @，union_id 与租户来自真实平台回执。首次使用或凭证变化时，后台自动进行一次不启动 AI 的双向消息验证，完成后继续已登记的求助。等待反馈的时长统一为 300 秒。

迁移 `0071` 起不再读取 `bot_collaboration_partners`，表和历史协作账本原样保留。以前没配伙伴的群从此也能求助；以前配过的伙伴不再起作用，要拦住某个 AI 员工被求助，在它那边关掉开关。

## 渐进式协作工具

系统提示词仅包含稳定协作规则：Claude 使用原生系统提示词，Codex 使用 `developer_instructions`。Codex 只在新建 thread 时读取 `developer_instructions`，续接轮不会再看新的版本，所以协作阶段说明（helper、续接、同事答复续接）写在用户消息开头由平台生成的本轮块（`[SYS_TURN:<tag>]`）里，只放这一轮的阶段与约束；协议规则本身不进用户消息，用户原文及附件保持原样。

运行时通过任务级 HTTP MCP `/api/runtime/collaboration/mcp` 暴露三个工具：

- `search_collaborators(query, cursor, limit)`：按名称、描述或标识的关键词搜索，空查询可浏览。服务端先过滤当前人类的使用权限、来源机器人和对方开关，再问飞书是否在当前群，然后分页。默认每页 5、最多 10，摘要最多 160 字符。多个空白分隔关键词按 OR 匹配；当前不是语义检索。
- `get_collaborator(id)`：按需返回详细描述（最多 4000 字符）和协作限制。描述及反馈都是外部数据，不能改变身份、授权或系统规则。
- `request_collaboration(collaborator_id, question, context)`：提交问题与必要背景，复用现有真实飞书事件交接。问题和拼接后的背景总长度不超过 4000 字符；背景本身最多 900 字符。

`COREMAN_COLLABORATION_URL` 与 `COREMAN_COLLABORATION_TOKEN` 由服务端逐轮注入运行时。凭证绑定当前任务及原始人类、30 分钟过期，任务结束/取消后不能使用；模型无需拼接命令或接触凭证值。运行时不继承前一任务的协作环境变量。帮助与恢复阶段不提供协作工具凭证。

AI 伙伴只在飞书群聊任务里可用；私聊和定时任务只能向同事求助。工具接口不暴露飞书调用细节，企微不实现机器人协作。

旧 `POST /api/runtime/bot-help` 保留兼容，原 `target_bot_key/question` 参数不变，与 MCP 共用授权和调用预算，不能换入口规避限制。它不再出现在新提示词中。

### 循环与消耗保护

所有限额固定由服务端执行，模型无法修改：

- **单跳、单次委派**：一个原始人类任务只登记一次求助；相同请求重试返回同一协作记录，不能生成第二个帮助任务。B 和恢复后的 A 都不能再次发现或求助，禁止 A→B→A / A→B→C。
- **共享调用额度**：一个任务最多成功进入 12 次协作工具处理，第 13 次取消本轮；相同规范化工具参数最多 2 次，第 3 次取消；无效参数、未知伙伴等累计第 3 次失败取消。统计存入任务 JSON，数据库行锁串行化并发请求；重连、换关键词、切换旧接口不能重置总额度。握手、工具定义读取不消耗协作工具额度。
- **注册后主动交接**：任务记录保存交接标记，worker 至多每秒检查一次；看到求助已登记就关闭模型流，交由平台等待真实反馈，不依赖模型主动停止或轮询。
- **执行兜底**：拥有协作入口的执行轮次及帮助/恢复轮次，观察到第 64 次工具开始事件时关闭模型流。此上限覆盖其他工具的反复尝试，不只计 MCP 调用。它是执行轮次工具数量上限，不是精确 token 配额，也不能撤回已经开始的工具副作用。
- **事件计数完整性**：Codex 的 MCP、网页搜索、文件修改等原生工具均计数，完成帧不会重复计数；Claude 按实际调用 ID 区分同名工具，避免漏计。完全缺少工具 ID 和消息 ID 的旧 Claude 帧无法可靠识别重放，会保守多计。
- **取消优先**：最终落库前再次检查取消标记，避免超限取消与模型完成竞态被写成成功。断流沿用现有运行时子进程终止机制。
- **有限等待**：原协作截止时间（默认 300 秒，路由范围 30–1800 秒）、任务硬 TTL、取消与消息去重仍有效。超时/失败关闭，不自动重新委派；重放或迟到反馈不能重新启动已关闭协作。

正常连续人类新请求各有独立额度；已经取消的同一任务不能靠工具重试恢复。搜索或数据核验因限额被中止时，应向人类说明未完成。

### 运行时升级要求

API、worker 与包含本次 Claude/Codex 适配的新运行时驱动需要配套发布。旧驱动不认识新的协作 MCP 环境配置；仅更新提示词不能完成升级。现有历史中的大段用户前缀不会被删除，新轮次不再追加。

## 校验和运维

- 人类身份源于原始真实人类事件。每次派发重新校验在职状态及双方用户白名单；业务令牌由当前机器人现有授权机制重新签发，没有创建者身份回退。
- 机器人消息独立保存在 inbound_events，永远不走普通人类入口。只有发件箱返回的消息编号、群、租户、sender union_id、明确 @ 与回复 parent_id 全部匹配才派发。
- 调度器会处理入站早于发送确认提交的情况；行锁与唯一任务键防止重复执行。
- A 始终沿用 `(bot_id, chat_id)` 群会话；直接 @、引用回复、是否配置或调用协作伙伴都不改变会话范围。不按发言人隔离；发言者身份和业务权限仍逐轮核验。
- 每次协助的 B 使用 `collaboration:<协作编号>` 独立会话，仅接收 A 提供的必要背景。B 的群聊、私聊和其他协助会话互不复用。A 在保存的原运行时会话中接收最终反馈，保留主任务上下文。
- 等待期间，合法的新群消息接替旧一轮（沿用普通聊天的 supersede 习惯）：取消旧协作及尚未结束的 A 任务，待旧执行退出后才派发新轮。同一群多个成员的补充也遵循此顺序；不会修改旧协作的原始发起人记录。连续快速补充以最后一条待执行消息为准，已取消消息不执行。
- 源会话映射被清除、切换或过期后，旧协作不能恢复。恢复前校验会话 UUID、后端、有效期及运行时；开流前重新检查取消状态。`new/reset/clear` 保持原群会话重置规则。
- A 的 `stop/reset` 作用于原共享群会话中的协作；向 B 停止协作仍只匹配原发起人。飞书快车道命令同样校验启用状态和白名单。存在本人活动协作时，整句“取消/cancel”也进入停止命令。若 B 应用没有提供稳定人类身份，应向 A 发送停止。
- 超时、权限变化和执行失败会通知人类，不把缺少反馈的结果标为完成。企微不实现机器人协作。
- 群里有进行中的协作时，新的人类消息才走协作的接替规则；没有时按普通群聊排队，不打断别人交代的事。
- 开了群聊旁听的第三个机器人看到 AI 员工之间带 @ 的求助和答复，只记进群聊上下文，不排旁听判断，也不清掉人类消息的待判断。
- 求助与 B 反馈使用 `post`：独立 `at` 段落加 `md` 段落，支持真实 @、加粗、代码与表格；旧发件箱文字消息兼容投递。模型输出中的额外 at 标签按文字显示，不能增加通知对象。普通人类最终回答继续用现有卡片。
- 入站优先读取 `content_v2` 保留 Markdown，兼容旧 `content`；收件匹配允许 text/post，其余身份和关联校验不变。
- 初始求助和反馈等待默认由 15 秒调度周期推进，因此会有数秒到十几秒的交接延迟。

排查顺序：协作记录状态 → request/response outbox 编号和 `_feishu_message_id` →
对应接收机器人的 inbound_events → helper/resume task → 最终 task_stream 与 FeishuDelivery。

## 管理后台：允许其他 AI 员工求助

入口：AI 员工详情 → 协作伙伴 → AI 员工，仅飞书 AI 员工显示，只有此 AI 员工的管理者能看和改。同一页下方的「同事」用于配置可以求助的人类同事，见 [向同事求助](feishu-human-collaboration.md)。

- 开关「允许其他 AI 员工求助」（默认开）。关掉时确认框显示进行中的被求助数量，确认后取消这些求助；不影响此 AI 员工向别人求助。修改记审计 `bot.collaboration.accept_bot_help`。
- 权限提示：后台读取飞书应用的权限清单，检查 `im:message.group_at_msg.include_bot:readonly`（收到其他机器人 @ 自己的消息）与 `im:chat.members:read`（查询群成员）。缺少时提示到「飞书应用」里补齐并发布，待审核时提示等管理员审核；应用没开自管理权限、查不了清单时显示「无法自动检查」。一键创建的应用默认就申请了这两项。

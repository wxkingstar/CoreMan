# 业务系统 MCP 交付

有的业务系统只提供一个 MCP 服务，并且要按调用人鉴权。把它登记成令牌下发方式为「MCP 服务」（`token_delivery = mcp`）的业务系统后，AI 员工被授权这个系统，每轮就会以当前发言者的身份挂上这个 MCP，不需要扫码授权，也不会共用某一个人的身份。

## 什么时候用业务系统，什么时候用技能

| | MCP 技能 | MCP 业务系统 |
|---|---|---|
| 身份 | 员工共用一个身份，或不需要身份（可以加 OAuth 授权，令牌存在节点 CLI 里） | 每轮按发言者签发令牌 |
| 配置位置 | 安装时写进工作目录的 `.mcp.json`，一直生效 | 每轮由驱动挂载，没有令牌就不挂 |
| 授权入口 | AI 员工的「技能」 | AI 员工的「系统权限」 |

需要按人鉴权的 MCP 走业务系统，不需要的走技能。

## 登记系统

管理台「业务系统」新建或编辑：

- **令牌交付方式**：选「MCP 服务」。
- **MCP 地址**：HTTPS 地址，不带凭证和片段。MCP 系统不使用 OpenAPI 操作目录，表单会隐藏这一项。
- **令牌签发方**、**令牌受众**：与其他系统相同。`builtin` 用平台 ES256 签名；受众留空时用系统标识。
- **配套技能**（可选）：见下文。

命令行：

```bash
coreman systems create lookup --name Lookup --delivery mcp --mcp-url https://mcp.example.com/mcp --audience mcp --companion-skill <技能 id>
```

需要数据库迁移 `0068`，运行时节点也要升级（驱动声明 `system_mcp_v1`）。滚动升级期间旧 worker 会把 MCP 系统当成普通系统处理，所以要等 API、worker 和节点全部升级后再把系统切到 MCP 服务。

## 每轮怎么挂载

1. 平台按 AI 员工被授权的系统，为当前发言者签发令牌。令牌与其他系统一样放在 `BOT_TOKEN_<KEY>`，签发记录写进 `business_token_issues`。
2. 本轮要挂的系统写进 `COREMAN_SYSTEM_MCPS`（`[{"key": ..., "url": ...}]`）。它和 `BOT_TOKEN_*` 都是保留变量，AI 员工自己的环境变量设不了。
3. 驱动把每个系统挂成 `system_<key>`，令牌作为 `Authorization: Bearer` 发送：Claude 用 `--mcp-config` 并在请求头里写 `${BOT_TOKEN_<KEY>}`，Codex 用 `bearer_token_env_var`。令牌不出现在命令行参数里，驱动诊断日志会把 `BOT_TOKEN_*` 的值打码。

不挂载的情况：

- 本轮签发失败：驱动显式禁用这个服务（Claude 加进 `--disallowedTools`，Codex 设 `enabled=false`），本轮块说明原因。
- 发言者身份未验证或账号不可用：不签发任何系统令牌，也不挂载。
- 运行时节点没有 `system_mcp_v1`：这类系统不签发，提示词写明当前运行环境不支持。

提示词里的一行写成「MCP 服务 `system_<key>`（用它的工具调用……）」。`$COREMAN_SYSTEMS` 里这类系统只给出 `mcp_server`，不写令牌变量名，模型应当用 MCP 工具，不要拿令牌自己去调。和其他持令牌的方式一样，令牌仍在运行环境里，模型的 Shell 能读到，范围是本人、本轮。

## 配套技能

实测 Codex 不会把 MCP 服务自带的说明（`instructions`）交给模型，Claude Code 会。所以 MCP 系统的用法、业务规则最好写成一个技能，设为这个系统的配套技能：

- 在「系统权限」里给 AI 员工勾选这个系统并保存时，平台自动排队安装配套技能（员工已安装、正在安装或待审的不动）。
- 取消勾选并保存时，只卸载因授权而装上的那份（`bot_skills.installed_by_system`）。员工手动安装过的，或者另一个仍被授权的系统也把它当配套技能的，都保留。
- 员工的技能列表里，这类技能标「随系统 X 安装」；手动重新安装后就归员工自己管，撤销授权不再连带卸载。
- 配套技能必须是已启用、免审批、没有必填参数的技能。「默认开放」的系统没有授权动作，不能设置配套技能。
- 授权的审计记录里写明这次自动安装、卸载了哪些技能。删除系统时，随它装上的技能保留，改按手动安装处理。

## 下游 MCP 服务要做的

用 `builtin` 签发时：

- 从 CoreMan 的 `/api/.well-known/jwks.json` 拉公钥（按 `kid` 选择，遇到未知 `kid` 重新拉取），只接受 ES256。
- 校验 `iss`，用 `scope` 判断令牌是不是给本系统的。部署配置了外部签发方密钥（`BOT_JWT_*`）时，令牌不带 `aud`，`iss` 取那把密钥的签发者。
- `sub` 是发言者邮箱前缀，按它映射到本系统的用户，并在每次调用时检查账号状态和权限：签发时没有经过下游的身份服务。
- `jti` 用于把下游的审计记录和 CoreMan 的签发记录对上。

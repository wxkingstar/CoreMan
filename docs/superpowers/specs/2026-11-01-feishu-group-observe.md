# 飞书群聊旁听：不 @ 也能在该说话时说话

状态：已实现，待测试飞书应用实测（V3、V4）
日期：2026-11-01

## 1. 背景

飞书机器人在群里只处理 @ 它的消息：网关在 `gateway_feishu/inbound.py` 的 `_normalize_event` 里，把没有 @ 机器人的群消息在落库前丢弃。要让 AI 员工像人一样在群里工作，它得能看到整段群聊，并在需要它的时候主动开口。

飞书支持这件事：

- 应用开通「获取群组中用户和机器人发送的消息」`im:message.group_msg.include_bot:read` 后，`im.message.receive_v1` 会推送群里所有用户和其他机器人的消息（不含机器人自己发的）。只要用户消息的话用 `im:message.group_msg`。两者都是需要企业管理员审核的高级权限。
- 「获取会话历史消息」`GET /open-apis/im/v1/messages`（`container_id_type=chat`）可以补拉历史，频率上限 50 次/秒、1000 次/分钟。机器人必须在群里；群关闭「新成员可查看历史消息」时，入群前的消息拉不到。

难点不在接口，而在**何时开口**和**成本**。用户的要求很明确：

- 宁可漏答，绝不乱接话、说个没完。漏答有补救办法，同事 @ 它就会照常回答。
- 话少，真能解决问题：该同步信息时同步，不该说时安静看着。

## 2. 目标与非目标

目标：

- 按机器人开关，默认关闭。没开的机器人行为完全不变，也不申请新权限。
- 打开后：@ 它一定回答（同现在）；没 @ 时，由判断模型结合上下文决定要不要插话，判断为要才启动完整 agent。
- 允许其他机器人的消息触发插话（例如其他 AI 员工在群里求助），同时在代码里保证机器人之间不会无限接话。
- 先只记录、不发言（试运行），确认没有乱接话后再真正发言。
- 判断模型可替换，第一版接 OpenAI Decisions API。

非目标：

- 企业微信。企业微信没有等价的群消息推送。
- 按群逐个开关。第一版只按机器人开关，群里可以用「安静」命令让它静音。
- 跨会话的知识（例如它在别的群做完的事）用于判断。第一版判断只看本群上下文和它在本群说过的话。
- 主动发起话题（没有人说话时定时汇报之类）。这是定时任务的职责。

## 3. 判断模型选型（实测结论）

同一套 65 段中文群聊样本（应介入 19 段，不应介入 46 段，其中 25 段专门诱导接话），两家各跑 4 轮：

| 方案 | 误插话 | 漏答（应介入共 76 次） | 延迟 p50 / p95 | 每次成本 |
|---|---|---|---|---|
| OpenAI Decisions（`gpt-6-luna`），阈值 0.3 | 0 | 8 | 约 620 / 870 ms | 约 $0.00013 |
| OpenAI Decisions，阈值 0.5 | 0 | 16 | 同上 | 同上 |
| Jev 1.14，阈值 0.5 | 10 | 4 | 约 520 / 700 ms | 约 $0.00004 |
| Jev 1.14，阈值 0.7 | 0 | 12 | 同上 | 同上 |

- OpenAI 在不该介入的样本上最高只给 0.08，4 轮结果完全一致，阈值 0.3 时余量很大。Jev 对「感觉最近数据都怪怪的」「我在查，数据库有点慢」这类话给出 0.5～0.65，正是要避免的乱接话。
- 只问一个整体问题，比拆成「是否职责内 / 是否已被回答 / 是否点名别人」再在代码里组合，结果更好。
- 结论：第一版用 OpenAI Decisions，阈值 0.3。判断层做成接口，Jev 等以后版本更新再用同一套样本复测。
- 两家都是境外服务，Jev 还有地区限制（部分地区返回 451）。

样本只有 65 段，全部由人编写和标注。上线前必须先试运行（见 §4.7）。

## 4. 设计

### 4.1 开关与配置

`bots` 表加两列（迁移 0069）：

| 列 | 类型 | 说明 |
|---|---|---|
| `group_observe` | Text，CHECK `off / shadow / on`，默认 `off` | `shadow` 只判断、记录，不发言；`on` 真正插话 |
| `group_observe_scope` | Text，默认 `''` | 旁听职责说明：它负责什么、什么情况该说话、什么情况不该。切到 `shadow` / `on` 时必填 |

判断时把 `group_observe_scope` 作为机器人职责交给判断模型，不用整段系统提示。系统提示太长，里面全是与判断无关的内容；实测职责写得越具体，误判越少。

全局参数放 `settings_schema.SETTING_DEFAULTS`，管理台可改：

| 设置 | 默认 | 说明 |
|---|---|---|
| `group_observe_threshold` | 0.3 | 判断概率高于它才介入 |
| `group_observe_quiet_seconds` | 8 | 群里安静这么久才判断（防抖） |
| `group_observe_max_wait_seconds` | 60 | 一直有人说话时，最长等这么久也要判断一次 |
| `group_observe_bot_streak_limit` | 6 | 熔断：最近一条人类消息之后，群里机器人消息（含所有机器人）连续达到这么多条，就停止主动插话，直到有人说话（§4.5） |

判断与插话带的最近群消息（20 条、30 分钟内）和「安静」的静音时长（2 小时）是代码里的常量（`core/chat/group_observe.py`），不做成设置。

判断服务的凭据走环境变量（`config.Settings`）：`DECISION_PROVIDER`（默认 `openai`）、`DECISION_MODEL`（默认 `gpt-6-luna`）、`OPENAI_API_KEY`。没配凭据时，管理台不允许把开关切到 `shadow` / `on`。这些是平台进程自己的变量；机器人环境变量对 `OPENAI_*` 的屏蔽（`bots/env_policy.py`）不受影响。

### 4.2 权限

- `manifest.py` 新增 `OBSERVE_SCOPES = ("im:message.group_msg.include_bot:read",)`，**不并入** `TENANT_SCOPES`。只有开关不是 `off` 的机器人，`missing_scopes` 才把它算进缺失项。
- 管理台打开开关时，提示需要「补齐权限」并由企业管理员审核，沿用现有的重新扫码流程（`feishu_app_registrations` purpose=update，再 `scopes/apply`）。权限未生效前开关也能保存，缺失的权限显示在「飞书应用」页签里。
- 打开开关的确认框写明：群里所有消息（包括其他机器人的）会经过 CoreMan，最近的群消息会发给境外的判断服务和机器人所用的模型服务。
- `docs/feishu.md`「引用消息」一节里「网关照旧只处理 @ 机器人的消息」的说法相应更新。

### 4.3 网关：放行，但不当成对话

`_normalize_event` 里，群消息没 @ 时：

- 开关为 `off`：照旧丢弃。
- 否则：照常解析，`mentions_bot=False`，落库到 `inbound_events`。按 `(bot_id, platform_msg_id)` 去重，与现有逻辑相同。
- 网关子进程需要知道开关值，并在开关变化后生效。实现时沿用子进程获取机器人配置的现有方式。

`enqueue_inbound` / `_enqueue_task` 里，`mentions_bot=False` 的群消息**不建 chat 任务**，只更新旁听状态（§4.4）。这一点很关键：群聊的会话键就是 `chat_id`，如果每条旁听消息都建 chat 任务，`tasks.supersede` 会把这个群里正在进行的回复取消掉。

收到旁听消息时，网关不加「收到」表情回复，也不做其他任何可见动作。

@ 消息的路径不变。@ 到达时同时清掉该群的待判断状态，避免 @ 回答之后又主动补一句。

### 4.4 防抖与判断任务

新表 `group_observe_states`（主键 `bot_id, chat_id`）：`pending_since`、`last_message_at`、`last_event_id`、`bot_streak`（最近一条人类消息之后的机器人消息数，人说话时清零）、`muted_until`、`last_interjected_at`。

不加调度器循环，防抖靠延后的任务：

- 每来一条群消息都记账（upsert）：人说话把 `bot_streak` 清零，机器人消息加一；没 @ 的消息设 `pending_since`（已有就保留）、`last_event_id`、`last_message_at`，并排一个 `kind="group_observe"` 任务（快速通道，`run_after=now+8s`，`dedupe_key=observe:{event_id}`，会话键 `observe:{chat_id}`，不和群聊对话共用，免得被对话的替代取消）。@ 它的消息清掉 `pending_since`。
- 判断任务到点后锁住状态行：不是最新那条且还没等满 `max_wait` → 退出；是最新那条但群里还没安静够 → 按剩余时间放回队列；否则由它判断这一批，清掉 `pending_since`，之后来的消息重新开始攒。

### 4.5 什么时候说话由模型决定，代码只管不重叠、不失控

说多说少不设硬性限制：没有冷却时间，也没有每天的次数上限。像人一样，该说就说，不该说就不说，全由判断模型决定。模型能看到它自己最近在群里说过的话（`sender_kind=self`），刚说过、别人还没接话、没有新情况的时候，判断指令要求它不再开口（附录 A）。

代码只保留下面几条，它们不限制正常对话的频率：

1. **不重叠**：该群的会话里有进行中的回复（@ 触发的或上一次插话的），就先不判断，等回复结束后的下一轮。人也不会自己还没说完就再插一句。
2. **尊重静音**：`muted_until > now`（§4.9）。
3. **防失控熔断**：最近一条人类消息之后，群里机器人消息（所有机器人，包括外部机器人）已经连续 `bot_streak_limit` 条（默认 6），就停止主动插话，直到有人说话。这一条防的是模型误判导致机器人之间无限接话。正常的机器人协作（一方求助、一方回答、再追问一次）远到不了 6 条；一旦触发，会在判断记录里标出来，方便事后复核。
4. 待判断的消息里，最后一条是本机器人自己发的（飞书不推送这种消息，这里只是防御）。

其他机器人发的消息可以触发判断，机器人之间可以正常一问一答（样本 #121：其他机器人追问它给的数据，判对）。现有的单跳协作（`bot_collaboration.py`：协作任务带 `collaboration_id` 就不能再发起求助）保持不变，与这里互不影响。

判断后：概率 ≤ 阈值，或模型返回拒答、请求失败、超时（3 秒），一律不说话。

### 4.6 判断请求

判断输入是一个 JSON：

```json
{
  "bot": {"name": "...", "role": "<group_observe_scope>"},
  "recent_messages": [
    {"sender": "张伟", "sender_kind": "human | bot | self", "text": "..."}
  ]
}
```

- 消息来自 `inbound_events`（包括已 @ 的和旁听的）与 `feishu_sent_messages`（本机器人自己说的，标 `self`）合并，按时间排序，取最近 `context_messages` 条且在 30 分钟内的。
- 发送者用通讯录名字，认不出的叫「用户 N」。内容解析复用 `feishu_content`；图片、文件只写占位。
- 时间不放进输入：「多久没人回」这类判断由代码算（§4.5）。

只问一个 `predicate`（指令全文见附录 A）：它现在是否应该主动发言，回应最近的话题。把「是」限定为职责内、尚未被回答或认领、不是点名问别人、没人让它别说话，或者它知道一个大家需要知道却不知道的信息。

判断层接口：

```python
class Decider(Protocol):
    async def should_interject(self, state: dict) -> Decision: ...
# Decision(probability: float | None, refused: bool, model: str, latency_ms: int, input_tokens: int)
```

第一版只实现 `OpenAIDecider`（`POST /v1/decisions`）。

### 4.7 记录与试运行

新表 `group_observe_decisions`：机器人、群、触发的最后一条事件、`mode`、跳过原因或概率、是否会插话、是否真的插话、模型、延迟、token 数、判断输入（保留 30 天，与入站事件同一个清理任务）。

- `shadow` 模式：只写这张表，不发言。
- 管理台机器人详情加「群聊旁听」页签：按群列出最近的判断，「会插话」的那些可以展开看当时的上下文。管理员对每条标「该说 / 不该说」，标注用来复核阈值。
- 推荐流程：开 `shadow` 跑一周 → 看「会插话」的记录里有没有乱接话 → 再切 `on`。

### 4.8 插话回合

判断为插话时，建一个普通 chat 任务：

- 会话键是 `chat_id`，回复目标是触发话题的最后一条消息（`reply_to`），`payload.origin="observe"`。
- **本回合的上下文**：`build_turn_context` 带上最近群消息（同 §4.6 的合并结果）。打开旁听后，@ 触发的回合也带这段上下文；以前的 @ 回合看不到群里之前的讨论，这是额外收益。
- **本回合的规则**（追加到系统提示的本回合部分）：「你是主动加入群聊，不是被点名。只说结论或关键信息，一两句话，不寒暄、不复述别人的话、不追问无关细节。需要展开就等同事追问或 @ 你。如果看完上下文发现其实不需要你说话，只输出 `<NO_REPLY>`。」
- **发送方式**：插话回合不推流式卡片，否则会先出现「思考中」，结果又不说话。终稿出来后再发一条消息；终稿是 `<NO_REPLY>` 就什么也不发，记为「agent 否决」。
- 发出去之后 `bot_streak` 加一（飞书不会把它自己的消息推回来），并更新 `last_interjected_at`（仅用于展示，不参与判断）；判断记录改为 `sent`，agent 改主意记 `vetoed`，失败记 `failed`。

### 4.9 安静命令

在 `commands.py` 里新增群聊命令，@ 机器人发「安静 / 别说话 / 闭嘴」就设置 `muted_until`，回一句「好的，接下来 2 小时我只在被 @ 时说话」；@ 机器人发「可以说话了」就解除。不 @ 时说的「小数先别说话」由判断模型处理（样本里判对了），不当成命令。

## 5. 成本与容量

- 防抖之后，按每个活跃群每天约 200 次判断估算，大约 $0.03/群/天。§4.5 的规则会先挡掉一大部分。
- 判断在平台侧调用，不占 Runtime 节点；只有真正插话才跑一次完整 agent 回合。插话次数没有硬上限，取决于群里有多少需要它的事；试运行期间按群统计「会插话」的次数，用来估算 agent 回合的用量。
- `inbound_events` 的写入量会随群活跃度上涨。保留期不变，需要关注表大小和清理任务的耗时。

## 6. 验证

- V1：自动测试覆盖网关放行和丢弃、旁听消息不建 chat 任务、不取消进行中的回复、防抖调度、§4.5 每条规则（含熔断计数在人说话时清零）、`<NO_REPLY>` 不发送、安静命令。判断服务一律打桩。
- V2：离线评测。把 §3 的样本作为评测集，放在 `scripts/` 下，只在手动运行时调用真实接口，不进 CI。改指令或换模型前后都跑一遍。附录 A 新增了「不重复自己」一句，并补充「刚说过、没人接话」「机器人之间一问一答」两类样本，第一次实现时先复测。
- V3：测试飞书应用开通权限，在测试群里用 `shadow` 跑真实对话，核对记录。
- V4：同一测试群切到 `on`，验证两个机器人同时开启时能正常一问一答，但不会无限接话（§4.5 第 3 条的熔断会在需要时生效）。

## 7. 上线顺序

1. 迁移 0069 与代码发布。所有机器人默认 `off`，行为不变。
2. 配置 `OPENAI_API_KEY` 等环境变量。
3. 选一个机器人：写好职责说明 → 补齐权限、管理员审核 → `shadow` 一周 → 复核 → `on`。

回滚：把开关切回 `off`，网关立即恢复丢弃；表和列可以保留。

## 附录 A：判断指令

实测版本如下，末尾加粗的一句是去掉冷却和次数上限后新增的，待复测（§6 V2）。

> 群聊里有一位 AI 同事 `bot.name`，职责见 `bot.role`。判断：它现在是否应该主动发一条消息，回应 `recent_messages` 最后一条消息所在的话题？应该（是）：最近的消息里有人（包括其他机器人）提出了属于它职责范围的问题、请求或数据疑问，或在追问它自己之前的回答；或者它掌握与当前讨论直接相关、大家还不知道且需要知道的信息（例如有人正在用已被纠正的数据）；并且还没有同事回答、认领或同步过，也不是点名问其他具体的人，也没有人要求它别说话。不应该（否）：闲聊、表情、确认致谢、通知公告、领域外的事、已被回答或有人认领、只是在谈论它而不是在找它、或是对它自己消息的致谢。**如果 `recent_messages` 里它（`sender_kind` 为 `self`）最近已经就这个话题说过，之后没有人回应或提出新的情况，也算否：不要重复自己。**

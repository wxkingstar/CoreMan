# 平台代理批量上限与限速按系统设置

承接 [平台代理批量写操作](2026-11-16-proxy-batch-writes.md)。

实现状态：已实现（迁移 `0114`），现行行为见 `docs/business-system-catalog.md`「批量写操作」。本机实测：5 万项（文件 5.5 MB）提交耗时约 2.2 秒，生成确认卡约 0.8 秒；已处理 49000 项时取下一项走部分索引，约 2 毫秒。5 万项、文件 26.9 MB（每行约 560 字节）时：提交约 3 秒，进程内存峰值增加约 135 MB（Python 分配峰值约 240 MB）；生成确认卡（整批解密并写 CSV）约 1.2 秒，内存峰值再增加约 270 MB（Python 分配峰值约 380 MB）。收尾生成结果 CSV 与生成确认卡是同一量级。

## 背景

批量写操作的上限写死在代码里：`write` 每批 1000 项、`destructive` 每批 50 项，单轮代理调用 3000 次。一次要改几万条（例如 5 万个商品）时只能拆成几十批，每批都要用户另发一条消息、确认一次、试跑核对一次。不同业务系统能承受的写入量和速度也不一样，平台没有办法按系统限速。

直接把常量调大撑不到 5 万项，下面几处会先出问题：

1. **批量文件不超过 5 MB。** 5 万项时每行平均只有 100 字节。
2. **提交在一次工具调用里完成。** 逐个对象插入 5 万行，可能超过运行时 MCP 工具调用的超时（Codex 默认约 60 秒）。
3. **每执行一项都按主键从头扫，找下一个待执行项。** 已处理的行越多，扫得越久，累计扫描量是平方级。
4. **进度卡每 20 项更新一次。** 5 万项要更新约 2500 次飞书卡片；单纯把每段加大到 500 项，小批量又会整批跑完都看不到进度。
5. **单轮代理调用计数时，每次都把参数指纹写进任务载荷。** 载荷随调用次数增长，而这份指纹在代理调用上从来不用。

## 目标

- 在「对接系统」里按系统设置四项：`write` 每批上限、`destructive` 每批上限、单轮代理调用上限、每项执行前的间隔。
- 每项都有平台规定的硬上限，管理员只能在硬上限内调整。
- 5 万项一批时：提交在工具调用超时内完成，执行速度不随进度下降，进度卡更新次数与执行时长成正比，与项数无关。
- **不执行错、不执行串**：每一项只按它暂存时的内容发出，最多发出一次；同一批严格按行号串行，同一时刻最多一项在途；批次之间互不混入。

## 非目标

- 不改变试跑：超过 10 项时仍先执行前 5 项，暂停等提问人核对。
- 不改变每轮最多提交一批、只能在提问人本人发消息的回合提交。
- 不做并发执行。限速按批次计算，同一系统同时跑的两批各自限速。
- 单项写操作（逐次提交、一张卡最多 50 个）不变。

## 设置项

| 字段（`systems` 表） | 含义 | 默认 | 范围 |
|---|---|---|---|
| `batch_write_max` | `write` 每批最多项数 | 1000 | 1～50000 |
| `batch_destructive_max` | `destructive` 每批最多项数 | 50 | 1～500 |
| `proxy_calls_per_turn` | 单轮对这个系统的代理调用次数上限 | 3000 | 1～20000 |
| `batch_interval_ms` | 批量执行时每项发出前的间隔，单位毫秒 | 0 | 0～60000 |

- 范围由数据库检查约束和 API 校验共同保证。
- 只对代理模式（`token_delivery=proxy`）生效；其他模式下这几项照存但不起作用。
- 改动立即对新提交的批次和新的调用生效。已确认的批次在每段开始时读取最新的间隔；项数上限只在提交时检查。

## 改动

### 提交（`batch.submit`）

- 项数上限按系统读取。超过上限时整批拒绝，提示里写明这个系统的上限。
- 批量文件上限从 5 MB 放宽到 30 MB，与上传上限一致。
- 暂存改为分批的批量插入（`insert ... values`，每千行一次），不再逐个对象 `session.add`。
- 每一项的密文仍按「批次 id + 行号」绑定（AAD）。换行、换批的密文都解不开，从根上保证不执行串。

### 执行（`batch.run_chunk` 与执行任务）

- 新增部分索引 `system_batch_items (batch_id, seq) WHERE status = 'pending'`。取下一项直接走索引，不再扫已处理的行。
- 每段最多 500 项或 60 秒（原来是 20 项）。分段只负责定期换一个新任务，进度卡在段内按节奏刷新：距上次刷新满 10 秒，并且进度又推进了 1%（至少 1 项）或者已过 60 秒。小批量约 10 秒一次，大批量约一分钟一次，总次数不超过约 100 次加上执行分钟数。
- 每发完一项，如果还有待执行项，就先等 `batch_interval_ms` 再发下一项。最后一项之后不等，第一项也不等。
- 段内剩余时间不够等一个间隔时，结束这一段；下一段以 `run_after = 现在 + 间隔` 入队，不占着 worker 空等。
- 下面这些机制不变：`sending` 标记、120 秒宽限、按段号认当前执行者、`skip_locked`、连续失败暂停、试跑暂停。它们保证每一项最多发出一次、同一批不会两段同时发。

### 单轮代理调用计数（`tools.charge`）

- `systems_call` 按系统分开计数，存在 `proxy_calls_by_system`；上限读该系统的 `proxy_calls_per_turn`。
- 未知系统按默认 3000 计。
- 旧的 `proxy_calls` 字段不再写，旧轮次里留下的值不影响新计数。
- `systems_call` 不再写入指纹表。目录类调用（browse/search/describe）仍记指纹，防止原地打转。

### 提示与说明

- 运行时提示词、`systems_describe` 的批量说明、调用规则里写死的「1000 / 50」，改为按系统的实际上限显示。
- `docs/business-system-catalog.md` 的「批量写操作」一节同步更新。

### 管理台、CLI、API

- 对接系统的编辑页新增「代理调用与批量」一组，四个数字输入框，标明范围和单位。
- `coreman systems` 的 CLI 新增对应参数。
- 管理 API 的创建、更新、读取都带上这四个字段。

## 迁移 0114

- `systems` 表新增四列，带服务端默认值和检查约束。
- `system_batch_items` 新增部分索引，用 `CREATE INDEX CONCURRENTLY` 建，不锁表。
- 迁移只增不删；旧进程不读新列，滚动升级期间无影响。

## 测试

- **设置项：** 默认值、上下限（API 与约束）、CLI 参数。
- **提交：** 按系统上限拒绝超限批次；30 MB 以内的文件能提交；5 万行提交的耗时（本机库实测，记在 PR 里）。
- **执行：** 间隔生效，只在两项之间等；间隔超过段内剩余时间时以 `run_after` 延后入队；进度卡在段内按时间与 1% 进度刷新，几秒内跑完的小批量不在中途刷新。
- **计数：** 按系统分开计；`systems_call` 不写指纹；目录调用仍记指纹。
- **不执行错、不执行串：** 换行号或换批次的密文解不开；同一批两段同时运行时同一项不会发两次（沿用现有用例）。

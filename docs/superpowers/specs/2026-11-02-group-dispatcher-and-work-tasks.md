# 群聊调度员与任务跟进

状态：已确认（2026-11-02）。第一期已上线；第二期先做了最小版（分派、内部交接、完成回报，见 §10）。

## 1. 背景

群聊旁听（[2026-11-01-feishu-group-observe.md](2026-11-01-feishu-group-observe.md)）让每个 AI 员工各自旁听、各自判断要不要接话。同一条消息只让概率最高的那个开口、插话只答不做之后，群里已经不太会乱，但结构上还有短板：

- **没有全局视角。** 每个员工只拿自己的职责说明判断。一件事分几条消息说，可能被两个员工各接一半；职责重叠时靠概率比大小，不是在比谁更合适。
- **看不出这件事归谁、做到哪了。** 群里只有零散的回复，没有统一的地方记录谁接了、进展如何、结果是什么。
- **做过的事留不下来。** 一件事的背景、结论和决定散在群聊和各员工的会话里，后续相关的事要从头再问一遍。
- **成本随员工数量增长。** 一个群里有 N 个员工旁听，每条消息就要判断 N 次。

## 2. 目标

- 一个群只有一个调度员在旁听。它只负责调度：判断这条消息是不是在找人办事；是的话，理解需求、必要时拆开，交给最合适的 AI 员工。它自己不干活。
- 群里只发一行像人说的话，例如「@数据助手 看下上周退货率（T-128）」。长篇的背景和要求不进群。
- 每件事都有任务编号。CoreMan 里有任务页：给人看的部分打开就能看到；给 Agent 看的细节逐项展开。
- 任务同时是团队的共享记忆。做完的事留下记要，后续相关任务自动带上，也可以用编号引用。

不在本期：企业微信（第一期只做飞书）、跨群的任务、定时触发的任务。

## 3. 整体流程

```
群消息（没有 @ 任何 AI 员工）
  │
  ├─ 第一段：判断模型（每批消息一次，<1 秒）
  │    「最后一条消息是不是在请人办一件事，而且还没有人接？」
  │    否 → 结束（绝大多数消息停在这里）
  │
  └─ 是 → 第二段：调度 Agent（只挂调度工具）
         读群聊记录、团队员工名录、相关的历史任务
         决定：建任务（可拆成几个）/ 追加到已有任务 / 先问一句澄清 / 不处理
           │
           ├─ 群里：一行简述 + @ 执行员工 + 任务编号（回复原消息）
           └─ 内部：任务直接交给执行员工（不依赖飞书推送这条 @）
                 │
                 执行员工以发起人的身份干活，进展写进任务（不刷群）
                 需要动手确认 → 回复原消息 @ 发起人「T-128 需要你确认：…」
                 完成 → 回复原消息「T-128 完成：一句话结果」+ 任务链接
                       并写下任务记要（进入共享记忆）
```

有人直接 @ 某个员工时不经过调度员，和现在一样。这件事要不要记成任务，见 §9 的待定问题。

## 4. 调度员

### 4.1 为什么分两段

| 方案 | 问题 |
|---|---|
| 只用判断模型 | 快、便宜、稳定，但只能做「是/否」和「多选一」。拆需求、写简述、找相关的历史任务都做不了，碰到「上周那个报表再加个渠道维度」这种依赖背景的话会判断失误。 |
| 只用 Agent | 能力够，但每批消息都要跑一轮大模型，十几秒、成本高。而且 Agent 看到什么都想帮着做，容易越界干活。 |
| **两段（采用）** | 判断模型拦住绝大多数闲聊和讨论；只有真像是在找人办事时，才启动调度 Agent。调度 Agent 跑得少，可以给它足够的背景、用聪明的模型。 |

### 4.2 第一段：要不要调度

沿用旁听的判断服务（OpenAI Decisions）。问题换成：「最后一条消息是不是在请人办一件具体的事（查、改、做、排查），而且还没有人回答、认领，也不是点名问某个具体的人？」输入是最近的群聊记录和团队的一句话简介，不包括每个员工的职责（选谁是第二段的事）。

阈值和防抖沿用旁听设置：安静 15 秒、最长等待 60 秒、静音命令、机器人连发熔断。每次判断照样记进 `group_observe_decisions`，供复核。

### 4.3 第二段：调度 Agent

调度员是一个普通的 AI 员工，在机器人设置里把旁听模式设为「调度」。它在运行时节点上跑，用自己的会话和系统提示词。管理员可以在系统提示词里写团队背景和分工习惯，它也有自己的记忆。

**只挂调度工具。** 不挂业务系统、技能、求助同事、个人工具、定时任务，所以它想干活也干不了。调度工具走任务级 MCP，凭证按轮签发，做法和协作工具一样：

| 工具 | 作用 |
|---|---|
| `list_employees(query)` | 当前群里可接任务的 AI 员工：名称、职责简介（取旁听职责说明或描述）、当前排队数。过滤规则沿用协作候选：已启用、在群里、发起人在它的白名单里。 |
| `search_tasks(query, scope)` | 搜相关的历史任务，范围是本群或本发起人，返回编号、标题、状态、记要摘要。 |
| `get_task(code)` | 取单个任务的详情。 |
| `create_tasks(items)` | 建一个或多个任务。每项写清：标题（≤30 字）、执行员工、给人看的一句话、给执行员工的要求（背景、验收标准、注意事项）、关联的历史任务。 |
| `append_to_task(code, note)` | 新消息是对已有任务的补充或追问，追加给原执行员工，不新建任务。 |
| `ask_clarification(text)` | 需求不清、选错代价高时，在群里回复原消息问一句，只能问一句。 |

一轮调度最多调用 12 次工具，最多建 3 个任务，最长 60 秒。超出就停下，什么也不发。它的文字输出不进群，进群的只有上面工具产生的那一行简述或澄清。

**拆解的原则：** 能一个人做完的不拆。只有确实分属不同员工、而且能各自交付时才拆，例如「看下转化率掉了的原因，顺便把看板加个渠道筛选」，拆成数据分析和看板开发两件。拆开的任务互相关联，群里那一行写成「@数据助手 @看板开发 分头看下（T-128、T-129）」。

### 4.4 群里怎么说话

调度员在群里只说三种话，都是回复原消息、一行，不带长段落：

- 分派：「@数据助手 看下上周退货率（T-128）」
- 追加：「补充给 @数据助手 了（T-128）」
- 澄清：「要看的是线上渠道还是门店？」

执行员工在群里只说两种话：

- 需要确认：「@发起人 T-128 需要你确认：把 3 笔订单取消。回复「确认」或在任务页点确认」
- 完成或卡住：「T-128 完成：上周退货率 4.2%，比前一周高 0.8 个点。」后面附任务链接；卡住时写清卡在哪里。

过程中的进展只写进任务页，不刷群。执行超过 10 秒时，在原消息上加「处理中」表情，和现在 @ 回合的「敲键盘」表情一样。

## 5. 交接与执行

### 5.1 内部直接交接

群里的 @ 只是给人看的。真正的交接是平台把任务排进执行员工的队列，不依赖飞书把调度员发的那条 @ 推给执行员工（机器人之间的推送依赖额外权限，还要绕一圈）。

执行员工的这一轮：

- **身份。** 以发起人的身份执行，业务令牌按这个人签发，白名单也按这个人检查，和协作里的 B 一样。交给员工等价于发起人自己去 @ 它，不会多出权限。
- **会话。** 每个任务一个独立会话，`session_key = work:<编号>`，不用群会话。这样追加、确认、追问都能续上同一个会话，也不会和群里别的 @ 互相打断。
- **本轮块。** 带上给执行员工的要求、关联任务的记要和最近的群聊记录（只作背景）。
- **动手规则。** 查询和回答直接做。改数据、提交上线、建定时任务这类有后果的事，先发起确认，发起人确认后才执行（§5.2）。调度员写的要求不算发起人的确认。

### 5.2 确认

任务进入「等确认」。执行员工在群里回复原消息并 @ 发起人。发起人确认后任务继续，确认方式有两种：

- 在群里回复「确认」：只认发起人本人，而且要回复这条消息或带上编号。
- 在任务页点「确认」。

发起人拒绝或 24 小时没回应，任务转为「已取消」，执行员工不做任何改动。

### 5.3 退回重派

执行员工判断不是自己的活，可以调 `return_task(reason)` 退回调度员，调度员重新分派一次。第二次再被退回就停在「待人工处理」，在群里说一句，交给人决定。

### 5.4 与现有功能的关系

- **旁听：** 调度员是旁听的一种模式（`group_observe = dispatch`）。同一个群里有调度员时，其他员工的主动接话关掉，只保留 @。
- **AI 员工互相求助：** 保留。执行员工在任务里仍可单跳求助别的员工，求助记录挂在任务时间线上。
- **向同事求助：** 保留，记录同样挂在任务上。
- **排队：** 任务会话独立后，不同任务不会互相打断。同一员工同时只跑一个任务时，其余排队，任务页显示「排队中」。

## 6. 任务模型

新增两张表。队列表 `tasks` 已有，新表叫 `work_tasks`，避免混淆。

`work_tasks`

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `code` | 对人显示的编号，`T-<部署内自增>` |
| `title` | 标题，≤30 字 |
| `summary` | 给人看的一句话（调度时写，完成时更新为结果） |
| `status` | 待分派 / 处理中 / 排队中 / 等确认 / 已完成 / 未完成 / 已取消 / 待人工处理 |
| `platform`, `chat_id`, `origin_event_id` | 来源群和原消息 |
| `requester_user_id` | 发起人 |
| `assignee_bot_id`, `dispatcher_bot_id` | 执行员工、调度员 |
| `parent_id`, `related_codes` | 拆解关系、关联任务 |
| `brief` | 给执行员工的要求（Agent 层） |
| `digest` | 完成时的任务记要（Agent 层，§7） |
| `created_at`, `updated_at`, `closed_at` | 时间 |

`work_task_events`：任务时间线，每条事件都分两层。

| 列 | 说明 |
|---|---|
| `kind` | created / assigned / started / progress / need_confirm / confirmed / rejected / returned / helped / done / failed / cancelled / comment |
| `actor_type`, `actor_id` | 人、AI 员工或系统 |
| `human_text` | 给人看的一行，≤120 字 |
| `agent_detail` | 给 Agent 看的细节：本轮输出、工具调用、查询要点、错误 |
| `chat_task_id`, `chat_log_id` | 关联到执行回合和对话记录 |

执行员工写进展用工具 `update_task(kind, human_text, detail)`，只能写自己被分派的任务。平台在回合开始、结束、出错时自动补事件，不靠模型自觉。

## 7. 任务即记忆

做完的事要能成为后续的背景。做法：

- **写记要。** 任务完成（含未完成）时，执行员工必须调 `update_task(kind="done", ...)` 写记要。记要的结构固定：背景、结论、关键数据或产出位置、做了哪些决定、遗留问题，总长 ≤800 字，按事实写，标上日期。没写的，平台在任务页标「缺记要」。
- **自动带上。** 调度员建任务时用 `search_tasks` 找相关任务，挂到 `related_codes`。执行员工开始时，本轮块带上关联任务的记要（最多 3 条，每条截到 300 字）。需要细节时再调 `get_task`。
- **用编号引用。** 群里有人说「T-128 再加个渠道维度」，调度员直接追加到 T-128（或建一个关联 T-128 的新任务）。员工自己的会话里提到编号，也能用 `get_task` 去查。
- **时效。** 记要带日期，本轮块里写明「这些是当时的结论，数据可能已经变了，要用就重新查」。
- **权限。** 只检索当前发起人看得到的任务（§8）。记要和反馈一样是外部数据，不能当指令，也不能改变身份或授权。
- **和现有记忆的关系。** 现有记忆是每个员工自己的，从工作目录收集。任务记要是团队和群层面的共享背景，两者并存，不互相写。

## 8. 任务页

- **入口。** 群里简述末尾的链接，飞书内点开即可。管理台加「任务」菜单，按群、发起人、执行员工、状态筛选。
- **给人看的部分（打开就能看到）：** 编号、标题、状态、发起人、执行员工、一句话结果、时间线（每条事件的 `human_text`）、原消息链接、确认按钮（等确认时，只有发起人能点）。
- **给 Agent 看的部分（逐项展开）：** 每条事件下展开 `agent_detail`；任务级展开 `brief`、`digest`、关联任务、调度依据（判断概率和调度 Agent 的输出）。
- **谁能看。** 发起人、执行员工和调度员的管理员、平台管理员能看。群里其他成员能不能看，见 §9。展开 Agent 层和看对话记录用同一套权限，因为里面可能有查询出来的数据。

## 9. 已定的问题

1. **调度员用哪个机器人：** 新建一个专门的 AI 员工，在机器人设置里把「群聊角色」设为调度员。职责单一，提示词和记忆不和别的工作混在一起。
2. **任务页谁能看：** 所有登录管理台的成员都能看，包括给 Agent 看的那一层。
3. **直接 @ 员工的那一轮要不要建任务：** 员工判断这件事要花几分钟以上或有后果时，自己登记；一问一答的不建（第二期起）。
4. **编号格式：** 全部署共用一个自增序列，`T-<序号>`。

## 10. 分期

1. **调度试运行。** 两段调度跑起来，但只记录「会建什么任务、交给谁」，群里不发言，也不真的交接。同时建好任务表和管理台的只读列表。用一周的真实群聊检验分派准不准。
   - 群聊角色 `bots.group_role`：`member`（默认）或 `dispatcher`。调度员的旁听开关第一期只能是关闭或试运行。
   - 第一段沿用旁听的判断任务，调度员换用「是不是在找人办事」这道判断题，输入的职责说明换成团队简介（调度员的旁听职责说明）。
   - 第二段是调度员的一轮对话（`origin = dispatch`，会话键 `dispatch:<群>`，每个群一条会话，调度员记得自己在这个群分派过什么）。第一期不做调度工具：群里的员工名录（含各自职责、发起人能否使用）和这个群最近的任务直接放进本轮块，调度员按固定格式输出一个 JSON 决定，平台校验后落库。调度回合不挂业务令牌、技能以外的任何能力，最长 60 秒，什么也不往群里发。
   - 落库：`work_tasks`（状态 `shadow`，即试运行记录）和 `work_task_events`；调度的原始输出和校验结果写进 `group_observe_decisions.dispatch`。
   - 管理台「任务」页：列表和详情，详情里给人看的部分直接显示，调度依据、给执行员工的要求逐项展开。
2. **交接上线。** 群里发简述，任务在内部交给执行员工，有独立会话、确认流程和任务页的给人看部分。
   - 最小版（已做）：调度员可以开启。开启后建的任务直接是「排队中」，平台在原消息上排一轮执行员工的对话（会话键 `work:<编号>`，同一任务串行），调度员回原消息一行「@员工 标题（T-n）」（纯文本，不真的 @，免得执行员工再被触发一次）；追加排给原执行员工，澄清发调度员问的那一句；出错不出声。执行员工以发起人的身份做（发起人须与调度时认出的一致，白名单按执行员工核对），本轮块带任务、要求、补充和回复规则，回复挂在原消息上；这一轮结束按回复把任务记为已完成、等确认或未完成。@ 执行员工并带上编号、或回复它的任务回复并 @ 它，续进同一个任务会话。试运行期间记下的任务不交接。
   - 跟进与否（已做，迁移 0075）：调度员给每件事标 `track`。当场能答完的（一问一答、查个数、说明办法）不跟进：照样记任务、照样交接，但调度员不发言、群里不出编号，执行员工直接回答；要多步、要等确认或别人配合、之后还要问进展的才跟进，群里的编号写成任务页链接。执行员工的群回复要简短：只给结论和必要信息，不写开场白、不解释怎么续。
   - 不跟进的事怎么续（已做，迁移 0080）：群里没有编号，所以回复员工的答复时按发送存档（`feishu_sent_messages.work_code`）认任务；只 @ 员工时，同一发起人在本群两小时内最近一件事（跟进与否都算）当作接着问，问的是别的事由员工按新问题答。任务会话只有发起人能续进去，带编号也一样。调度员新建任务标了 `related` 时，员工本轮块带上已完成相关任务的结果（最多 3 条，每条 300 字）。
   - 还没做：确认按钮与「确认」识别、退回重派、任务记要、处理中表情。
3. **记忆与细节。** 记要、关联任务自动带上、编号引用、Agent 层展开、退回重派。

## 11. 风险

- **调度错人。** 第一期试运行先拿数据。上线后执行员工可以退回，第二次退回就转人工。
- **长任务没人知道进展。** 「处理中」表情，加上任务页的时间线。
- **记要质量参差。** 结构固定、有长度上限、平台标出缺记要的任务；第三期可以加记要的复核。
- **成本。** 第一段每批消息约 0.0001 美元；第二段只在判断为是时跑，按每天几十次估算。上线后在管理台统计。

# 个人助理

## 背景

成员希望有一个以本人飞书身份工作的助理：盯消息、起草回复、改文档、处理审批、跟进待办，并主动推进事情。所有对外有影响的操作先经本人审批。

平台已有的基础：飞书个人授权（约 110 个 `feishu_*` 工具，含以本人身份读写消息），飞书私聊记录仅本人可见，私有 Runtime，群写入的「暂存参数 → 本人确认 → 平台原样执行 → 续接」通路，Tower 审批的回调与对账。

缺的部分：

1. 私聊里的个人写操作只有提示词约束，工具被调用就执行。
2. 飞书没有用户身份的消息事件，平台收不到「别人发给本人」的消息。
3. 对话、流式输出、原始事件在库里是明文；节点上的 CLI 转录是明文；记忆和工作目录是文件。
4. 没有「一轮里派出独立会话再收回结果」的做法。

## 已定决策

| 决策 | 结论 |
|---|---|
| 范围 | 只做飞书；人人可开通，由管理员控制可开通范围 |
| 入口 | 只接私聊；群消息在网关丢弃，被拉进群时退群并私信说明 |
| 飞书应用 | 全员共用一个应用，平台里每人一条助理记录；路由层支持多个应用 |
| 数量 | 同一飞书企业内一人只有一个生效的助理 |
| 审批 | 全部走 Tower，不做飞书卡片审批 |
| Runtime | 默认用共享的助理池；可绑定本人的私有 Runtime |
| 个人数据 | 聊天记录、个人知识、待跟进、审批参数全部加密入库；密钥只在平台侧，不下发给 Agent。例外：调度公共 AI 员工时交出去的问题与对方的答复，在目标员工的记录里是明文（见第八节） |
| 工作目录 | 每人一个，只放规则与经验总结，不放个人信息 |
| 协作 | 可派平台子任务，可调度公共 AI 员工；结果回助理会话，不往飞书发消息 |

## 原则

1. **对外有影响的操作由平台拦截**，不靠模型自觉。批准后平台按暂存参数原样执行。
2. **密钥不离开平台。** 助理每天读别人发来的消息，这些是不可信输入；Agent 进程里不能有能解密历史数据或直接调用飞书的东西。
3. **明文在节点上只存在于一轮运行期间。**
4. **没事不花模型额度。** 盯消息由平台轮询，不经模型。

## 威胁模型

| 对象 | 能否看到个人内容 | 依据 |
|---|---|---|
| 其他成员、团队负责人、平台管理员（经管理台和接口） | 不能 | 接口只对本人放行；调度公共员工留在目标员工名下的那一轮，其管理者与平台管理员只看得到元数据；「我的助理」接口不受理管理命令以成员身份建的会话，这种会话读对话记录与任务详情时助理的加密内容也不还原 |
| 只拿到数据库或备份的人 | 不能 | 内容列是密文。等待审批的附件在临时桶里未加密，对象名只在密文里；持有桶凭据的人可以读到，这是所有者接受的取舍。调度公共员工时，问题与答复在目标员工名下的 `chat_logs`、`task_streams` 里是明文，不随所有者的数据密钥销毁，按各表的保留期清理；同样是所有者接受的取舍 |
| 同一节点上的其他 AI 员工 | 不能 | 与普通员工之间：助理只在单独系统用户下的助理专用实例里运行，平台每轮开轮前核对所在节点（助理池或私有运行时）及同机同 uid 的节点上没有普通员工，不满足就暂停；助理之间：沙箱隔离，转录每轮清除 |
| 被注入的助理自身 | 不能外传（有残留，见第三节「已知限制」） | 写操作过审批，沙箱限制出网。调度公共员工是沙箱之外的通道：只读调度不过审批，靠提示词规则、问题 4000 字上限、每日个数与审计约束；要对方改动的一律过审批 |
| 同时拿到数据库和平台主密钥的人 | 能 | 不防；经平台的接口与命令解密时记访问记录（`assistant_access_log`），直接读库解密不留痕 |
| 只能在服务器上执行管理命令的人（没有主密钥与数据库口令） | 不能 | 管理命令以成员身份建的会话不算本人在场：内容不还原，尝试会记进所有者的访问记录 |
| 共享节点的 root，在该助理运行的那一轮里 | 能 | 不防；需要时绑定私有 Runtime |
| 审批系统的其他用户（经其界面和接口） | 不能 | 正文只对审批人本人开放 |
| 能直接读审批系统数据库的人 | 能，限审批单正文 | 审批系统明文保存；见第四节「对 Tower 的依赖」 |

要防「主密钥持有者」和「节点 root」需要用户自持密钥，那样无法无人值守盯消息，不做。

## 一、助理记录与入口路由

### 数据模型

- `bots` 加列 `kind`（`standard` / `assistant`，默认 `standard`）与 `owner_id`。部分唯一索引：`kind='assistant' AND enabled` 时 `owner_id` 唯一（一个部署对应一个飞书企业）。
- 应用凭证以现有的 `platform_apps` 为准，新增能力值 `assistant`。`bots` 加列 `platform_app_id`；助理记录的 `credentials_enc` 是应用凭证的副本，应用凭证变更时在同一事务里同步到该应用下的全部助理记录。这样约 20 处按记录读取飞书凭证的代码不需要改。
- 飞书个人授权沿用 `feishu_personal_grants`（主键仍是机器人 × 人），档位固定为 `all`，授权时带上离线访问权限。

### 网关改造

现状是一条机器人记录一个子进程、一条长连接、约 4 条数据库连接，并用咨询锁禁止两条记录共用一个应用。对助理应用改为**一个应用一条连接**，开销随应用数增长，不随助理人数增长：

- 租约与子进程按 `platform_app_id` 认领；建机器人时「一个应用只能分给一个机器人」的校验对助理应用放开。
- 入站：私聊消息按发送人的用户编号找到其助理记录，再进入现有的归一化与落库流程；没有记录时发「开通个人助理」卡片。身份识别沿用通讯录同步的用户编号，没和应用聊过的人首次私聊也能认出。
- 群消息一律丢弃，不入库。收到进群事件时退群，并私信拉群的人说明这个应用只支持私聊。退群接口需要新封装，应用清单补群成员写权限。
- 卡片回调按操作人的用户编号路由，只认记录的所有者。
- 出站：同一进程认领该应用下所有助理记录的待发消息，出站锁仍按记录。

应用密钥轮换会让该应用下所有助理的个人授权同时失效（授权行的指纹含密钥）。轮换前提前通知，轮换后各人重新授权一次。

### 对助理记录关闭的能力

成员与协作者、可用人白名单（固定为所有者一人）、群聊旁听、调度员、接受其他员工求助、API 驱动任务、开发模式、文件记忆、规则文档备份、公共任务页、管理台里的工作目录文件与 git 管理（所有者本人也不行）、装技能（含系统自动安装）、MCP 登录、运行环境检查、定时任务、告警来源、审批人设置。这些在服务端按 `kind` 拒绝，管理台不显示对应设置；对应的节点命令在助理专用实例上同样拒绝（见第三节）。换运行时与预览只对所有者开放。

## 二、加密与存储

### 密钥

- 新表 `assistant_keys`：`user_id`、`dek_enc`、`created_at`、`destroyed_at`。每人一把 256 位数据密钥，用平台主密钥包裹（沿用 `core/crypto.py`，带 kid，AAD 绑定 `user_id`）。
- 内容用数据密钥做 AES-256-GCM 加密，AAD 为「表名.列名:助理记录编号」：密文不能挪到别的表、别的列或别人的助理。不按行主键绑定，因为这些表的主键在插入时才生成，按主键绑定每行要多写一次；代价是同一助理同一列的两行之间可以互换。
- 数据密钥带代数。销毁后重新开通会签发新一代密钥，旧一代的密文一律视为已锁定，永久不可读。
- 主密钥轮换只需重新包裹数据密钥，不重写内容。
- 数据密钥只在平台进程内解开，不写入任务载荷、环境变量或日志。

### 加密范围

对 `kind='assistant'` 的记录，下列内容列写入前加密、读取时解密：

| 表 | 列 |
|---|---|
| `inbound_events` | 事件载荷 |
| `tasks` | 载荷、结果 |
| `task_streams` | 思考与正文 |
| `outbox` | 出站载荷（网关发送前解密） |
| `chat_logs` | 消息与回复正文 |
| 本文新增的表 | 标了 `_enc` 的列 |

状态、时间、类型、长度等元数据保持明文，供调度与排障使用。运维接口照旧只返回元数据。调度公共员工时目标员工名下的行不在范围内（那是普通员工的行）。

### 销毁

停用助理或成员离职时销毁其数据密钥（清空 `dek_enc`，记 `destroyed_at`）。密文随即永久不可读，不需要逐表删除；过期清理任务照常回收行。调度留在目标员工名下的记录不受影响。

## 三、节点隔离

### 沙箱

助理的每一轮在沙箱里运行：

- 可读写：本人的工作目录、本轮临时目录、本助理的 CLI 配置目录（每轮新建、轮次结束删除；续聊需要的会话转录由平台保管）。
- 只读：CLI 程序与模型登录凭证（是去掉刷新令牌、按字段白名单收窄的副本，不是节点上的原文件）。
- 不可见：节点上其他目录，包括其他员工的工作目录与转录。
- 出网只放行平台地址与模型接口地址，其余连接拒绝。查外部资料走平台提供的工具。沙箱断网，经守护进程的放行代理连平台与模型接口；平台地址是控制面地址加上一组写死的环境变量键（系统目录、飞书个人工具、飞书文档、企微个人工具、定时任务、凭证、云代理）的取值，这些值由平台写进请求，请求里别的值不进名单；不收地址字面量，解析到回环或链路本地地址的拒绝；登录令牌的刷新地址不在名单里。
- 环境变量里只有本轮能力令牌（沿用现有做法），没有数据密钥、飞书令牌或应用凭证。

采用 bubblewrap 沙箱（助理之间），再加每台机器一个助理专用的系统用户（助理与普通员工之间）；每个助理一个系统用户的方案不采用。沙箱方案落地为 bubblewrap：节点启动时自检，通过后在心跳里声明 `assistant_sandbox_v1`，平台只把助理的轮次派给声明了的节点。

只有装成助理专用实例（`config.json` 的 `assistant_only`，安装参数 `--assistant-only`）的守护进程才自检、才声明能力；它在节点这一侧兜底：不带沙箱标记的对话请求一律拒绝，节点命令只接探活、状态、额度、席位与开通 / 换运行时用到的目录检查和初始化，不跑遍历工作目录的定时任务。不是助理专用实例的守护进程从不跑助理。

### 转录

- 一轮结束后，节点守护进程把本轮的 CLI 转录经 TLS 上传平台，平台用数据密钥加密后存入新表 `assistant_transcripts`（`bot_id`、`session_id`、`blob_enc`、`size`、`updated_at`），节点上随即删除。
- 续聊前由平台解密下发，守护进程还原到沙箱内，再启动 CLI。
- 单个转录上限 50MB，超过时结束该会话，下一轮开新会话。
- 上传与下发凭派出这一轮时的交接编号；上一轮的转录没传回来时不拿旧的续，开新会话。打包与还原都不跟随符号链接，还原时限制成员数与展开后的总量，失败时清干净。
- 守护进程启动时清扫助理目录下遗留的转录（上一轮异常退出）：上传后删除。清扫在启动时与之后每 10 分钟各一次，再传一次后无论成败都删除。平台的 scheduler 另外清理长期不再更新的转录行。
- 本轮临时目录在轮次结束时删除。下载的文档、附件只放这里。

### 工作目录

分配方式与普通员工相同，一条记录一个目录。内容限于规则、经验总结和技能。安全提示词写明：工作目录不放人名、聊天内容、审批内容和任何个人信息，这些一律用知识库工具保存。

### Runtime 分配

- `relay_servers` 加列 `assistant_pool`。开通时在池内选助理数最少的在线节点。
- 所有者可改绑到自己的私有 Runtime（沿用 `relay_policy` 的可选规则），那台机器上要装一份助理专用实例。私有节点离线时助理暂停并私信所有者，不回落到池。
- 隔离规则对助理池与私有运行时一样：跑助理的节点上没有普通员工，同机同 uid 的节点上也没有，节点上报本机指纹与 uid 且不是 root。平台在每轮开轮前（不满足就暂停，私聊告知所有者，不带节点信息）、助理换运行时、普通员工绑定或换运行时（拒绝跑着或正在迁来助理、声明了沙箱能力的节点及其同机同 uid 节点）三处核对。
- 迁移只需改绑：个人状态在库里。第 1 期换运行时只落到目标上一个全新的空目录：不复制工作目录、不迁会话与记忆（这些都要守护进程在沙箱外读写助理写过的目录），换完后的第一轮带上平台保存的上下文说明；同一共享目录原样沿用。开通没完成、正在停用或已停用的助理不换运行时（预览同样拒绝，也不能初始化工作目录）；换的过程中停用开始了，这次换作罢，刚建的新目录登记待删。轮次开始时工作目录已不在原处或正在删除，这一轮被拒绝（`workdir_missing` / `workdir_busy`）。
- 每个节点对助理轮次设并发上限，超出的排队。每人设每日轮次预算（设置 `assistant_daily_turn_budget`，默认 200；`assistant_settings.daily_turn_budget` 可按人覆盖），按所有者时区的自然日数真正开了轮的次数。用完后只有立即交回级别的事项照常交回（至多再透支 20 轮），其余攒到次日，并私信告知一次；所有者自己发的消息不受限制。
- 助理与普通员工共用机器：要跑助理的机器上以专用的系统用户再装一份助理专用实例、注册成单独的节点；平台凭心跳上报的本机指纹与 uid 强制助理所在节点与承载普通员工的节点分属不同系统用户（见上面的隔离规则）；运行普通员工的用户不能有 root 或免密 sudo（平台查不到，部署方保证）。
- 池节点离线同样暂停，不重新选节点；助理池开关被关掉时绑在那里的助理也暂停，直到管理员改绑（是否应在仍有助理绑定时拒绝关闭，待定）。

### 已知限制

- 出网代理只按主机名放行、不解 TLS：被注入的助理可能用自带的密钥把数据传到模型厂商一侧它能控制的存储，或利用共享 CDN 做域名前置。本期不防。
- 节点用环境变量或 API Key 文件登录时，带进沙箱的是一枚长期有效、没有到期门槛的凭证，被注入的助理读得到；OAuth 登录时只是一枚到期即失效的访问令牌。
- 本机其他用户读得到进程命令行（CLI 的命令行里有系统提示词）：助理机器应以 `hidepid=2` 挂载 `/proc`；第 2 期的个人知识页不进 system prompt，放在首轮的本轮块里经标准输入传给 CLI，命令行里没有个人内容。
- 封存最大 50MB 的转录在平台进程的事件循环上同步执行，与普通员工共用进程；转录传输同时只放 2 个，每个约占转录大小三到四倍的内存。
- 交接编号在内容构建之前就已登记：这一轮若在派出之前因别的原因结束（媒体失败、中途停止），下一轮会丢掉原本还好的转录、开新会话；只有排队超时且确定没有节点领到的一轮会作废编号、下一轮照旧续上。
- 暂停期间每条消息各回一次暂停提示，不节流。
- 沙箱没有 seccomp、没有禁止嵌套用户命名空间（需要 bubblewrap 0.8 以上，旧节点会因此失去能力）；沙箱不限内存、进程数与可写目录大小，部署文档建议给助理专用实例加 systemd 的 `MemoryMax` / `TasksMax`。
- 换走后的旧目录由平台登记、经原节点删除；原节点一直离线时目录一直留着，删掉之前助理回不到那台节点；还有目录等着删的运行时实例不能删除。节点只在确知时才答「已删除」或「不是这位助理的」，确认不了（共享存储没挂上或报错、登记缺失或损坏、目录被手工还原或复制过）一律答「无法确认」，平台保留登记、最长每 6 小时重试（`dir_unverified`），可能需要运维手工删目录并清登记；没有登记的目录节点从不删，删完后登记留 30 天墓碑。
- 账号停用的宽限期里，已决定或已过期的审批单已经收口，所有者的账号在宽限期内恢复后，这些单的结果不会回到对话里，需要所有者重新提。
- 管理员没有「暂停」：只有停用（不可撤销，只回状态）；助理记录不能用启停开关启停，停用完成前不能删除。
- 沙箱里流出的额度、运行时与报错帧不可信，平台不拿它们更新实例的额度与健康记录（这一轮自己的用量照常记进它的对话记录）。

## 四、审批闸门

### 拦截

个人工具按 `endpoints.py` 的 `kind` 分为读与写。对助理记录，写类工具（发送、编辑、撤回、表情、建群拉人、文档与表格写入、评论、权限、审批决定、日程、任务、邮件）不执行，改为：

1. 参数加密存入新表 `assistant_approvals`。
2. 向 Tower 提交一张审批单，沿用云签名代理的 agent 发送端流程：发起人是所有者，审批人不填（默认即发起人本人），目标系统为 `feishu-personal`，请求体是暂存参数的规范化形式。
3. 返回 `{status: "pending_approval", approval_id}`。本轮不结束，助理可以继续处理别的事。

平台同时是发送端和目标系统：批准后拿到的一次性令牌与请求体哈希绑定，平台执行前先核销，保证执行的就是被批准的那份参数。`feishu-personal` 与 `assistant-dispatch` 两个目标系统登记时关闭模型比对，正文不送任何模型。

`assistant_approvals`：`id`、`bot_id`、`tool`、`args_enc`、`args_hash`（带密钥的摘要，只拿到数据库的人无法据此猜参数）、`channel`、`chat_id`、`anchor_message_id`、`thread_id`、`topic`、`status`（pending / approved / rejected / withdrawn / stale / executed / failed / expired）、`reason_enc`、`result_enc`、`external_id`、`approval_id`（Tower 的编号）、`request_hash`、`error_code`、`origin_event_id`、`session_key`、`expires_at`、`notified_at`、`execute_started_at`、`has_files`、`created_at`、`decided_at`、`executed_at`。这张表同时是审批流水。

唯一不经审批的写操作是在待回复的那条消息上打「处理中」表情及其撤销，由专门的工具提供，表情类型和目标消息由平台限定；打过的表情记在 `assistant_marks`。

### 审批单内容

- 由平台按工具模板从实际参数生成，正文是纯文本：渠道（私聊 / 群聊 / 文档 / 审批 / 日程 / 任务 / 邮件）、对象（人名或群名）、被回复的原话、要发出的正文或改动摘要。对象里的会话名、对方名字压成单行，摘要与「对象」行都是如此，名字里夹带换行也伪造不出抬头行。
- 带文件的操作（发文件、存入云空间、邮件附件）把文件放在临时桶里等待审批：随机对象名、不加密本体、桶上 7 天自动清理；审批单上附文件名、类型、大小与查看链接，执行前核对大小与 SHA-256。
- 助理可附两段说明：背景、做过的调研。它们显示在正文之下，并标明是助理撰写。
- 一张单只装一件事。同一内容发给多人可以合并，最多 10 条。
- 摘要（单行，会出现在手机锁屏推送里）只写渠道和对象，如「私聊 → 某人」，不带正文和原话。正文上限 10000 字，超出时截断被引用的原话，要发出的内容不截断，仍超出则拒绝提交。
- 审批单默认 72 小时过期，过期按撤回处理并通知助理。

### 提交前检查

消息类必须带 `chat_id` 与锚点（回复的那条，或助理读到的最后一条）；各消息工具分别怎么套锚点规则，见计划「设计选择」第 12 条的表，空会话可以不带锚点。提交时平台重新读取会话：

- 锚点之后所有者本人已经发言：拒绝，要求读完最新消息后重写。
- 锚点之后对方又发了消息：拒绝，同上。这里只数真人发的、未撤回的消息。
- 同一 `args_hash` 已有待批或已执行的单：返回已有的那张；已执行的只看 72 小时内。

同时待批上限 10 张。

### 决定之后

- 决定经 Tower 回调送达，丢失时由现有对账补上。
- 助理不再是可用状态（已要求停用，或账号停用满 24 小时后进入停用）之后才送达的决定不执行，单按「已撤回」收口；过期也不再回投对话，不再发提醒。停用开始之前已批准的单照常执行。
- **批准**：平台再做一次锚点检查，通过后按暂存参数原样执行，结果上报 Tower，并作为事件投回助理会话。锚点检查不通过时不执行，状态记为 `stale`，交回助理重新起草。
- **拒绝**：理由投回助理会话，由它按理由改稿重提或放弃。
- **执行失败**：错误投回助理会话。不自动重试，改好后重新提交。
- **执行中断**：执行进程在调飞书期间被杀时，同一任务重跑把单收口为失败。此外 scheduler 每轮调用 `execute.recover_stuck`：已批准超过 15 分钟、又没有在途执行任务的单记为失败，通过结果回合告诉助理并上报 Tower，绝不第二次执行（已记下开始执行的是 `execution_interrupted`，需要核对；没有记下的是 `execution_not_started`，什么都没执行、可重新提交）；这一轮的计数多一项 `assistant_approvals_recovered`。飞书调用做完之后提交数据库失败，也不妨碍这张单被收口。
- 批准时填写的理由只作备注，平台不解析，执行内容不变。

### 改稿与撤回

工具 `approval_revise(id, 新参数)`、`approval_withdraw(id, reason)`、`approval_list(status, topic)`。只有 `pending` 的单可以改稿或撤回。改稿是用同一个外部编号重新提交，Tower 原地替换并重新通知；撤回调用 Tower 的撤回接口。平台在下列情况自动撤回往会话里发新内容的待批单并通知助理（每 5 分钟检查一次，原因记在 `error_code`）：所有者已在该会话亲自回复（`owner_replied`）、对方撤回了被回复的消息（`anchor_recalled`）、锚点之后会话又有了新消息（`anchor_moved`）。「会话又有了新消息」在私聊里指对方发的任何一条；群里只算与这个话头有关的——@ 所有者、直接回复锚点那条、与它同在一个话题里（或在以它为根的话题里；只认话题编号 `thread_id`，普通的引用回复链根消息相同也不算）、锚点的发送人自己又发的——别人接着聊别的不算；审批单带着话题、读的是话题视图时按私聊口径全算（话题里第三人的回复可能已经把问题答掉），提交前检查与执行前复查同一口径（所有者亲自回复、对方撤回在哪里都算；不是回复、只带锚点的发送，锚点那条已被撤回时同样判过时 `message_gone`）。为了不在活跃的群里形成「撤回、提醒、重新起草、再撤回」的循环：同一位助理同一个会话 30 分钟内至多因 `anchor_moved` 自动撤一次，之后的留着待批、交给执行前复查；这类提醒按攒批的级别交回，另两种原因的立即交回。「之后」从这张单提交的时刻算起，改过稿的从最近一次改稿算起（`assistant_approvals.revised_at`）：改稿时平台重新读过会话。审批单正被执行、决定或改稿锁着时这一次不撤，留到下一次检查。审批通过后由平台代所有者发出的消息记下编号（表 `assistant_sent`），盯消息读到它时不当作所有者亲自发言。

Tower 不可用时提交失败，写操作不执行。所有者在 Tower 没有对应账号时提交失败（`tower_account_missing`）；开通时查不到账号，只提醒先登录一次（见第十节）。

### 对 Tower 的依赖与已知限制

| 事项 | 现状 | 处理 |
|---|---|---|
| 单的可见范围 | 只有审批人能看正文；列表与个人令牌只露摘要 | 满足要求 |
| 正文保存 | 明文、永久保留，撤回也不清除 | 接受现状；开通页如实告知「审批单正文保存在审批系统里」 |
| 提交与撤回 | 提交时带 `expires_at`；撤回按外部编号；`feishu-personal` 登记为免比对 | 见 `docs/tower-approval.md` |
| 推送 | 只有 iOS 推送，没有其他通道 | 平台在助理私聊里补一条「有 N 张待批」加链接，不带内容；同一批次合并，5 分钟内不重复 |
| 账号 | 首次登录或管理员预登记后才存在 | 没有按用户名查账号的接口，开通时查不到：开通卡片与欢迎语提醒先登录一次，没有账号时第一次提交报 `tower_account_missing` |
| 限流 | Tower 侧没有 | 由平台的待批上限约束 |

## 五、盯消息

### 轮询

平台侧进程，不经模型。新表 `assistant_watch`（`bot_id`、`cursor_enc`、`head_enc`、`interval`、`next_poll_at`、`state`、`last_error`、`last_ok_at`、`failures`、`keepalive_at`、时间戳）。游标（各会话读到的位置，`cursor_enc`）与上一轮的会话顺序（`head_enc`）都用所有者的数据密钥加密：和谁有会话、什么时候说过话本身就是他的私事；要按游标里的字段判断时取出来在内存里看。在所有者的工作时段内每 60 秒轮询一次，多个助理的轮询时刻错开。

飞书的限频按「应用 × 企业 × 接口」计，全员共用：列会话与读会话历史各为每分钟 1000 次，搜索消息只有每分钟 100 次。所以不逐个会话轮询，也不用搜索接口：

1. 每轮只调一次列会话接口（用户身份，含单聊与群，按最近活跃倒序，取前 50 条）。
2. 与上一轮保存的顺序（`head_enc`）对比：排到前面的会话视为有新动静；顺序没变的会话里，藏着新消息的只可能是开头连续的一段，所以从第一个开始逐个读，读到一个没有新消息的为止。所有者标记的重点群每轮直接读。
3. 只对这些会话读取游标之后的历史；话题里的回复按话题读取。游标里没有的会话（刚被拉进的群、被挤出游标又活跃的会话）不从开始盯的时刻读，只回看 30 分钟（轮询停得更久时回看到上一次成功轮询）；会话从忽略名单移出时游标置为当时；发出超过 24 小时、且早于上一次成功轮询的消息不入箱，只前移游标（截止点取「现在 − 24 小时」与上一次成功轮询里更早的那个：周末、请假期间发来的消息平台没见过，回来后的第一轮照常入箱；回看起点与截止点都不早于「现在 − 7 天」，停了两三周后恢复只交回最近 7 天的）。这三条防的都是把一段历史整批倒进收件箱。一轮读不完、排到下一轮的会话当场把这一轮的回看起点与年龄截止点记进游标，不因为「上一次成功轮询」变成刚才而少读。顺序没变的那一段没探完（时间或次数用完）时同样：没探到的会话与这一轮的年龄截止点记在游标顶层（`p`、`a`），之后各轮接着这一段探、截止点取较早者，探完才清。

这样每人每分钟约 1 次列会话加少量读历史（空闲时 1 次）。平台对每个应用记两类接口最近一分钟的用量（表 `feishu_rate_usage`），接近上限时拉长所有人的间隔；收到限频错误时按响应头给出的等待秒数退避。单个应用承载不下时把新开通的人分到下一个应用（未做，接近上限时只拉长间隔并告警）。同一个会话连续 3 轮被飞书拒绝读取时先放下它 1 小时，不让它拖住整个轮询。

令牌：刷新令牌一次性使用，刷新与落库在同一把行锁内完成；轮询本身保证不会超过刷新令牌的有效期，不轮询的时候（下班、暂停）每 24 小时强制刷新一次（只刷新令牌，不核对任何接口的权限）。一轮里换到新令牌之后出错（包括意外的异常）也照常提交。飞书要求授权满 365 天重新授权，到期前 14 天起每天在私聊里提醒一次（按 `feishu_personal_grants.authorized_at` 算，只在工作时段提醒）。scheduler 停止时，正在进行的那位助理的一轮最多再等 20 秒提交完，不就地回滚。

拉到的消息只在内存里分级，交回的条目写入 `assistant_inbox`（`bot_id`、`kind`、`level`、`chat_id`、`message_id`、`thread_id`、`message_at`、`summary_enc`、`status`、`void_code`、`hold_until`、`delivered_task_id`、时间戳），同一条消息只入箱一次。

### 分级

| 级别 | 条件 | 处理 |
|---|---|---|
| 立即交回 | 私聊；群里 @ 本人；审批被拒或执行失败；所有者标记的重点群里的消息 | 立刻投递 |
| 攒批 | 其他群里真人的消息；私聊里机器人发来的通知（新出现的飞书审批待办以这种形式到达） | 满 5 分钟投递一次 |
| 压着 | 所有者 10 分钟内在该会话亲自发过言 | 他停下满 10 分钟仍未回才投递 |
| 忽略 | 所有者自己发的；群里没 @ 他的机器人消息；所有者设为忽略的会话 | 不投递 |

平台另外每 5 分钟为每位在上班的助理做一次顺带检查（不经模型）：待批单的锚点变化与对方撤回（自动撤回审批单）、已交回的消息在 24 小时内被对方撤回（关掉它引出的待跟进）、「处理中」表情挂了 4 小时未回、当天到期的待跟进。结果作为 `kind = 'reminder'` 的收件箱条目与消息条目一起交回；后两类每条每天至多一次。

### 投递与会话

- 投递是在助理会话里创建一个任务，类型 `assistant_handover`，载荷只有本批条目的编号；条目的内容在开轮时由平台解密、写成整理稿（别人写的字都在引用行里）。`feishu_personal/policy.py` 允许的任务类型加入它和 `assistant_job_result`、`assistant_approval_result`。
- 助理会话与所有者的私聊共用一个会话键，所有者在私聊里说的话和交回事项在同一个上下文。
- 会话每天换新（按所有者时区，`chat_sessions.local_day` 记这个会话是哪天开始的；子任务会话不换）。跨天的连续性靠待跟进和知识库，不靠会话上下文。
- 同一位助理同一时刻至多一个交回任务；上一轮未结束时新的交回事项排队，由下一轮带上。条目只有在这一轮正常结束后才记为已交回；被所有者的消息取消、让路放弃、暂停或失败的轮次，条目回到待交回（真失败满 3 次作废）。下班、冷启动没做完、运行时暂停、所有者的账号停用或飞书身份解绑期间不入队（入队前就看，不等开轮时才发现）。
- 一轮没走完之后不马上再排：第一次等 60 秒，连续没走完逐次加倍，封顶 15 分钟（`assistant_delivery.handover_misses`、`handover_retry_at`），走完一轮清零；等待期间新到的条目也不另开一轮。所有者持续在聊时每一轮都会被他的下一条消息取消，他本人在场，这些事本来就该等。
- 被取消的那一轮平台分不清哪几件做完了，整批放回。那一轮的转录也不保证留在会话里：节点在取消之后才在后台上传转录，下一轮要是先开，平台发现上一轮的交接没办完就换一个新的 relay 会话，此前的上下文都不在了。所以条目上记着带着它开过几轮（`assistant_inbox.handovers`，开流时加一），大于 0 的条目重新交回时整理稿写明「这件事之前交回过 N 次」，要助理先用 `approval_list`、`followup_list` 核对再动。
- 每位助理的投递状态在新表 `assistant_delivery`（`bot_id`、`handover_seq`、`budget_notified_on`、`reauth_reminded_on`、`next_sweep_at`、时间戳）；`assistant_inbox` 另有 `failures` 与 `handovers`。

### 上下班

默认按所有者设置的工作时段自动开始和停止（时区、每天的起止时间、工作日；不支持跨午夜）。私聊里发「上班」「下班」临时切换，平台直接处理、不经模型：「上班」到当天的下班时间（当天不是工作日或已过下班时间则到当地次日零点），「下班」到下一个工作时段开始，到点自动失效。所有者在私聊里说要改时段、时区、重点群或忽略的会话时，助理用 `assistant_settings_get` / `assistant_settings_update` 改；这两个工具只在所有者发起的轮次里可用。

下班时做当天的编译：把当天的进展、被拒与执行的审批、有变化的待跟进整理进知识库。每位助理每个自然日至多一次，当天没有活动不做。编译是平台派出的一个子任务（`origin = system`）：不占主会话，不占助理每天的名额，做完不投回主会话；无人在场，改不了置顶页。子任务没有审批工具，被拒与已执行的审批单的摘要由平台写进交代。（第 2 期曾做成主会话里的一轮 `assistant_compile`，这个任务类型不再入队。）

## 六、个人知识与待跟进

### 知识库

新表 `assistant_pages`：`id`、`bot_id`、`path_hmac`（同一助理内唯一：规范化并折叠大小写后的路径，用所有者数据密钥算的带密钥摘要）、`path_enc`、`title_enc`、`summary_enc`、`body_enc`、`size`（正文字节数，明文，合计上限按它求和）、`pinned`、`version`、`updated_by`（`owner` / `assistant` / `import`）、`updated_at`。

工具（平台 MCP，解密在平台侧）：

| 工具 | 作用 |
|---|---|
| `notes_index` | 返回全部页面的路径、标题、一句话摘要 |
| `notes_read(path)` | 读一页 |
| `notes_search(query)` | 把该助理的全部页面解密到内存，按关键词匹配排序，返回命中片段 |
| `notes_write(path, body, summary)` | 新建或整页替换，带 `version` 乐观锁 |
| `notes_delete(path)` | 删除一页 |

- `pinned` 的页面（口吻、判断原则、被拒复盘归纳出的规则）和索引放进主会话每个会话首轮的本轮块（随用户消息经标准输入传给 CLI，不进 system prompt 与命令行）；之后的轮次只在置顶页有更新时补一条变更说明。页面的文字（正文、路径、标题、摘要，含索引行）进本轮块时一律逐行以「> 」引出，平台写的行里不带页面的文字：无人在场的轮次也能建不置顶的页，它的索引行不能与平台的说明行同形。置顶页正文合计上限 24KB，超出时只注入索引；索引上限 16KB，超出时只列置顶的与最近更新的。置顶页被删除或取消置顶后同一会话里没有说明，换新会话时纠正。
- 平台写的三页置顶页：`profile/voice.md`（口吻样本，冷启动时由助理从所有者自己发出的消息归纳，`updated_by = assistant`；已有的这一页最后不是助理写的就不覆盖）、`profile/people.md`、`profile/duties.md`（冷启动里所有者在卡片上填的，`updated_by = owner`）。口吻页是唯一在无人在场时写成的置顶页：那一轮在独立会话里，只有保存这一页的工具，输入只有所有者自己发出的消息。
- 上限 2000 页、合计 20MB、单页 200KB，足够在内存里检索，不做密文索引和向量检索。
- 工具比上表多出的参数：`notes_write` 的 `title`、`pinned`、`version`；`notes_index` 的 `folder`、`limit`、`offset`；`notes_read` 的 `text_offset`、`text_limit`；`notes_search` 的 `limit`。
- 组织方式沿用「索引 + 页面 + 链接 + 定期编译」：人、项目、决策、日志各自成页，下班时编译。

### 待跟进

新表 `assistant_followups`：`id`、`bot_id`、`seq`（每个助理内递增，显示为 F012）、`category`（等我决定 / 我答应 / 等别人 / 提醒我）、`status`、`review_on`、`due_on`、`origin_message_id`、`job_id`、`title_enc`、`notes_enc`、时间戳，另有 `closed_at` 与 `close_code`（平台自动关闭的原因，目前只有 `origin_recalled`）。分类在库里是 `decide` / `promised` / `waiting` / `remind`，状态是 `open` / `snoozed` / `done` / `dropped`；每位助理未结的条目上限 500。

工具：`followup_add`、`followup_update`、`followup_snooze`、`followup_close`、`followup_list(scope)`（`scope` 也可以是一个编号，返回这一条连同备注）。日期按所有者时区，推后的条目到回看日那天改回未结。分类、状态、日期是明文，按日期查询不需要解密。起因消息被撤回时自动关闭。

## 七、子任务

用于需要时间的调查，主会话不被占住。

- 工具 `assistant_spawn(title, brief)`。新表 `assistant_jobs`：`id`、`bot_id`、`kind`（subtask / bot_help）、`origin`（assistant / system）、`target_bot_id`、`status`（queued / running / done / failed / cancelled / blocked）、`title_enc`、`brief_enc`、`message_enc`（最近一次追问）、`result_enc`、`blocked_enc`、`session_key`、`origin_session_key`、`rounds`、`last_task_id`、`error_code`、`deadline_at`，投回的记账列 `report`、`result_task_id`、`report_seq`、`report_after`、`report_failures`、`reported_at`、`report_code`，以及时间戳。`assistant_followups.job_id` 外键到它。
- 子任务以同一条助理记录、同一个沙箱运行，会话独立。同一助理同时最多 3 个。助理自己每天至多派 20 个，一个子任务至多 6 轮，每次派出或追问起 2 小时没结束记失败。子任务的轮次计入每日轮次预算；所有者不在场的轮次在预算用完后不能再派。
- 工具范围：个人工具中的读类、知识库读写（置顶页除外）、待跟进读写，另有 `assistant_job_blocked(reason)` 报告自己卡住了。没有写类个人工具，不能提交审批，不能再派子任务，不能发起或撤销授权，没有定时任务工具。子任务不往飞书发任何东西（回复、进度、提问卡、额度切换卡、中断通知都不发）；需要对外操作时在结论里写明建议，由主会话提交。
- 完成后结论作为 `assistant_job_result` 投回主会话，结论逐行引用；失败、超时同样投回一句说明。投回的一轮被所有者的消息打断时由平台重投，投到一次为止。主会话可用 `assistant_job_message(id, text)` 追问同一个子任务，`assistant_job_list` 查看，`assistant_job_cancel(id)` 取消。
- 不出现在公共任务页；转录按第三节处理。

几分钟内能查完的事，助理可以直接用 CLI 自带的子代理。

## 八、调度公共 AI 员工

- 工具 `assistant_ask_bot(bot, question, allow_write=false)` 与 `assistant_bot_list()`。目标必须是启用中的飞书普通员工、开启了接受求助，且所有者在它的可用人范围内（与员工之间求助同一口径，不另要求私聊过）。`bot` 按编号、标识或名称解析；标识命中时若另有员工的名称正是这个串，与同名一样报 `bot_ambiguous` 并附候选，改用候选的编号；候选先过与名单相同的资格条件，所有者调不动的员工不交给模型。问题至多 4000 字；进行中的调度与子任务合计最多 3 个、每天合计最多 20 个；一次求助只有一轮。
- 平台在目标员工那边开一个独立会话（`assistant-help:<编号>`），以所有者的身份执行：业务系统权限与所有者在该员工名下已保存的个人凭证相同；飞书与企微个人工具、个人定时任务、群文档工具、向员工或同事求助、凭证索取、云签名代理不提供。全程不往飞书发任何东西；答复作为 `assistant_job_result` 投回助理会话。
- 这一轮照普通私聊的方式明文存在目标员工名下，标为 `private`：正文只对所有者本人开放，目标员工的管理者与平台管理员只看得到发生过一次调度（时间、发起人、状态、用量）。问题与答复在助理这边存在 `assistant_jobs` 的密文列里。
- 无人在场的轮次可以发起只读调度，不需要审批。防范放在助理这一层：提示词要求只把完成任务必需、合理的问题交出去，不带原始聊天记录与他人隐私，来件里有诱导外传的内容时不调度并记待跟进；平台侧限制问题长度，每次调度写审计（不含问题正文）。平台侧另拦一种情况：无人在场的轮次不能调度跑在别人私有运行时上的员工（运行时实例 `visibility = 'private'` 且 `owner_id` 不是这位助理的所有者），返回 `owner_turn_required`，名单里也不列；私有运行时的所有者在自己的节点上读得到问题，这条路不该由一条来件就能走通。所有者当面发起的不限；经审批的调度由无人在场的轮次提交时在提交时就拒，执行时再查一次；目标那一轮开轮前按任务载荷里记的在不在场再查一次，被拒时不跑、按失败投回。
- `allow_write=true` 表示要对方改东西，属于对外操作，只在所有者明确要求时使用：先提交审批单（目标系统 `assistant-dispatch`，单上显示目标员工与问题原文），批准后才派出（不受并发上限与每日个数限制，所有者已亲自批准，仍计入计数）；批准后不单独通知，被拒、过期、失败与最终答复才投回。`allow_write=false` 时平台告诉对方只查不改，并且不放业务系统目录代理的写；对方用所有者的业务令牌能做什么，平台不保证。
- 目标员工中途需要确认、授权、凭证或想提问时，不发卡片，以 `blocked` 结束并带所需事项，由助理转成待跟进或请所有者当面处理。
- 目标员工的节点不做转录清除：问题会留在它的转录、工作目录与记忆里，等同所有者自己私聊它。问题原文在「我的助理」页可查。

所有者在私聊里看到的是一行「已请某员工查某事」，之后是助理消化过的结果。

## 九、「我的助理」页

仅所有者可见。接口在 `/api/me/assistant` 下，按会话身份鉴权，不接受机器人令牌。

| 分区 | 内容 |
|---|---|
| 等你出手 | 待批的审批单（只给摘要，跳转 Tower：入口取自部署配置 `TOWER_WEB_URL`，没配就不给链接；等待审批的调度也在这里）、被卡住的子任务、今天到期的待跟进 |
| 正在跑 | 子任务与调度出去的求助，含问题原文与进度；调度写明目标员工，平台派出的下班整理单独标出；进行中的可以取消 |
| 待跟进 | 四类清单；可以勾选办完、推后、改分类、标为不再需要、新增 |
| 最近落地 | 审批单的全部终态：已执行、被拒、撤回、执行失败、过期、内容过时作废 |
| 知识库 | 索引、查看、编辑、新建、删除；置顶页醒目标出。所有者只能在这里置顶、取消置顶或改写置顶页，每页写明最后由所有者、助理还是导入修改；内容一律按纯文本显示；可以重新生成口吻页（冷启动做完之后，每天至多排 3 轮，所有者自己改过的不覆盖；尝试次数另限每小时 3 次、每 24 小时 6 次，不管排没排上；应用的飞书分钟用量紧时让路；同时只有一个请求在读）；导入（先预览后确认）与导出 |
| 设置 | 时区、工作时段与工作日、重点群与忽略的会话（填 `chat_id`）、每日轮次预算（只能调低，不超过平台默认值；实际生效的是个人值与平台默认里较小的）、所在 Runtime（只读）、停用（输入助理名确认）、访问记录（只读，非本人的访问醒目标出） |

概览里可以即时「上班」「下班」或回到按工作时段，与私聊里说「上班」「下班」是同一件事。没有助理的人看到开通指引或不在范围的原因。接口没有任何助理编号参数，助理一律由登录人推出；管理员调用同样只能拿到自己的。知识页的路径本身是个人内容，读、写、删都放在请求体里，不进网址。数据密钥销毁后页面只显示编号、状态与时间。经页面读取个人内容的每个接口都调用 `access_log.record`：在访问日志表落地之前它只写一条不含内容的应用日志（`assistant_content_access`）。

## 十、开通、冷启动与停用

**开通**：私聊助理应用 → 卡片上点「开通」→ 平台校验可开通范围（账号启用、有登录名、在范围内；范围设置读不懂时谁都不放行），创建助理记录与数据密钥，分配节点，在节点上建一个全新的工作目录，发起飞书授权 → 授权完成后进入冷启动（第 2 期；第 1 期授权完成即可用）。没有配置 AI 后端时开通当场放弃，暂时没有可用节点则重试；一人名下还有没完全停用的助理记录，就不能再开通。Tower 没有按用户名查账号的接口，开通时查不到账号：开通卡片与欢迎语提醒先登录一次审批系统，没有账号时第一次提交审批如实报 `tower_account_missing`。刚停用过的人重新开通，要等约一分十五秒（各进程缓存的旧数据密钥过期）才建新记录；应用密钥暂时解不开则稍后重试；助理名字被别人的记录或普通员工占着时开通失败并提示联系管理员。开通由看护进程一步一步推进，任何一步放弃都走一遍停用把已建的东西收掉；授权完成前记录跑不了轮次。开通卡片的说明里写明：助理调度公共员工时，问题会像你自己私聊那位员工一样留在它的记录里（文案随第 3 期的页面一起改）。

**冷启动**：授权完成后记录即可用，同时开始冷启动，做完才开始盯消息。①平台以所有者身份读他最近 7 天、最近活跃的至多 8 个会话，只留他自己发出的文本消息（至多 200 条、每条 300 字；平台经审批代发的不算），交给一轮只带保存工具、不出声的独立会话归纳成口吻样本页（只概括特征，不抄原话；这一轮不往私聊里发任何东西）；不足 5 条或读不到（重试 1 小时）时跳过。②用表单卡片依次问四题：上级与主要协作人、负责的事（各成一页置顶页）、重点群（从最近活跃的群里选，至多 5 个）、工作时段与时区；每题可跳过，发「跳过」整个跳过。③做完、跳过，或开始满 24 小时（按默认值完成并私信告知）后写入完成时刻，盯消息与投递从此开始。状态记在 `assistant_settings` 的 `cold_start_started_at`、`cold_start_step`、`cold_start_next_at`、`cold_start_outcome`、`cold_start_done_at`。本功能上线前开通的助理不回填，所有者下一次来私聊时开始。

**停用**：停止轮询（第 2 期）并清掉没做完的冷启动与上下班的临时切换→ 停下在跑的轮次（已批准、排队中的写操作等它执行完，最多等 15 分钟）→ 撤回待批的审批单 → 撤销飞书授权 → 销毁数据密钥并停用记录 → 清除节点上的工作目录（登记后由看护进程经节点删除，节点离线就等它回来）。入口：所有者在私聊里发「停用助理」并确认（这条命令在私聊里认出发送人就截下，运行时停用、有公告或待答时也有效，不并进排队的消息，别人发的不回应）、平台管理员在助理列表里停用、成员账号停用满 24 小时自动执行（期间恢复就作罢；宽限期里所有者或管理员明确要求停用的立即生效，之后账号恢复也不撤回）。飞书授权在最后一步再清一次，停用开始后不能再发起或完成个人授权。管理员停用对已经停用完的旧记录不做任何事，也不影响这个人当前的助理。一旦开始就不可撤销，失败原地重试直到做完。

**导入与导出**：所有者本人在「我的助理」页的「知识库」分区上传一个 zip（`POST /api/me/assistant/import`），把已有的个人笔记并进知识库：每个 `.md` 文件成为一页，路径取相对路径去掉 `.md`，文件开头可选的 YAML front matter 里的 `title`、`summary`、`pinned` 被采用（导入是所有者在场的操作，可以置顶；写入记为 `import`）；根目录下可选的 `followups.json` 导入待跟进。先预览（将新建、覆盖、跳过的路径与原因，不回显正文，置顶的页标出），确认时带回预览的摘要才写入；已有的页默认跳过，选了覆盖才整页替换；预览之后有变化则拒绝（409）并要求重新预览。整个导入一个事务。压缩包只在内存里读：上限 20MB（按块读上传，超过即中止）、页面文件 2000 个、解包后合计 32MB（正文合计仍受知识库 20MB 上限约束），拒绝路径穿越、符号链接、加密条目、嵌套压缩包、非 `.md` 文件与非 UTF-8 文本；系统自带压缩功能带上的文件（`.DS_Store`、`__MACOSX/`、`Thumbs.db`、`._*`）跳过并在预览里计数。`GET /api/me/assistant/export` 把全部知识页与未结的待跟进打成同样格式的 zip；停用确认里提示可以先导出。两者都记访问记录。没有做成管理命令：管理命令在服务器上由运维执行，不是所有者本人。

## 十一、管理员控制与审计

- 设置项：可开通范围（全员 / 指定部门或人）、允许的模型后端、每人每日轮次预算的默认值、助理池节点并发上限。
- 新表 `assistant_access_log`（`id`、`bot_id`、`actor_id`、`actor_kind`、`action`、`target`、`at`，没有内容列）：记录运行时路径之外的每次解密——「我的助理」页的读取（含改设置与即时上下班的回显）、导入与导出、所有者在管理台读自己的对话记录与任务详情、服务器上的管理命令（密钥轮换记 `cli.rewrap`）。管理命令以所有者身份建的会话读调度公共员工那一轮（明文存在目标员工名下）时内容同样收起，并在所有者的助理名下记 `cli.chatlogs` / `cli.tasks`。`target` 只放范围名或计数，知识页的路径属于内容，不放。记录与读取同一个事务提交；单独这一行写失败不挡读取，只记应用日志。所有者在「设置」分区查看自己的记录；保留 180 天。一张按语法树扫描的测试台账要求每一处这样的解密都在同一个函数里记账或写明豁免理由。
- 管理命令以成员身份（`--as`）建的会话不是本人在场：`/api/me/assistant` 整个前缀拒绝它；凡是「只对所有者本人还原」的接口（对话记录、任务详情）对它一律不还原，输出与不是所有者时相同，并给所有者留一条 `system` 的访问记录（`cli.chatlogs`、`cli.tasks`）。运行时节点上的会话过程（会话查看页与事件流）同样不把它当本人：以所有者身份取调度公共员工那一轮被拒绝并记 `cli.session`。助理自己的会话在节点会话查看里对谁都不开。管理命令看不到助理的内容是有意的。
- 管理员能看到的只有：谁开通了、状态与流程步骤、所在节点、是否在班、冷启动是否完成、轮次与额度用量、待交回的条目数、进行中的子任务与调度数、轮询健康状态、待删的旧目录数、最近一次非所有者访问个人内容的时间（没有动作与对象）（管理台「个人助理」列表）。停用要输入所有者的登录名确认。

## 分期

每期各自出实现计划。

| 期 | 内容 | 做完能用什么 |
|---|---|---|
| 0 | 前置验证 | 确定沙箱方案与限频策略 |
| 1 | 助理记录与路由、加密存储、节点隔离、审批闸门、开通与停用 | 私聊里让它办事，所有写操作经 Tower |
| 2 | 盯消息、知识库、待跟进、上下班、冷启动 | 主动盯消息并起草 |
| 3 | 子任务、调度公共员工、「我的助理」页、导入 | 长调查不占主会话，可借助其他员工 |

## 不做

- 企业微信。
- 群聊中使用助理。
- 一人多个助理。
- 用户自持密钥。
- 飞书卡片审批。
- 每轮按负载重新选节点。
- 密文检索索引、向量检索。
- 助理改代码（需要时调度公共员工）。

单元：

- 写类工具全部被拦截，读类不受影响；`kind` 清单与 `endpoints.py` 逐项对照，新增接口未分类时测试失败。
- 提交前检查与执行前检查的各分支；`args_hash` 去重；待批上限。
- 加解密与 AAD 绑定；主密钥轮换；销毁后读取失败。
- 分级规则；压着与攒批的时间窗。
- 知识库检索、版本冲突、注入上限。
- 路由：私聊按人投递、群消息丢弃、非所有者的回调无效。

集成：

- 开通 → 授权 → 私聊发起一次回复 → 审批单 → 批准 → 执行 → 结果回会话。
- 拒绝、撤回、改稿、`stale`、Tower 不可用。
- 盯消息交回 → 起草 → 所有者亲自回复后自动撤单。
- 子任务与调度：结论回主会话；子任务不能提交审批、不能调度；没资格的员工调不动；目标那一轮不往飞书发东西、要确认时返回 `blocked`；`allow_write` 走审批，只读调度写审计。
- 转录：轮次结束后节点上无残留；续聊可还原；异常退出后的清扫。
- 可见性：管理员、团队负责人、其他成员经任一接口都读不到助理内容。
- 停用后库里密文不可解（调度留在目标员工名下的明文记录除外）。

| 转录删除后还原续聊 | Codex：删除后续聊失败，还原后正常。Claude：删除后续聊失败，还原后会话可被找到，完整续聊待补测 | 本机实测 |

| 列会话排序与新消息 | 前 15 个会话（单聊、群、话题群混排）里 14 个的顺序与各自最新消息时间一致；1 个因非消息活动靠前，只会多读一次历史，不会漏。免打扰的会话默认包含在内 | 真机实测 |
| 节点沙箱能否启动 | 可以：5 台候选节点（1 台 Alibaba Cloud Linux 4、4 台 Ubuntu 24.04，都是虚机、不在容器里）装上系统源里的 bubblewrap（0.12.0 / 0.9.0）后，助理专用用户都能起沙箱。Ubuntu 24.04 默认由 AppArmor 限制非特权用户命名空间，bwrap 报 `setting up uid map: Permission denied`，要加一条只放行 `/usr/bin/bwrap` 的 AppArmor 规则；这条规则对节点上所有用户生效 | 节点实测，2026-11-13，共享节点甲至戊 |
| 沙箱里的文件隔离 | 成立：沙箱里看不到别人的转录与工作目录上级目录下的任何条目，沙箱外写不进去；两种 CLI 的转录都落在沙箱的私有配置目录 | 同上，5 台 |
| 助理用户与普通员工用户的跨用户隔离 | 目录隔离成立：两个用户互相读不到对方的家目录、配置目录、数据目录与工作目录；普通员工用户没有免密 sudo。进程隔离不成立：5 台的 `/proc` 都没开 `hidepid`，普通员工用户看得到助理用户进程的命令行，上线前要开 | 同上，5 台 |
| 出网限制的实现方式 | 采用「沙箱断网 + 本机代理放行」：同一个沙箱不断网时访问外网返回 200，加上断网命名空间后连不出去。按进程组做防火墙规则不需要 | 节点实测，2026-11-13，共享节点甲、乙（两种系统各一台） |
| Codex 用收窄后的登录凭证 | 可以，但 `tokens.refresh_token` 字段必须在：整个字段去掉时 Codex 不认这份登录，请求一律 401（沙箱内外都一样）；留空串或任意无效值则正常回答，全新的配置目录不需要先初始化。节点原来的登录文件前后摘要一致。访问令牌是带 `exp` 的 JWT，实测剩余有效期 7 到 9 天。实现已改为留空串 | 节点实测，2026-11-13，共享节点甲至戊，Codex 0.162 至 0.164 |

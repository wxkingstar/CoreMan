# 个人助理

## 背景

成员希望有一个以本人飞书身份工作的助理：盯消息、起草回复、改文档、处理审批、跟进待办，并主动推进事情。所有对外有影响的操作先经本人审批。

平台已有的基础：飞书个人授权（约 110 个 `feishu_*` 工具，含以本人身份读写消息），飞书私聊记录仅本人可见，私有 Runtime，群写入的「暂存参数 → 本人确认 → 平台原样执行 → 续接」通路，Tower 审批的回调与对账。

缺的部分：

1. 私聊里的个人写操作只有提示词约束，工具被调用就执行。
2. 飞书没有用户身份的消息事件，平台收不到「别人发给本人」的消息。
3. 对话、流式输出、原始事件在库里是明文；节点上的 CLI 转录是明文；记忆和工作目录是文件。
4. 没有「一轮里派出独立会话再收回结果」的做法。

## 已定决策

| 决策 | 结论 |
|---|---|
| 范围 | 只做飞书；人人可开通，由管理员控制可开通范围 |
| 入口 | 只接私聊；群消息在网关丢弃，被拉进群时退群并私信说明 |
| 飞书应用 | 全员共用一个应用，平台里每人一条助理记录；路由层支持多个应用 |
| 数量 | 同一飞书企业内一人只有一个生效的助理 |
| 审批 | 全部走 Tower，不做飞书卡片审批 |
| Runtime | 默认用共享的助理池；可绑定本人的私有 Runtime |
| 个人数据 | 聊天记录、个人知识、待跟进、审批参数全部加密入库；密钥只在平台侧，不下发给 Agent |
| 工作目录 | 每人一个，只放规则与经验总结，不放个人信息 |
| 协作 | 可派平台子任务，可调度公共 AI 员工；结果回助理会话，不往飞书发消息 |

## 原则

1. **对外有影响的操作由平台拦截**，不靠模型自觉。批准后平台按暂存参数原样执行。
2. **密钥不离开平台。** 助理每天读别人发来的消息，这些是不可信输入；Agent 进程里不能有能解密历史数据或直接调用飞书的东西。
3. **明文在节点上只存在于一轮运行期间。**
4. **没事不花模型额度。** 盯消息由平台轮询，不经模型。

## 威胁模型

| 对象 | 能否看到个人内容 | 依据 |
|---|---|---|
| 其他成员、团队负责人、平台管理员（经管理台和接口） | 不能 | 接口只对本人放行 |
| 只拿到数据库或备份的人 | 不能 | 内容列是密文 |
| 同一节点上的其他 AI 员工 | 不能 | 沙箱隔离，转录每轮清除 |
| 被注入的助理自身 | 不能外传 | 写操作过审批，沙箱限制出网 |
| 同时拿到数据库和平台主密钥的人 | 能 | 不防；记录解密访问审计 |
| 共享节点的 root，在该助理运行的那一轮里 | 能 | 不防；需要时绑定私有 Runtime |
| 审批系统的管理员 | 取决于审批系统 | 见「前置验证」 |

要防后三类需要用户自持密钥，那样无法无人值守盯消息，不做。

## 一、助理记录与入口路由

### 数据模型

- `bots` 加列 `kind`（`standard` / `assistant`，默认 `standard`）与 `owner_id`。部分唯一索引：`kind='assistant' AND enabled` 时 `(owner_id, 租户)` 唯一。
- 新表 `assistant_apps`：登记可承载助理的飞书应用（应用凭证、名称、适用范围）。助理记录引用其中一条，不再各自保存应用凭证。
- 飞书个人授权沿用 `feishu_personal_grants`（主键仍是机器人 × 人），档位固定为 `all`。

### 路由

网关对 `assistant_apps` 里的应用：

- 私聊消息按发送人找到其助理记录并投递；没有记录时发「开通个人助理」卡片。
- 群消息一律丢弃，不入库。收到进群事件时退群，并私信拉群的人说明这个应用只支持私聊。
- 卡片回调只认记录的所有者。

### 对助理记录关闭的能力

成员与协作者、可用人白名单（固定为所有者一人）、群聊旁听、调度员、接受其他员工求助、API 驱动任务、开发模式、文件记忆、规则文档备份、公共任务页、管理台里他人查看工作目录。这些在服务端按 `kind` 拒绝，管理台不显示对应设置。

## 二、加密与存储

### 密钥

- 新表 `assistant_keys`：`user_id`、`dek_enc`、`created_at`、`destroyed_at`。每人一把 256 位数据密钥，用平台主密钥包裹（沿用 `core/crypto.py`，带 kid，AAD 绑定 `user_id`）。
- 内容用数据密钥做 AES-256-GCM 加密，AAD 为「表名:行主键」，防止密文被挪到别的行。
- 主密钥轮换只需重新包裹数据密钥，不重写内容。
- 数据密钥只在平台进程内解开，不写入任务载荷、环境变量或日志。

### 加密范围

对 `kind='assistant'` 的记录，下列内容列写入前加密、读取时解密：

| 表 | 列 |
|---|---|
| `inbound_events` | 事件载荷 |
| `tasks` | 载荷、结果 |
| `task_streams` | 思考与正文 |
| `outbox` | 出站载荷（网关发送前解密） |
| `chat_logs` | 消息与回复正文 |
| 本文新增的表 | 标了 `_enc` 的列 |

状态、时间、类型、长度等元数据保持明文，供调度与排障使用。运维接口照旧只返回元数据。

### 销毁

停用助理或成员离职时销毁其数据密钥（清空 `dek_enc`，记 `destroyed_at`）。密文随即永久不可读，不需要逐表删除；过期清理任务照常回收行。

## 三、节点隔离

### 沙箱

助理的每一轮在沙箱里运行：

- 可读写：本人的工作目录、本轮临时目录、本助理的 CLI 配置目录。
- 只读：CLI 程序与模型登录凭证。
- 不可见：节点上其他目录，包括其他员工的工作目录与转录。
- 出网只放行平台地址与模型接口地址，其余连接拒绝。查外部资料走平台提供的工具。
- 环境变量里只有本轮能力令牌（沿用现有做法），没有数据密钥、飞书令牌或应用凭证。

沙箱方案与独立系统用户方案二选一，由「前置验证」的实测结果决定；独立系统用户时编号由平台统一分配，保证在共享存储上跨节点一致。

### 转录

- 一轮结束后，节点守护进程把本轮的 CLI 转录经 TLS 上传平台，平台用数据密钥加密后存入新表 `assistant_transcripts`（`bot_id`、`session_id`、`blob_enc`、`size`、`updated_at`），节点上随即删除。
- 续聊前由平台解密下发，守护进程还原到沙箱内，再启动 CLI。
- 单个转录上限 50MB，超过时结束该会话，下一轮开新会话。
- 守护进程启动时清扫助理目录下遗留的转录（上一轮异常退出）：上传后删除。
- 本轮临时目录在轮次结束时删除。下载的文档、附件只放这里。

### 工作目录

分配方式与普通员工相同，一条记录一个目录。内容限于规则、经验总结和技能。安全提示词写明：工作目录不放人名、聊天内容、审批内容和任何个人信息，这些一律用知识库工具保存。

### Runtime 分配

- `relay_servers` 加列 `assistant_pool`。开通时在池内选助理数最少的在线节点。
- 所有者可改绑到自己的私有 Runtime（沿用 `relay_policy` 的可选规则）。私有节点离线时助理暂停并私信所有者，不回落到池。
- 迁移只需改绑：个人状态在库里，工作目录在共享存储或按现有换运行时流程复制。
- 每个节点对助理轮次设并发上限，超出的排队。每人设每日轮次预算，用完后非紧急事项攒到次日，并私信告知。

## 四、审批闸门

### 拦截

个人工具按 `endpoints.py` 的 `kind` 分为读与写。对助理记录，写类工具（发送、编辑、撤回、表情、建群拉人、文档与表格写入、评论、权限、审批决定、日程、任务、邮件）不执行，改为：

1. 参数加密存入新表 `assistant_approvals`。
2. 向 Tower 提交一张审批单：发起人和审批人都是所有者，目标系统为 `feishu-personal`。
3. 返回 `{status: "pending_approval", approval_id}`。本轮不结束，助理可以继续处理别的事。

`assistant_approvals`：`id`、`bot_id`、`tool`、`args_enc`、`args_hash`、`channel`、`chat_id`、`anchor_message_id`、`thread_id`、`topic`、`status`（pending / approved / rejected / withdrawn / stale / executed / failed / expired）、`reason_enc`、`result_enc`、`external_id`、`created_at`、`decided_at`、`executed_at`。这张表同时是审批流水。

唯一不经审批的写操作是在待回复的那条消息上打「处理中」表情及其撤销，由专门的工具提供，表情类型和目标消息由平台限定。

### 审批单内容

- 由平台按工具模板从实际参数生成：渠道（私聊 / 群聊 / 文档 / 审批 / 日程 / 任务 / 邮件）、对象（人名或群名）、被回复的原话、要发出的正文或改动摘要。
- 助理可附两段说明：背景、做过的调研。它们显示在正文之下，并标明是助理撰写。
- 一张单只装一件事。同一内容发给多人可以合并，最多 10 条。

### 提交前检查

消息类必须带 `chat_id` 与锚点（回复的那条，或助理读到的最后一条）。提交时平台重新读取会话：

- 锚点之后所有者本人已经发言：拒绝，要求读完最新消息后重写。
- 锚点之后对方又发了消息：拒绝，同上。
- 同一 `args_hash` 已有待批或已执行的单：返回已有的那张。

同时待批上限 10 张。

### 决定之后

- 决定经 Tower 回调送达，丢失时由现有对账补上。
- **批准**：平台再做一次锚点检查，通过后按暂存参数原样执行，结果上报 Tower，并作为事件投回助理会话。锚点检查不通过时不执行，状态记为 `stale`，交回助理重新起草。
- **拒绝**：理由投回助理会话，由它按理由改稿重提或放弃。
- **执行失败**：错误投回助理会话。不自动重试，改好后重新提交。
- 批准时附带的备注只作备注，平台不解析，执行内容不变。

### 改稿与撤回

工具 `approval_revise(id, 新参数)`、`approval_withdraw(id, reason)`、`approval_list(status, topic)`。只有 `pending` 的单可以改稿或撤回。盯消息进程在下列情况自动撤回并通知助理：所有者已在该会话亲自回复、对方撤回了被回复的消息。

Tower 不可用时提交失败，写操作不执行。所有者在 Tower 没有对应账号时不能开通助理。

## 五、盯消息

### 轮询

平台侧进程，不经模型。新表 `assistant_watch`（`bot_id`、`cursor`、`interval`、`next_poll_at`、`state`、`last_error`）。在所有者的工作时段内每 60 秒用本人令牌拉一次新消息；遇到限频按退避延长间隔，多个助理的轮询时刻错开。

拉到的消息只在内存里分级，交回的条目写入 `assistant_inbox`（`bot_id`、`level`、`chat_id`、`message_id`、`thread_id`、`summary_enc`、`status`、`created_at`）。

### 分级

| 级别 | 条件 | 处理 |
|---|---|---|
| 立即交回 | 私聊；群里 @ 本人；审批被拒或执行失败；所有者标记的重点群里的消息 | 立刻投递 |
| 攒批 | 其他群里真人的消息；新出现的飞书审批待办 | 满 5 分钟投递一次 |
| 压着 | 所有者 10 分钟内在该会话亲自发过言 | 他停下满 10 分钟仍未回才投递 |
| 忽略 | 所有者自己发的；群里没 @ 他的机器人消息；所有者设为忽略的会话 | 不投递 |

同一轮还负责：待批单的锚点变化、对方撤回、「处理中」表情挂了 4 小时未回的提醒、当天到期的待跟进。

### 投递与会话

- 投递是在助理会话里创建一个任务，类型 `assistant_handover`，载荷是本批条目。`feishu_personal/policy.py` 允许的任务类型加入它和 `assistant_job_result`、`assistant_approval_result`。
- 助理会话与所有者的私聊共用一个会话键，所有者在私聊里说的话和交回事项在同一个上下文。
- 会话每天换新（按所有者时区）。跨天的连续性靠待跟进和知识库，不靠会话上下文。
- 上一轮未结束时新的交回事项排队，合并进下一轮。

### 上下班

默认按所有者设置的工作时段自动开始和停止。私聊里说「上班」「下班」可临时切换。下班时派一个子任务做当天的编译：把当天的进展、被拒与执行的审批整理进知识库。

## 六、个人知识与待跟进

### 知识库

新表 `assistant_pages`：`id`、`bot_id`、`path_hmac`（唯一，路径的 HMAC）、`path_enc`、`title_enc`、`summary_enc`、`body_enc`、`pinned`、`version`、`updated_at`。

工具（平台 MCP，解密在平台侧）：

| 工具 | 作用 |
|---|---|
| `notes_index` | 返回全部页面的路径、标题、一句话摘要 |
| `notes_read(path)` | 读一页 |
| `notes_search(query)` | 把该助理的全部页面解密到内存，按关键词匹配排序，返回命中片段 |
| `notes_write(path, body, summary)` | 新建或整页替换，带 `version` 乐观锁 |
| `notes_delete(path)` | 删除一页 |

- `pinned` 的页面（口吻、判断原则、被拒复盘归纳出的规则）和索引每轮注入提示词，放在稳定前缀之后，避免破坏提示词缓存。注入总量设上限，超出时只注入索引。
- 上限 2000 页、合计 20MB，足够在内存里检索，不做密文索引和向量检索。
- 组织方式沿用「索引 + 页面 + 链接 + 定期编译」：人、项目、决策、日志各自成页，下班时编译。

### 待跟进

新表 `assistant_followups`：`id`、`bot_id`、`seq`（每个助理内递增，显示为 F012）、`category`（等我决定 / 我答应 / 等别人 / 提醒我）、`status`、`review_on`、`due_on`、`origin_message_id`、`job_id`、`title_enc`、`notes_enc`、时间戳。

工具：`followup_add`、`followup_update`、`followup_snooze`、`followup_close`、`followup_list(scope)`。分类、状态、日期是明文，按日期查询不需要解密。起因消息被撤回时自动关闭。

## 七、子任务

用于需要时间的调查，主会话不被占住。

- 工具 `assistant_spawn(title, brief)`。新表 `assistant_jobs`：`id`、`bot_id`、`kind`（subtask / bot_help）、`target_bot_id`、`status`、`title_enc`、`brief_enc`、`result_enc`、`session_key`、时间戳。
- 子任务以同一条助理记录、同一个沙箱运行，会话独立。同一助理同时最多 3 个。
- 工具范围：个人工具中的读类、知识库读写、待跟进读写。没有写类个人工具，不能提交审批，不能再派子任务。需要对外操作时在结论里写明建议，由主会话提交。
- 完成后结论作为 `assistant_job_result` 投回主会话。主会话可用 `assistant_job_message(id, text)` 追问同一个子任务。
- 不出现在公共任务页；转录按第三节处理。

几分钟内能查完的事，助理可以直接用 CLI 自带的子代理。

## 八、调度公共 AI 员工

- 工具 `assistant_ask_bot(bot, question, allow_write=false)`。目标员工必须开启接受求助，且所有者本人有权使用它。
- 平台在目标员工那边开一个独立会话，以所有者的身份执行，权限与所有者私聊它时相同。答复不发到飞书，作为 `assistant_job_result` 投回助理会话。
- 这一轮在目标员工的记录里标为 `private`，仅所有者可见，内容用所有者的数据密钥加密。
- `allow_write=true` 表示要对方改东西，属于对外操作：先提交审批单（目标系统 `assistant-dispatch`，单上显示问题原文），批准后才派出。
- 目标员工中途需要确认、授权或凭证时，返回 `blocked` 和所需事项，由助理转成待跟进或审批单。
- 目标员工的节点不做转录清除。提示词要求问题只带完成任务必需的信息，不带原始聊天记录；问题原文在「我的助理」页可查。

所有者在私聊里看到的是一行「已请某员工查某事」，之后是助理消化过的结果。

## 九、「我的助理」页

仅所有者可见。接口在 `/api/me/assistant` 下，按会话身份鉴权，不接受机器人令牌。

| 分区 | 内容 |
|---|---|
| 等你出手 | 待批的审批单（跳转 Tower）、被卡住的子任务、今天到期的待跟进 |
| 正在跑 | 子任务与调度出去的求助，含问题原文与进度 |
| 待跟进 | 四类清单 |
| 最近落地 | 已执行、被拒、撤回的审批单 |
| 设置 | 工作时段、重点群与忽略的会话、Runtime、停用 |

## 十、开通、冷启动与停用

**开通**：私聊助理应用 → 卡片上点「开通」→ 平台校验可开通范围与 Tower 账号，创建助理记录与数据密钥，分配节点，发起飞书授权 → 授权完成后进入冷启动。

**冷启动**：拉取所有者最近发出的消息生成口吻样本页；用选择卡问几个问题（上级与主要协作人、负责的事、重点群、工作时段）；写入对应页面。完成前只响应私聊，不开始盯消息。

**停用**：停止轮询 → 撤回待批的审批单 → 撤销飞书授权 → 清除节点上的工作目录 → 销毁数据密钥 → 停用记录。成员离职时自动执行。

**导入**：提供管理命令，把一个目录里的 Markdown 页面与待跟进清单导入某人的知识库，供已有个人笔记的成员迁入。由所有者本人执行。

## 十一、管理员控制与审计

- 设置项：可开通范围（全员 / 指定部门或人）、允许的模型后端、每人每日轮次预算的默认值、助理池节点并发上限。
- 新表 `assistant_access_log`：记录运行时路径之外的每次解密（页面读取、导出、管理命令），含操作人、对象、时间。所有者可在页面上查看自己的记录。
- 管理员能看到的只有：谁开通了、所在节点、轮次与额度用量、轮询健康状态。

## 分期

每期各自出实现计划。

| 期 | 内容 | 做完能用什么 |
|---|---|---|
| 0 | 前置验证 | 确定沙箱方案与限频策略 |
| 1 | 助理记录与路由、加密存储、节点隔离、审批闸门、开通与停用 | 私聊里让它办事，所有写操作经 Tower |
| 2 | 盯消息、知识库、待跟进、上下班、冷启动 | 主动盯消息并起草 |
| 3 | 子任务、调度公共员工、「我的助理」页、导入 | 长调查不占主会话，可借助其他员工 |

## 不做

- 企业微信。
- 群聊中使用助理。
- 一人多个助理。
- 用户自持密钥。
- 飞书卡片审批。
- 每轮按负载重新选节点。
- 密文检索索引、向量检索。
- 助理改代码（需要时调度公共员工）。

## 测试

单元：

- 写类工具全部被拦截，读类不受影响；`kind` 清单与 `endpoints.py` 逐项对照，新增接口未分类时测试失败。
- 提交前检查与执行前检查的各分支；`args_hash` 去重；待批上限。
- 加解密与 AAD 绑定；主密钥轮换；销毁后读取失败。
- 分级规则；压着与攒批的时间窗。
- 知识库检索、版本冲突、注入上限。
- 路由：私聊按人投递、群消息丢弃、非所有者的回调无效。

集成：

- 开通 → 授权 → 私聊发起一次回复 → 审批单 → 批准 → 执行 → 结果回会话。
- 拒绝、撤回、改稿、`stale`、Tower 不可用。
- 盯消息交回 → 起草 → 所有者亲自回复后自动撤单。
- 子任务与调度：结论回主会话；子任务不能提交审批；`allow_write` 走审批。
- 转录：轮次结束后节点上无残留；续聊可还原；异常退出后的清扫。
- 可见性：管理员、团队负责人、其他成员经任一接口都读不到助理内容。
- 停用后库里密文不可解。

## 前置验证

写第 1 期实现计划前完成，结果不符时调整对应章节。

1. 飞书读消息接口（搜索、会话历史）的限频，按应用还是按用户计。
2. 以用户身份能否列出单聊会话，还是只能经搜索取得 `chat_id`。
3. 两种 CLI 在沙箱里能否运行；转录删除后由平台还原能否正常续聊；模型登录凭证只读挂载是否可用。
4. Tower：按人映射发起人与审批人是否可行；审批单是否只有审批人可见；请求体是否可以不送比对模型；审批人是否都能收到推送。
5. 一个飞书应用对应多条助理记录时，网关的连接数与内存变化。
6. 长时间无调用时飞书刷新令牌的过期行为。

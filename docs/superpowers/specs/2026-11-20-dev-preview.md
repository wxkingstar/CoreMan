# 开发模式：开发环境预览

## 背景

开发模式的 AI 员工改完代码，要推分支、跑完整 CI/CD、发到测试环境才能看到效果。很多改动只动了一个逻辑点或一句文案，时间几乎都花在打包和发布上。

Runtime 节点（云上的 Linux 和办公室的 Mac）内存充足，可以直接在节点上跑 Docker。本设计让开发模式的 AI 员工在自己的 worktree 里把改动的服务跑起来，通过一个开发域名交给用户点开验证；用户确认没问题，再推分支走测试环境做集成验证。

目标：

- **用户无感**：用户只看到 AI 员工回复里的一条链接，点开就能测。启动、端口、域名、回收都由 AI 员工和节点完成。
- **多项目、多分支并行**：每个 worktree 一个独立的开发地址，同一节点上多个 worktree 互不干扰。
- **Linux 和 macOS 节点同等支持**，办公室的 Mac 是主力。
- **维护成本低**：搭好之后不需要为每个预览改网关、DNS 或证书，节点侧全部自动回收。

## 环境约定

开发环境（下文用 `*.dev.example.com` 指代开发域名）是一个独立的环境，规则如下：

| 项 | 约定 |
|---|---|
| 数据库 | 直连测试环境的数据库，用**读写但不能改表结构**的账号（只有 SELECT / INSERT / UPDATE / DELETE） |
| 缓存 | 直连测试环境的 Redis，沿用测试环境的 key 前缀（和共享的数据库保持一致） |
| 登录 | 用各系统默认的登录方式，不接单点登录。SSO 相关的改动直接去测试或仿真环境验证 |
| 表结构变更 | 迁移先单独走一次测试环境发布；之后不改表结构的迭代在开发环境验证，通过后再走测试环境做集成验证 |
| 异步任务 | MQ 消费者、定时任务默认关闭，避免抢测试环境的消息或重复写共享数据库 |
| 其他服务 | 调用测试环境的服务地址，不在本地起依赖服务 |
| 访问控制 | 和测试环境同一个网关，沿用测试环境的 IP 白名单 |

## 整体结构

```
浏览器 → https://<项目>-<id>.dev.example.com
  → 测试环境的 API 网关（通配证书 *.dev.example.com，IP 白名单）
  → 通配路由 → 隧道服务端 frps（测试环境集群里一个 Deployment）
  → 隧道 → 节点上的隧道客户端 frpc
  → 127.0.0.1:<该 worktree 的入口端口> → worktree 的 compose（入口 Caddy → 前端 / 接口）
```

- **复用测试环境的 API 网关**，只加两条路由：`*.dev.example.com`（预览流量）和 `tunnel.dev.example.com`（节点建隧道），都指向 frps。以后新增预览不用再动网关。
- **隧道用 frp**（Apache-2.0）。节点只需要主动连出，不用开入站端口，云节点和办公室的 Mac 走同一条路。frp 自带按子域名分发（`subDomainHost`），不用自己写路由。
- **frpc 经网关连 frps**：`transport.protocol = "wss"`，网关终结 TLS 后以 WebSocket 转给 frps 的 `bindPort`。这样不用为隧道单独买负载均衡，隧道连接也受网关的白名单保护。
- **关闭 TCP 多路复用**（frps 和 frpc 都设 `transport.tcpMux = false`），每个用户连接走一条独立的工作连接。办公室到机房是长距离链路，单条连接吞吐低，多条并行才能把前端资源拉得动。
- 隧道服务端与客户端共用一个 token。所有节点都是自己的机器，第一期不做按节点限制子域名。

## 地址规则

- 主机名：`<项目>-<id>.dev.example.com`，只有一级子域，通配证书才覆盖得到。
- `<项目>`：取 `origin` 远端地址的仓库名，转成小写，非字母数字的字符换成 `-`，最长 30 个字符。
- `<id>`：`sha1(节点 id + worktree 绝对路径)` 的前 6 位十六进制。同一 worktree 在同一节点上地址固定，AI 员工每轮改完刷新的还是同一个链接。
- 员工换到另一台节点后地址会变，属于预期行为。

## 仓库约定：`dev/` 目录

每个业务仓库在根目录放一个 `dev/` 目录，由 AI 员工自己生成和维护：

| 文件 | 内容 |
|---|---|
| `dev/compose.yaml` | 只包含本仓库自己的服务，加一个入口服务（Caddy）。入口监听 `127.0.0.1:${DEV_PORT}`，按测试环境 Ingress 的规则分流 `/`、`/api` 等路径。服务尽量复用仓库已有的 Dockerfile |
| `dev/Caddyfile` | 入口的路径分流 |
| `dev/env.example` | 列出需要哪些环境变量（数据库、Redis、其他服务地址），不含任何值 |
| `dev/README.md`（可选） | 健康检查路径、需要关掉的消费者和定时任务、已知限制 |

要求：

- 所有服务都写 `healthcheck`，`docker compose up --wait` 能判断启动完成。
- 环境变量从节点下发的环境文件读取（`env_file: ${DEV_ENV_FILE}`），仓库里不出现任何凭据。某个仓库独有的值（如它自己的加密密钥）由管理员放进节点环境文件同目录的 `projects/<仓库名>.env`，`coreman-dev up` 拼进同一份文件。
- 启动时自动建表、改表的逻辑（如 ORM 的 AutoMigrate）在开发配置里关掉。账号本来也没有 DDL 权限，开着会启动失败。
- MQ 消费者、定时任务默认关闭。
- 镜像要能在 arm64 和 amd64 上原生构建，基础镜像选多架构的。
- 以开发模式运行，目标是改代码几秒内可见：源码挂进容器（`../` 相对 `dev/`），后端用自带的热重载（如 `uvicorn --reload`、Go 的 `air`），前端用 dev server（如 Vite）而不是打包后的静态文件；依赖留在镜像或具名卷里，不被挂载遮住。只有依赖、Dockerfile、`dev/` 或环境变量变了才重新 `coreman-dev up`。
- 文件监听一律开轮询（如 `WATCHFILES_FORCE_POLLING=true`、Vite `server.watch.usePolling`）：实测 macOS 上 colima（vz + virtiofs）的挂载目录不会把宿主机的文件变化事件传进容器。
- 页面经入口以 `${DEV_URL}`（HTTPS）访问：dev server 要放行这个主机名（Vite `server.allowedHosts`），热更新的 WebSocket 要走 443 回连（Vite `server.hmr.clientPort: 443`）。

## 节点侧

### 配置

节点 `config.json` 新增一段，没有这一段就表示本节点不支持开发环境预览：

```json
"dev_preview": {
  "domain": "dev.example.com",
  "tunnel_server": "tunnel.dev.example.com",
  "token_file": "~/.local/share/coreman-runtime/dev-preview/token",
  "env_file": "~/.local/share/coreman-runtime/dev-preview/env",
  "port_range": [42000, 42999],
  "max_previews": 8
}
```

心跳里上报 `dev_preview: 1`，平台据此决定是否在提示词里加入开发环境规则。

### `coreman-dev` 命令

随 Runtime 发布，放在 AI 员工的 PATH 里。在 worktree 根目录执行：

| 子命令 | 做什么 |
|---|---|
| `up` | 分配或复用端口 → `docker compose -p <项目>-<id> -f dev/compose.yaml up -d --build --force-recreate --wait` → 写入 frpc 代理配置并热重载 → 经网关访问一次健康检查路径 → 输出开发地址。失败时输出出错的那一步和最后几十行容器日志 |
| `down` | 停止容器，注销子域名，保留镜像缓存 |
| `status` | 本 worktree 的地址、容器状态、最近一次启动时间 |
| `logs [服务]` | 查看容器日志 |
| `list` | 本节点上所有预览（项目、分支、地址、状态） |

端口分配记录在 `dev-preview/ports.json` 里（worktree 路径 → 端口），文件锁保护。

### frpc 托管

- Runtime Daemon 把 frpc 当作子进程托管：异常退出就重启，断线由 frpc 自己重连。
- 主配置用 `includes` 引入 `dev-preview/proxies/*.toml`，每个 worktree 一个文件；`coreman-dev up/down` 增删文件后执行 `frpc reload`。
- frpc 固定版本：守护进程首次启动时按平台从 frp 的 GitHub 发布页下载，核对代码里写死的 sha256 后放进数据目录；升级 frpc 就是随 Runtime 版本改版本号和校验值。节点不能访问 GitHub 时用 `frpc_path` 指定自带的 frpc。

### 自动回收

| 时机 | 动作 |
|---|---|
| worktree 闲置超过 24 小时（沿用开发模式每轮刷新 worktree 修改时间的做法） | `down`，保留镜像，下一轮改动时 AI 员工再 `up` |
| worktree 被清理（开发模式的定期清理） | `docker compose down -v --rmi local`，删除代理文件和端口记录 |
| 本节点运行中的预览数达到 `max_previews` | `up` 时先停掉闲置最久的一个 |
| 每天一次 | `docker image prune` 和 `docker builder prune`，只清 72 小时前的 |

回收都挂在开发模式已有的 30 分钟定期检查里，不另起定时任务。

### Linux 节点

- 安装 docker-ce 和 compose 插件，运行 AI 员工的系统用户加入 `docker` 组。
- `docker` 组等同于节点 root，只给开发节点开，跑个人助理沙箱的系统用户不加。
- 云节点和测试资源在同一个内网，直连。

### macOS 节点

- Docker 用 colima（MIT，免费，兼容 compose），由 launchd 以运行 AI 员工的用户身份常驻。虚拟机资源按机器配置，例如 128G 内存的机器给 8 核、48G、200G 磁盘。amd64 专属镜像用 `--vz-rosetta` 转译。
- 端口：colima 把容器端口转发到宿主机的 127.0.0.1，frpc 连的是回环地址，不受 macOS「本地网络」隐私限制影响。
- **到测试资源的网络**：办公室 Mac 经公司 VPN 进测试环境内网。要确认两件事：
  1. 容器里发出的连接能走宿主机的 VPN。colima 默认的用户态网络由宿主机进程代发连接，预期可以；如果不行，就在宿主机上用 launchd 跑一个 TCP 中转，容器经 `host.lima.internal` 访问。
  2. 数据库、Redis 的内网域名在 Mac 上能解析。解析不了时，环境文件里直接写内网 IP。
- 调用测试环境的其他服务：Mac 上的环境文件写测试环境的公网域名（走网关和白名单），云节点写内网域名。两类节点各用一份环境文件。
- **速度预期**：办公室到机房每次往返约 80 毫秒，查库多的接口会明显变慢。开发环境用来验证功能，不用来测性能。前端用构建好的产物（压缩后）预览，不用开发服务器，避免几百个小文件走隧道。

## 提示词

节点上报 `dev_preview: 1` 且员工开了开发模式时，开发模式说明里加一段（实现时写成英文，和现有 `DEV_MODE_RULE` 一致）：

1. 改完第一处代码就在 worktree 根目录执行 `coreman-dev up`，不先跑检查；之后的改动靠热更新生效。
2. 仓库没有 `dev/` 时，参照仓库的 Dockerfile 和测试环境的配置生成一份，随本次改动一起提交。`dev/` 跟不上代码时顺手修好。
3. 地址可用后（或之后每次改完、热更新生效后），用最快的方式确认改动生效（取页面、调接口，只有界面改动且取页面看不出来时才开浏览器），然后马上把地址回复给用户，再做别的检查。失败就先修，不把打不开的链接给用户。
4. 开发环境里只跑和改动相关的检查（涉及模块的测试、改动文件的类型检查或 lint、对着地址的简短端到端脚本），放在回复地址之后；不每轮跑完整检查和长时间的测试，仓库自己要求每次改动都跑的也挪到推送前。检查在本轮里前台跑完，不放后台：后台任务在回复之后结束会再触发一轮，用户的新消息只能排队。
5. 用户在开发环境确认没问题（或明确要求）后，先跑项目的完整检查、修好失败项，再推送分支、开 PR，走测试环境。完整检查在 PR 这一环把关。
6. 改动涉及表结构变更时，不用开发环境：告诉用户迁移需要先走一次测试环境发布，迁移上线后，后续不改表结构的迭代再回到开发环境验证。
7. 改动涉及单点登录时，不用开发环境，告诉用户需要到测试或仿真环境验证。
8. 不在开发环境里打开 MQ 消费者和定时任务，不改环境文件里的数据库账号。

第 5 条改变了现有规则第 1 条「跑项目自带的检查」和第 2 条「改动就绪后推送分支、开 PR」的时机：节点支持开发环境预览时，先预览、后推送，完整检查挪到推送前。

（2026-11-21 实测：环境起来约 1 分 40 秒、热更新不到 1 秒，但员工每轮跑完整检查加浏览器自测，回复要 5～8 分钟，于是改成上面的做法。）

## 平台改动

- 节点：`dev_preview` 配置、`coreman-dev` 命令、frpc 托管、回收挂进定期检查、心跳上报能力。
- 提示词：按节点能力追加上面一段。
- 不做：平台侧的预览记录和管理页（链接由 AI 员工直接写在回复里）、按节点限制子域名、预览访问统计。

## 维护成本

| 环节 | 搭好之后 |
|---|---|
| 网关、DNS、证书 | 一次性配置；证书由证书管理组件自动续期 |
| frps | 无状态，单副本，挂了由集群拉起；故障只影响预览，不影响业务 |
| frpc、端口、容器回收 | Runtime Daemon 自动处理，随节点升级更新 |
| 凭据 | 节点环境文件由部署方统一下发，只在改密码时更新 |
| 仓库 `dev/` 配置 | AI 员工生成和维护 |

## 实施步骤

1. **基础设施**（部署方，不改 CoreMan）：
   - 开发域名解析、通配证书、frps 和两条网关路由；
   - 测试数据库建只有 DML 权限的账号；
   - Linux 节点装 Docker，Mac 节点装 colima；
   - 手工跑通一个仓库，并逐项验证下面的「待验证」。
2. **节点与提示词**（CoreMan）：`coreman-dev`、frpc 托管、回收、心跳能力、提示词。
3. **试点**：选一个仓库，在一台 Linux 节点和一台 Mac 节点上，各让 AI 员工从零生成 `dev/` 并完成一次「改动 → 预览 → 确认 → PR」。

## 待验证

| 项 | 怎么验证 | 不通时的做法 |
|---|---|---|
| 网关把 `wss` 隧道转给 frps | 在一台节点上用 frpc 连 `tunnel.dev.example.com`，注册一个子域名并访问 | 给 frps 单独开一个四层入口 |
| Mac 容器经宿主机 VPN 访问测试数据库和 Redis | colima 容器里连数据库端口 | 宿主机 TCP 中转 |
| Mac 上数据库内网域名能解析 | 宿主机和容器里各解析一次 | 环境文件写 IP |
| 办公室出口在网关白名单里 | Mac 上 `coreman-dev up` 的健康检查一步 | 把办公室出口加进白名单 |
| 办公室到机房的预览速度 | 打开一个典型页面，看首屏时间 | 前端用压缩产物；查库多的接口接受变慢 |

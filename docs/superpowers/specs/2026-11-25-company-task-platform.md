# 全公司任务平台：人与 Agent 之间的任务流转

状态：第一期已上线（迁移 0129）；第二期（迁移 0130）、第三期（迁移 0131）已实现。第三期的账本镜像覆盖 API 任务、两类求助与人工求助（escalations）：新建只看最近 7 天，没结束的一直跟到结束，只读；私聊来源（含人工求助）只记谁找谁与状态，不复制内容。承接 `2026-11-02-group-dispatcher-and-work-tasks.md`（调度员与任务跟进），本稿取代其中 §5.2 确认、§6 任务模型、§8 任务页。

## 1. 目标与已定

把「任务」从群调度员的附属记录，变成全公司的任务账本：人和 Agent 都能发起、执行、转交任务，流转过程全部留痕。

三种流转都要支持：

- **人 → Agent**：人建任务交给 AI 员工；人类执行人把手上的任务再转给 AI 员工做。
- **Agent → 人**：Agent 需要人回答、确认或去做一件事。
- **Agent → Agent**：Agent 拆出子任务交给别的 AI 员工，或把整件事转交出去。

已定（2026-11-25）：

1. 走统一账本（方案 B）：现有的 AI 互相求助、向同事求助、API 任务、群调度任务都记成任务或子任务。
2. 人类侧的界面是 CoreMan 网页加飞书卡片，不同步飞书任务。
3. 这一期所有登录成员都能看全部任务，包括 Agent 那一层。个人助理的跟进（`assistant_followups`）只属于所有者，这一期不并入。
4. **给人看的和给 Agent 看的是两条线，从建任务到收尾全程分开**（§3）。

## 2. 基本概念

**任务**：一件事，编号 `T-<序号>`，沿用现有序列。

**参与方**：每个角色都可以是人（`users`）或 AI 员工（`bots`），统一记为 `actor = {type: human|bot, id}`。

| 角色 | 说明 |
|---|---|
| 发起人 | 提出这件事的人或 Agent。Agent 拆出的子任务，发起人就是那个 Agent。 |
| 代表人（principal） | Agent 以谁的身份做事：业务令牌、白名单、个人工具都按这个人。任务链上的 Agent 都沿用同一个代表人，权限不会被放大。人建的任务，代表人是建的人；人把任务转给 Agent，代表人是转交的人。 |
| 执行人 | 现在手上拿着这件事的人或 Agent，同一时刻只有一个。 |
| 验收人 | 执行人交付后由谁判断是否做好。可以为空（不验收）。 |
| 关注人 | 只接收关键通知。 |

**父子任务**：`parent_id` 表示拆解关系，`root_id` 指向整条任务链的根。父任务等子任务时处于「等待中」。

## 3. 两条线（核心）

每个对象、每条事件都同时有两份内容：给人看的一份短而直接，给 Agent 看的一份尽量完整。**两份分开存储、分开撰写，不从一份截取另一份。**

### 3.1 给人看（人话线）

原则：直击要害，只说结论和需要谁做什么；要人做事时，只问一个最精炼的问题。

| 内容 | 规则 |
|---|---|
| 标题 | ≤30 字，动词开头，说清要什么结果 |
| 现状 | 一句话，≤60 字：「已完成：…」「卡在：…」「等李四确认：…」 |
| 时间线每条 | 一行，≤80 字，只写对人有意义的变化（交接、提问、交付、验收、取消） |
| 要人做的事（ask） | 只有一个问题，≤60 字；能给选项就给选项（≤4 个，每个 ≤20 字），最后固定附一个「其他」，点了出输入框让人补充；没有选项时直接给输入框；可附一行「为什么问你」（≤40 字）。交互见 §3.4 |
| 交付 | 一句话结果，加产出物链接（PR、文件、文档） |

平台负责校验：超长就退回给写的 Agent，让它压缩后重交，不由平台截断。运行中的细节（工具调用、查询过程、重试）不进人话线；Agent 每跑一轮，人话线上只合并成「运行中」「已交付」这类状态变化。

### 3.2 给 Agent 看（细节线）

原则：面面俱到，让接手的 Agent 不用回头问人。

| 内容 | 结构 |
|---|---|
| 任务简报 `brief` | 目标、背景、已知事实与数据、约束（权限、不能动的东西、截止）、验收标准、上游任务的要求、相关任务记要、原始消息与群聊上下文、附件 |
| 进展 `detail` | 每轮的输出全文、调用了哪些工具和得到的要点、查询语句与结果摘要、错误原文、对应的会话链接 |
| 交接包 `handoff` | 执行人变更时必须附上：已做了什么、结论、还剩什么、产出在哪、踩过的坑、建议下一步、相关会话 |
| 答复原文 | 人回答的问题，原样进入细节线，带问题、选项与回答者 |
| 记要 `digest` | 收尾时写：背景、结论、关键数据或产出位置、做了哪些决定、遗留问题，≤800 字，带日期；以后的相关任务会带上它作背景 |

### 3.3 两条线如何贯穿

| 环节 | 人话线 | 细节线 |
|---|---|---|
| 人建任务 | 人只填标题和一句话（可选截止、执行人） | 平台自动补齐：原消息、群聊上下文、相关任务记要、附件；指派给 Agent 时，再由它在开工前把简报整理成结构化形式，写回 `brief` |
| Agent 建任务 | 必须写标题和一句话现状 | 必须写完整简报；缺验收标准或背景时，工具直接拒绝 |
| 转交 | 「张三 → 运维：原因」一行 | 交接包（必填） |
| Agent 问人 | 卡片：一个问题加选项 | 完整背景、为什么卡住、各选项的后果 |
| 人回答 | 「李四：选 A」 | 答复原文，接上细节续跑 |
| 交付 | 一句话结果加链接 | 全部输出、产出清单、记要 |
| 验收不通过 | 「退回：一句理由」 | 理由原文加验收人补充说明，作为下一轮的输入 |

**谁读哪条线：**

- 人：网页和卡片默认只显示人话线。任务详情页上，给 Agent 看的内容默认折叠，所有人都能展开：任务级有一个「Agent 细节」区（简报、交接包、记要、运行记录、完整汇报），时间线上每条事件也能单独展开它的细节。展开状态按浏览器记住。
- Agent：拿到任务时，本轮块带上**细节线全文**，再附上人话线时间线作索引；`get_task` 工具返回两条线。
- 人在网页上写的评论同时进两条线；Agent 写的进展只写进细节线，需要人知道的事要单独写一行人话。

### 3.4 选项交互：网页和飞书卡片同步

凡是要人做选择的地方（Agent 的提问、验收通过或退回、派给你的接受或转交），都用同一个「待选择事项」对象，同时出现在两处：

- **任务页**：详情页顶部和「我的任务」列表行内直接显示问题和选项按钮，点了就提交。
- **飞书卡片**：同一时刻推一张卡片给要回答的人，卡片里的按钮点了就提交，不用跳网页。

规则：

- 每个选项是一个按钮；最后固定有「其他」，点开是输入框，人可以写自己的答案或补充说明，提交后作为答复原文。
- 选了某个选项也能顺带补一句话（选项按钮旁的可选输入），补充内容一并进细节线。
- 两处任一处先提交即生效，另一处随即更新成「已由 xx 选择：A」，不能再改；需要改答案时在任务页评论，评论同样进细节线并唤醒 Agent。
- 只有被问的人能回答，代表人和平台管理员可以代答（标注代答）。
- 答复进人话线一行（「李四：选 A」），完整答复（问题、全部选项、选中项、补充文字、回答者、渠道）进细节线，交给 Agent 续跑。

## 4. 状态

任务状态是给人看的，和 Agent 的单轮运行分开。

| 状态 | 含义 | 人话里显示什么 |
|---|---|---|
| `todo` | 待开始：人类执行人还没接受；或人派给 Agent 的任务还没被领取（§5.1） | 待 xx 开始 / 待 xx 领取 |
| `in_progress` | 进行中 | xx 处理中 |
| `waiting` | 等待中，`waiting_on` 记录在等什么：某人答复、子任务、排队、额度、外部条件 | 等 xx：一句话 |
| `review` | 待验收 | 等 xx 验收 |
| `done` | 完成 | 已完成：结果 |
| `cancelled` | 取消，或执行人做不了且没人接手 | 已取消：原因 |
| `shadow` | 调度试运行的记录（沿用现有） | 不在默认列表显示 |

旧状态迁移（迁移 `0129`；发布期间上一版本还会写旧状态，这一版检查约束两套都允许，下一版去掉旧的）：`pending` 迁为 `todo`，`queued` 迁为 `waiting`（排队）；`running` 迁为 `in_progress`；`awaiting_confirmation` 迁为 `waiting`（等发起人）；`unfinished`、`needs_human` 迁为 `waiting`（等发起人决定）；其余不变。

**Agent 运行记录**放进新表 `work_task_runs`：每跑一轮记一条（执行员工、代表人、队列任务 id、会话键、开始和结束时间、结果、耗时、费用）。人话线只显示「运行中 3 分钟」，详情放在细节线。

**验收默认规则**（沿用「写操作要人确认」的原则）：

- Agent 执行的、人发起的任务：做完后进入 `review`，由代表人验收。建任务时可以勾选「不需要验收」；调度员判定不跟进的一问一答，默认不验收。
- Agent 发起的子任务：由父任务的 Agent 自动验收（它收到结果后自己判断），不打扰人。
- 人执行的任务：默认不验收，发起人可以指定验收人。
- 验收退回：任务回到原执行人并重开，退回理由进细节线；Agent 被退回两次后，转给代表人决定。

## 5. 三种流转

### 5.1 人 → Agent

入口：

- **网页新建**：填标题、一句话，执行人选 AI 员工，可选截止和验收。
- **人类执行人转给 AI**：任务详情页和飞书卡片上的「交给 AI 员工」按钮。选员工、补一句要求；代表人改为自己，验收人默认也是自己。
- **群调度员**：沿用现有流程。
- **API**：沿用 `api_tasks`，每次调用登记成一个任务（§7）。

**指派后不自动开工。** 人派给 Agent 的任务进入这个 Agent 的待办（`todo`，人话显示「待 xx 领取」），等触发后才开始。触发方式：

1. **人在对话里叫它干活**：在飞书里对这个 AI 员工说「看看有什么活」「把 T-12 做了」。Agent 调 `list_my_tasks` 列出自己的待办（人话线：编号、标题、谁派的、截止），按人的意思调 `start_task` 开工。
2. **Agent 自己配定时任务拉取**：用现有定时任务能力配一条，例如「每天 9 点领取我的待办并开始」。定时执行时挂上同样的工具，由 Agent 自己按优先级和截止挑选、开工。

开工后：平台按任务的**代表人**身份排一轮 chat 任务（不是按叫它干活的人，也不是按定时任务的创建人），会话键沿用 `work:<编号>`，本轮块带细节线全文。触发者记进事件。叫它干活的那段对话里只回一行「已开始 T-12、T-15」，结果走任务：进验收、推卡片给验收人。之后追加要求、验收退回、答复与子任务回流，都自动续进同一个会话，不用再触发。

例外：群调度员派的任务、API 任务、Agent 拆出的子任务，都是自动开工（发起时就有人或 Agent 在等结果）。验收退回后也自动重跑。

**开工方式要让人一眼看出来。** 任务记 `start_mode`：`auto`（自动开工）或 `manual`（等人叫）。页面和卡片上这样显示：

- 列表行和详情页标题旁放一个标签：「自动开工」（灰）或「等你叫它开工」（醒目色，只在还没领取时显示，领取后变成「已领取」）。
- 详情页顶部的「现在」一行，对 `manual` 且未领取的任务直接写明怎么驱动：「运维员工还没开工。在飞书里对它说『做 T-12』，或给它配定时领取。」附一个「复制指令」按钮。
- 「我的任务」的「待我处理」栏，把我派给 Agent、还没被领取的任务也列进来，提醒我去驱动。
- `auto` 的任务不出现驱动提示；排队或等额度时，「现在」一行写明在等什么，人不用操作。

### 5.2 Agent → 人

Agent 用工具（§6）发起，分两种：

- **问一句**（`ask_human`）：需要人的判断、确认或内部信息。登记成功后，平台建一个执行人是这个人的子任务，父任务转为 `waiting`，Agent 结束这一轮。人答复后，答复原文进父任务的细节线，平台在原会话续跑父任务。这就是现有「向同事求助」的流程，改为挂到任务上。
- **派一件事**（`create_task` 指定人类执行人）：需要人线下去做，例如审批、联系客户、在某系统里点一下。父任务可以选择等它完成，也可以不等。

触达：每次 Agent 把事交给人（提问、派活、请验收），都同步推一张飞书卡片，同时出现在对方「我的任务」的待我处理里。有待选择事项时，直接在卡片里点选或填写「其他」完成（§3.4）。群任务在原群 @ 对方，否则私聊（沿用现有求助的规则）。卡片以发起这件事的 AI 员工身份发出，对方能看出是谁在问。

限制：每人同时最多 5 条待答复的问题（沿用现有上限）；同一条任务链最多问人 3 次；24 小时提醒一次，72 小时没回应时父任务转为 `waiting`，等代表人处理。人可以「转给别人」或「交给 AI 员工」，不能直接丢弃，拒绝时要写一句理由。

### 5.3 Agent → Agent

- **拆子任务**（`create_task` 指定 AI 员工）：子任务以同一个代表人的身份执行，有自己的会话 `work:<子编号>`。父 Agent 写完简报后可以继续做别的；调用 `wait_for` 后结束本轮，所有它在等的子任务都结束时，平台把子任务的结果（细节线的交付与记要）放进父会话续跑。
- **回到主任务做完整汇报**：子任务一律回到父任务。子任务交付时，结果（人话一句加细节线全部输出、产出、记要）挂到父任务。父 Agent 等的子任务都结束后续跑，汇总后对主任务调 `submit_result`，必须带完整汇报 `report`：
  - 总结论；
  - 每个子任务：谁做的、结论、关键数据、产出位置、是否通过父 Agent 的验收；
  - 父 Agent 自己做的部分；
  - 未解决的问题和风险；
  - 建议下一步。

  完整汇报放在细节线，任务页「Agent 细节」里单独一栏「完整汇报」；人话线只写一句总结论加「3 个子任务已完成」，验收人点开就能看汇报。子任务失败或被取消，也要在汇报里写明，不能略过。
- **整件转交**（`handoff_task`）：执行人换成另一个 AI 员工，交接包必填；原执行人退出这件事。
- **限制**：任务链深度不超过 3 层；一个任务同时进行中的子任务不超过 5 个；不能派给自己，也不能派给链上已有的执行人（防止循环）；对方要开着 `accept_bot_help`，代表人也要能使用对方；个人助理不能当执行人，也不能发起转交（沿用现有限制）。
- 和现有 AI 互相求助的关系：求助是「拆子任务并等待」的特例。第三期把 `request_collaboration` 改为内部调用 `create_task` 加 `wait_for`，账本挂到任务上。

### 5.4 人 → 人

网页建任务指派给同事，或转交给同事。卡片通知对方，对方可以接受、交给 AI 员工、转给别人或拒绝。

## 6. Agent 的任务工具

新增 MCP 工具组 `work_tasks`。执行任务的回合挂全部工具；普通对话和定时执行只挂领取类（`list_my_tasks`、`start_task`）和只读类（`get_task`、`search_tasks`）。工具只能操作调用者自己执行的任务及其子任务。

| 工具 | 作用 | 必填（人话 / 细节） |
|---|---|---|
| `list_my_tasks(status)` | 列出派给自己的任务，默认待领取的，按优先级和截止排序 | 无 |
| `start_task(codes)` | 领取并开工（每个任务各排一轮，独立会话） | 无 |
| `get_task(code)` | 读一个任务的两条线 | 无 |
| `search_tasks(query)` | 找相关任务（标题、记要），返回摘要 | 无 |
| `create_task` | 建子任务，或建一个独立的新任务 | 人话：`title`、`summary`；细节：`brief`（结构见 §3.2），以及 `assignee`、`wait`、`review` |
| `ask_human` | 问人一个问题 | 人话：`question`、`options` 或 `free_text`、`why`；细节：`context` |
| `handoff_task` | 整件转交 | 人话：`reason`（一行）；细节：`handoff` 交接包 |
| `update_task` | 写进展 | 细节：`detail`；人话 `human_text` 选填，只在人需要知道时写 |
| `submit_result` | 交付 | 人话：`result`（一句话）、`artifacts`；细节：`output`、`digest`；有子任务时 `report`（完整汇报，§5.3）必填 |
| `wait_for()` | 结束本轮，等这件事所有没结果的子任务和问题 | 无 |
| `find_assignees(query)` | 找能接子任务的 AI 员工和同事 | 无 |

人话字段超长或缺必填项时，返回 `stop=false` 和修改要求，让 Agent 改了重交（和现有协作工具的约定一致）。没调 `submit_result` 就结束的一轮，平台按现有逻辑从回复里推断结果，并在任务页标「缺记要」。

## 7. 统一账本：现有功能怎么挂进来

| 现有 | 改成 | 期数 |
|---|---|---|
| 群调度任务 | 原本就是任务，迁移状态即可 | 一 |
| `human_collaborations`（向同事求助） | 每次求助是一个人类执行人的子任务，求助表加 `work_task_id` | 二 |
| `bot_collaborations`（AI 互相求助） | 每次求助是一个 AI 执行人的子任务，求助表加 `work_task_id` | 三 |
| `api_tasks` | 每次调用一个任务，发起人是调用方代表的员工，来源记 API | 三 |
| `escalations`（定时任务的人工求助） | 同向同事求助 | 三 |

原表保留，继续作为执行细节（触达、续跑、过期），任务表只记「一件事」和两条线。接入前的历史数据不回填。

没有任务包着的普通对话（一问一答）不建任务，保持现状。员工自己判断「这件事要花几分钟以上或有后果」时，可以用 `create_task` 登记给自己（原设计稿 §9.3）。

## 8. 数据模型

`work_tasks` 新增或修改的列：

| 列 | 说明 |
|---|---|
| `source` | `dispatch` / `web` / `agent` / `api` / `collaboration` |
| `requester_type`, `requester_bot_id` | 发起人可以是 Agent（现有 `requester_user_id` 保留） |
| `principal_user_id` | 代表人 |
| `assignee_type`, `assignee_user_id` | 执行人可以是人（现有 `assignee_bot_id` 保留） |
| `reviewer_type`, `reviewer_user_id`, `reviewer_bot_id` | 验收人，可以为空 |
| `root_id`, `depth` | 任务链 |
| `waiting_on` | JSONB：`{kind: human|task|queue|quota|external, ref, human_text}` |
| `ask` | JSONB：当前要人回答的问题（人话线），回答后清空、答复进事件 |
| `start_mode`, `claimed_at` | 开工方式 `auto` / `manual`；Agent 领取时间（§5.1） |
| `priority` | `normal` / `high` / `urgent` |
| `due_at` | 截止时间 |
| `platform`, `chat_id` | 改为可空（网页建的任务没有群） |
| `title`, `summary` | 人话线 |
| `brief`, `digest` | 细节线，结构化以后存 JSONB：`brief_doc`、`digest_doc`；保留旧的文本列做兼容 |

`work_task_events` 保留两层结构（`human_text` 和 `agent_detail`），`kind` 新增：`handoff`、`ask`、`answer`、`review_pass`、`review_reject`、`comment`、`artifact`、`subtask`。`human_text` 可以为空：只在细节线出现的事件不进人话时间线。

新表：

- `work_task_runs`：Agent 运行记录（§4）。
- `work_task_artifacts`：产出物（类型、标题、链接、哪一轮产生的）。
- `work_task_watchers`：关注人。

## 9. 人的界面

### 9.1 网页

- **「我的任务」首页**，分四栏：
  - 待我处理：我是执行人、我是验收人、有问题等我回答。
  - 我发起的。
  - 我关注的。
  - 全部。

  默认打开「待我处理」，每行一句话现状，问题直接在行内回答。
- **看板**：按状态分列，可以按群、执行人、发起人筛选。
- **详情页**：
  - 顶部一行「现在：等李四确认 xxx」加相应的按钮。
  - 下面是人话时间线和产出物。
  - 「Agent 细节」默认折叠：简报、每轮运行、交接包、记要、会话链接。
  - 任务链以树的形式显示父任务和子任务。
- **操作**：新建、指派、转交、交给 AI 员工、回答、验收通过或退回、评论、关注、取消、重开、改截止和优先级。谁能操作：发起人、代表人、执行人、验收人、平台管理员可以改；其他成员只能评论和关注。

### 9.2 飞书卡片

每张卡片正文最多 3 行，加按钮，再加「查看任务」链接。卡片按事件更新，不重复发新卡片。

| 卡片 | 发给谁 | 内容与按钮 |
|---|---|---|
| 派给你 | 人类执行人 | 标题、一句话、截止；按钮：接受、交给 AI 员工、转给别人、拒绝 |
| 有个问题 | 被问的人 | 一个问题，加选项按钮或输入框 |
| 待你验收 | 验收人 | 一句话结果、产出链接；按钮：通过、退回（带输入框） |
| 已完成 / 已取消 | 发起人、关注人 | 一句话结果 |
| 快到期 / 已超期 | 执行人 | 一句话；按钮：延期、交给 AI 员工 |

发送通道：

- 和某个 AI 员工有关的卡片，用这个员工的飞书应用发。
- 网页上建的、人到人的任务，用系统设置里指定的「任务通知员工」发。
- 对方不在应用的可用范围内时，在任务页标「通知未送达」，并提示调整可用范围（沿用可用范围实时读写的能力）。

## 10. 分期

**第一期：人也能当执行人，两条线打底**

- 数据模型（§8，除 artifacts 外）、状态迁移、`work_task_runs`。
- 网页：「我的任务」、详情页（两条线分开展示）、新建、指派、转交、评论、验收通过或退回、取消、重开。
- 人 → 人、人 → Agent（网页指派、「交给 AI 员工」），代表人身份执行，验收默认规则。
- Agent 领取：`list_my_tasks`、`start_task`、`get_task` 三个工具先上，对话里叫它干活、定时任务拉取都能用（§5.1）。
- 待选择事项（§3.4）：网页行内选项和飞书卡片按钮同步，带「其他」输入；第一期用在派给你、待你验收两处。
- 飞书卡片：派给你、待你验收、已完成；任务通知员工设置。
- 群调度员迁到新状态，行为不变。

**第二期：Agent 的任务工具**

- MCP 工具组其余工具（§6），人话字段校验。
- Agent → 人（`ask_human`、派人做事）、Agent → Agent（子任务、`wait_for` 回流、主任务完整汇报、整件转交），以及各项限制。
- 「有个问题」卡片；产出物；向同事求助挂进任务。

**第三期：统一账本与运营**

- AI 互相求助、API 任务、定时任务的人工求助挂进来。
- 记要检索、自动带上相关任务。
- 截止提醒和超期卡片；统计（积压、交接次数、Agent 一次通过率、平均耗时）。

每期拆成若干 PR，逐个上线。

## 11. 风险

- **人话线写不精炼。** 平台校验长度并退回重写；提示词里给正反例；上线后抽查。
- **Agent 滥派任务打扰人。** 有问人次数、待答复数、链深度上限；问题卡片里写清「为什么问你」。
- **权限扩大。** 代表人贯穿整条链，Agent 之间转交不换身份；派给人的任务不附带 Agent 的业务令牌。
- **全员可见泄露数据。** 这一期按已定全员可见；细节线里可能有查询出的数据，之后要收紧时，按参与者加公开开关处理。
- **和现有协作的过期、续跑逻辑冲突。** 第二、三期挂接时原表逻辑不动，只加 `work_task_id` 和事件写入。

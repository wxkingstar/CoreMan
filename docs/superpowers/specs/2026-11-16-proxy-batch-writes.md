# 平台代理批量写操作

实现状态：已实现（迁移 `0112`），代码在 `coreman/core/systems_catalog/batch.py` 与 `coreman/runtime/worker/systems_batch_cards.py`，现行行为见 `docs/business-system-catalog.md`「批量写操作」。末尾「待定」的三项本期都没有做。实现后经过一轮审查，下面几处以现行文档为准：确认时先落库再复查；超时记为结果未知而不是失败；执行任务按段号认当前执行者，被接手的一段自行停下；刚发出的项等 120 秒宽限后才记结果未知。

## 背景

平台代理（`systems_call`）的写操作现在是：模型每调用一次暂存一项，本轮结束后发一张确认卡，提问人确认后平台逐条执行，遇到第一个失败就停下（见 [平台代理写操作确认卡](2026-11-14-proxy-write-confirmation.md)）。每批最多 50 项。

实际业务里常有一次改几百条的需求，例如按用户给的表格批量改价、批量改状态。业务系统没有批量接口时，50 项的上限迫使用户拆成很多轮，每轮重新确认一次。单纯把上限调高也解决不了：

1. **模型逐条调用。** 1000 项就要 1000 次工具调用，又慢又费 token，还会撞上运行时的轮数上限；数据也要模型逐字抄写一遍，容易抄错。
2. **确认卡放不下。** 卡片上限约 28 KB，按常见写法最多放 85～160 项。
3. **结果卡放不下。** 执行结果逐项列出，1000 行远超卡片上限，用户会看不到结果。
4. **暂存和执行的方式撑不住。** 整批加密存在一行里，每暂存一项就要整份解密、加密一次；执行在点确认的那个任务里一口气跑完，跑几十分钟期间既没有进度，中途重启也会停在一半。

## 目标

- 一次确认最多 1000 项写操作，模型只调用一次。
- 拆分、校验、暂存、执行都由平台完成；数据不经模型逐字转述。
- 确认卡显示总量、按字段聚合的统计和最多 50 项抽样预览，并提供全部明细的下载。
- 平台串行执行；某一项失败时继续执行其余项，最后汇总。
- 执行过程中卡片显示进度，提问人可以中途停止；进程重启后能接着跑，已发出的不重发。

## 非目标

- 不改变单项写操作的现有行为（每批 50 项、遇到失败就停）。
- 不支持带文件字段（`multipart/form-data`）的操作批量执行。
- 不支持无人能当场确认的轮次，包括个人助理无人在场时提交审批的那条路径：审批单正文上限 10000 字，放不下整批明细。
- 不对个人助理开放：助理的内容按所有者的数据密钥封存，逐项暂存的表不在那一层里。
- 不做并发执行，也不做跨操作的混合批次。

## 范围与限制

| 项目 | 规则 |
|---|---|
| 风险等级 | `write` 每批最多 1000 项；`destructive` 每批最多 50 项；`financial` 不代理；`read` 不能批量 |
| 每批操作数 | 只能是一个系统里的一个操作 |
| 每轮批次数 | 最多 1 批；与单项写操作分开，各发各的确认卡 |
| 能提交的轮次 | 与单项写操作的确认卡相同：飞书里提问人本人打字发来的消息所在的回合 |
| 权限 | 与单项写操作相同：员工对该系统开了「允许写入」，操作对提问人可见 |
| 代理调用预算 | 一次批量提交计 1 次；执行时的逐项调用不占模型这一轮的预算 |
| 数据文件 | JSON Lines，用现有代理上传接口上传，单个文件不超过 30 MB，本轮内有效 |

## 模型侧接口

`systems_call` 新增选填参数 `batch`，与 `path_params`、`query`、`body` 互斥：

```jsonc
systems_call(
  system = "shop",
  operation_id = "updateListing",
  batch = { "upload_id": "…" },
  note = {                       // 选填，整批的说明，只用于展示
    "impact": "…",
    "rollback": "…"
  }
)
```

数据文件每行一项：

```jsonc
{"path_params": {"id": "L1001"}, "body": {"price": 19.9}, "target": "挂牌 L1001", "before": {"price": 21.9}}
{"path_params": {"id": "L1002"}, "body": {"price": 29.9}, "target": "挂牌 L1002", "before": {"price": 35.0}}
```

- `path_params`、`query`、`body` 与单项调用的含义相同。
- `target`（对象的业务名称）和 `before`（修改前的值）选填，只用于展示，平台不核实。
- 典型做法：模型在运行环境里写一个脚本，把用户给的表格转成 JSON Lines，再按 `systems_describe` 给出的 curl 命令上传。数据从用户的文件到平台都不经过模型的输出。
- `systems_describe` 对 `write`、`destructive` 操作说明批量用法（文件格式、上限、上传命令）。提示词补一句：同一个操作要改多项时用 `batch`，不要逐条调用。

## 提交与校验

平台收到 `batch` 后，先做单项调用的全部检查（系统、操作可见、风险策略、允许写入、可确认的轮次），再逐行处理数据文件：

1. 文件必须是本轮本人上传、未过期的；按 UTF-8 逐行解析，空行跳过。
2. 每行用现有的 `build_request` 校验参数和请求体，与单项调用完全一致。
3. 完全相同的两行（`path_params`、`query`、`body` 都一样）视为错误。
4. 行数为 0，或超过该风险等级的上限，视为错误。

只要有一行出错，整批不暂存，返回 `invalid_batch`，列出前 20 个错误（行号 + 原因），让模型修正后重新提交。全部通过后：

- 每行生成自己的幂等键，加密后逐行写入新表 `system_batch_items`。
- 生成全部明细的 CSV 并存入对象存储，下载链接用于确认卡（见下文）。
- 返回 `pending_confirmation`，附总数和提示：本轮结束后发确认卡，告诉用户需要确认，不要说已经完成。

本轮已有一批时再次提交，返回 `batch_exists`。本轮失败、超时或被停止时，整批作废。

## 数据模型

批次本身沿用 `interaction_states`，新的 `kind = systems_batch`。`state` 里只放明文元数据：

```jsonc
{
  "origin_task_id": 123,
  "user_id": "…",
  "chat_id": "…",
  "chat_type": "p2p",
  "system": "shop",
  "operation_id": "updateListing",
  "risk": "write",
  "op_digest": "…",
  "count": 1000,
  "note": { "impact": "…", "rollback": "…" },   // 加密
  "summary": { … },                              // 聚合统计，加密，见下文
  "detail_object_id": "…",                       // 全部明细 CSV
  "sent": true,
  "progress": { "done": 420, "ok": 417, "failed": 3, "unknown": 0 }
}
```

新表 `system_batch_items`（迁移 `0112`）：

| 列 | 说明 |
|---|---|
| `batch_id` | 指向 `interaction_states.id`，级联删除 |
| `seq` | 行号，从 1 开始；与 `batch_id` 组成主键 |
| `request` | 加密的 `path_params`、`query`、`body`、`target`、`before`（AAD 含批次和行号） |
| `idempotency_key` | 暂存时生成 |
| `status` | `pending` / `sending` / `ok` / `http_error` / `unreachable` / `unknown` / `skipped` |
| `status_code` | 业务系统返回的 HTTP 状态码 |
| `brief` | 结果摘要，截断到 300 字，加密 |
| `finished_at` | 完成时间 |

暂存的数据与现有确认卡相同：第一次发卡后保留 24 小时；执行过的批次保留到执行结束后 24 小时，之后连同明细文件一起清掉。审计照旧：每项执行在 `system_calls` 里记一行，结局带前缀 `confirmed_`。

## 确认卡

一张卡由四部分组成，全部按暂存的请求渲染，纯文本：

```
请确认 1000 项操作                          [标题：操作名；含 destructive 为红色]
商品后台 · 修改挂牌价格

共 1000 项。以下按字段统计，并抽样预览 50 项，完整明细见下载。

【字段统计】（按请求体取值）
price：19.9（612 项）、29.9（301 项）、其他 41 种取值（87 项）
⚠️ 同一对象出现多次：L1203（2 次）、L1877（2 次）

【抽样预览 50 / 1000】
1. 挂牌 L1001  price：21.9 → 19.9
2. 挂牌 L1002  price：35.0 → 29.9
…

[下载全部明细（CSV）]
改动说明由 AI 整理，以明细中的请求为准。

[确认执行 1000 项]  [取消]
```

- **字段统计**：取请求体顶层字段（没有请求体时取查询参数），每个字段列出出现最多的 3 种取值及其项数，其余合并为「其他 N 种取值」。值单行显示，最长 80 字符。路径参数完全相同的项，作为「同一对象出现多次」列出来，最多 5 个。
- **抽样预览**：最多 50 项，按下面的顺序挑选，保证少数值不被多数值淹没：
  1. 每个字段的每种取值至少出现一次，出现次数少的取值优先；
  2. 「同一对象出现多次」的项；
  3. 剩下的名额按批次编号做种子随机抽取，重发卡片时抽到的一样。
  预览按行号排序，每项显示行号、`target`（没有时显示路径参数），以及 `before` → 请求体的改动，最多 3 个字段。卡片放不下时依次减少预览条数，总数、字段统计和下载链接始终保留。
- **全部明细**：CSV，每行一项，列为行号、对象、路径参数、查询参数、请求体（JSON）、修改前（AI 提供）。下载链接与卡片同时有效（60 分钟）；点「重新发起」时生成新链接。
- 卡片有效期、只有提问人本人能点、过期后可重新发起等规则，与单项确认卡相同。

## 执行

点「确认执行」后：

1. 核验点击人、有效期（与单项确认卡相同），批次状态改为 `submitted` 并提交。
2. 重建提问人的代理上下文，对整批做一次复查：系统与操作仍可见、风险未变、仍允许写入、`op_digest` 未变。不通过时整批不执行，卡片说明原因。
3. 入队一个执行任务（`kind = systems_batch_run`），卡片改为进度卡。

执行任务**串行**处理：

- 按行号取下一项 `pending`，先把状态改为 `sending` 并提交，再用 `prepare` 拼出请求、`send` 发出（幂等请求头取该项的幂等键），然后写回结果和状态。
- **失败后继续**：业务系统返回非 2xx 记 `http_error`，连不上或超时记 `unreachable`，接着处理下一项。
- **环境变化就停**：执行中途员工被收回写入权限、系统停用或改为不经代理、提问人账号不可用时，剩余各项记 `skipped`，结束执行。这类情况每一项都会失败，继续跑没有意义。
- **分段执行**：每处理 20 项或运行超过 60 秒，任务就结束本段并入队下一段（`dedupe_key` 含批次和段号），让同一个员工的其他任务有机会插进来，也避免单个任务跑太久。每段重建一次上下文，业务令牌不会过期。
- **重启恢复**：开始一段时，如果有项还停在 `sending`（上次发出后没来得及写回），记为 `unknown`（结果未知，不重发），然后继续处理后面的项。
- **进度卡**：每段结束时更新一次卡片，例如「已处理 420 / 1000：成功 417，失败 3」，带「停止执行」按钮，只有提问人本人能点。点了之后，当前这项完成后停止，剩余各项记 `skipped`。

全部处理完（或被停止）后：

- **结果卡**：标题为「已完成」（全部成功）或「没有全部完成」。正文给出成功、失败、结果未知、未执行各多少项，再列前 10 个失败项（行号、对象、状态码、摘要），以及完整结果 CSV 的下载链接（在明细列之后加上状态、状态码、摘要）。
- **交回模型**：与单项确认卡一样续接原会话，结果作为数据交给模型：各类计数、前 20 个失败项的摘要、结果文件说明，并要求抽查读回几项核对、如实汇报，失败项不要自行重试，先告诉用户。

## 安全

- 批量只是把「逐条提议、一次确认」换成「一次提议、一次确认」，确认本身不能跳过。执行时平台只发出暂存的那一份，参数变了就要重新提交、重新确认。
- 数据文件只认本轮本人上传的；每行和单项调用走同一套校验，不存在只有批量才能绕过的检查。
- 卡片上的统计和抽样完全来自暂存的请求；`target`、`before` 由模型提供，在卡片上注明以明细中的请求为准。
- 请求、结果摘要加密存储，不写进日志；明细 CSV 放在对象存储，链接有时效。
- `destructive` 仍然限制在 50 项以内；`financial` 永远不代理。

## 测试

- 提交：上传文件归属与过期校验、逐行校验与行号报错、重复行、超出上限、`destructive` 的 50 项上限、每轮只能一批、不能确认的轮次拒绝。
- 确认卡：字段统计、少数取值优先进入抽样、同一对象重复提示、抽样可复现、1000 项时卡片不超过 28 KB、链接随重新发起更新。
- 执行：严格按行号串行；失败后继续；收回写入权限后剩余各项记 `skipped`；停在 `sending` 的项恢复后记 `unknown` 且不重发；停止按钮；分段续跑；幂等键在重跑时不变。
- 结果：结果卡大小、计数、前 10 个失败项；续接给模型的内容。
- 单项写操作的现有测试保持不变。

## 待定

- 业务系统长时间连不上时，1000 项会逐个超时，最坏要跑几个小时。是否在连续 N 项 `unreachable` 后自动暂停，并在卡片上让提问人选择继续或停止？
- 是否需要「重试失败的」按钮：把失败项重新组成一批，发一张新的确认卡。
- 是否限制整批执行的总时长。

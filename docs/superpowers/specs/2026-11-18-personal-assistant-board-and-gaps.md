# 个人助理：事项总表与能力缺口

## 背景

个人助理上线一段时间后，所有者与助理各自总结出两类问题。

**所有者看不清全貌。** 他不知道现在有哪些待处理的事、哪些有人（助理、子任务、公共员工）在跟、哪些停了在等他、哪些要到以后再回看。数据其实大多已经有了，只是散在几处：

| 想知道的 | 现在在哪 | 缺什么 |
|---|---|---|
| 有哪些事 | 待跟进（`assistant_followups`，四类 decide / promised / waiting / remind） | 早报摘要、「我的助理」页、审批系统各露一部分，没有一张总表 |
| 谁在办 | 子任务（`assistant_jobs`，含调度公共员工的 `bot_help`） | 与待跟进只有 `job_id` 弱关联；没有「同事在办」「所有者自己在办」 |
| 停了、等他 | `needs_owner`、`blocked` 的子任务、在途审批单 | 没有「最近一次进展」时间，判断不了停滞；纯决策（不涉及写操作）不进审批系统 |
| 以后回看 | `review_on` / `due_on` | 只有到日子才冒出来，平时看不到排期 |

**助理办不成事，也说不清缺什么。** 助理自述：从上线到现在，做的基本是看消息、记待跟进、发提醒，真正替所有者办完的事很少。原因是能用的工具大多只到飞书——没有代码仓库的访问、没有业务数据的只读通道、不清楚云签名代理放行了哪些产品；它要现查一遍运行环境才知道自己缺什么，查完也只是写成一段话。所有者因此不知道该开什么权限、开了能换来什么。另外它自己承认做得太保守：有些事凭现有权限也能先只读推进，却直接推后成了提醒。

## 目标

1. 一张总表回答「有什么事、谁在办、卡在哪、多久没动了」，飞书里和「我的助理」页都能看。
2. 「等所有者」的事在总表里集中成一组：写操作仍按现有规则走审批系统或确认卡，纯决策仍按现有的当面处理流程，总表把两者列在一起。
3. 能力缺口结构化：缺什么、卡住了哪几件事、怎么开通；按解锁事项数排序给所有者；开通后相关事项自动续接。
4. 助理先用已有权限只读推进，查不了的写清楚卡在哪个权限上，而不是只记一条提醒。

## 不做

- 不改待跟进的四类划分；「卡在哪」由分类与新字段推出，不新增分类。
- 不让助理自己去要密钥：凭证仍然只走个人凭证表单，令牌不在聊天里出现。
- 不放宽写操作规则：写操作照旧在场确认卡、不在场审批系统。
- 不替所有者在业务系统里自动通过权限申请。

## 待所有者确认的决策

D1 已由所有者确定，其余按我的默认写进了设计，确认或改掉后再进计划。

| # | 问题 | 结论 / 默认 |
|---|---|---|
| D1 | 不涉及写操作的纯决策也进审批系统吗 | **已定：不进。**仍按在场 / 不在场区分，沿用现有的当面处理设计（见第三节） |
| D2 | 总表以飞书为主还是以页面为主 | 两边都做；飞书是主入口（「看板」指令和早报首段），页面给完整视图 |
| D3 | 哪些事助理可以直接起草、提交给所有者批 | 第一期不放开新的类别，只在提示词里明确「凡是写操作都可以起草成待批单，不要只提醒」；更大的授权范围另议 |
| D4 | 停滞阈值 | 进行中的事 2 个工作日没有进展；等别人的事过了 `due_on`，或 5 个工作日没有进展 |

## 一、事项状态

### 新字段

`assistant_followups` 新增：

- `handler`：谁在办。`assistant`（助理自己）/ `job`（子任务，含调度公共员工，指向 `job_id`）/ `person`（某位同事）/ `owner`（所有者自己）。默认 `assistant`；挂上子任务时由平台自动改成 `job`。
- `handler_name_enc`：`person` 时的同事称呼，封存方式同标题。
- `progress_at`：最近一次进展的时间。平台在以下时候写入：新建、`followup_update` 或新工具 `followup_progress`、关联子任务状态变化、关联审批单状态变化、关联缺口状态变化。
- `gap_id`：卡住它的能力缺口（第四节），可空。

`assistant_approvals` 新增 `followup_id`（可空）：由某条待跟进引出的审批单记在它名下，总表里「等你」一栏能直接带出审批单。

### 新工具 `followup_progress`

参数：`id`、`note`（一两句话）。往备注末尾追加一行带日期的进展，并刷新 `progress_at`。备注超长时丢掉最早的进展行，保留开头的来龙去脉。这样「多久没动了」由真实进展决定，而不是看助理有没有改过标题。

### 状态推导

每条未关闭的待跟进推导出一个**阶段**（优先级从上到下，命中即停）：

1. **卡在权限**：`gap_id` 指向未解决的缺口。
2. **等你**：`needs_owner`，或分类为 `decide`，或有在途审批单（`followup_id` 指向它的 pending 单）。
3. **等别人**：分类为 `waiting`，或 `handler = person`。
4. **排期**：`review_on` 在今天之后（含 snoozed）。
5. **在推进**：其余（助理或子任务在办）。

另外独立判断**停滞**（对「在推进」「等别人」两个阶段生效，阈值见 D4），按阶段和停滞标记分组展示。阶段只在读取时计算，不落库，免得两份状态互相打架。

## 二、展示

### 飞书

- **「看板」指令**：所有者私聊发「看板」（或「有什么事」），平台直接回一张卡片，不开助理轮次。卡片分六组：等你 / 停滞 / 在推进 / 等别人 / 卡在权限 / 排期（未来 7 天）。每组最多 10 条，多的只说个数；每条一行：编号、标题、谁在办、多久没动。「等你」的条目带「现在处理」按钮（沿用摘要里的回复按钮），有审批单的带审批链接。
- **早报**：例行 `morning_brief` 摘要的第一段换成总表的计数行与「等你」「停滞」两组明细。现有的三节（等你批的、等你当面处理的、我处理了这些）里，前两节并入总表，第三节保留。

### 「我的助理」页

新增「总表」视图，设为默认视图，分组同飞书；条目展开后显示进展记录、关联的子任务、审批单和缺口。现有的待跟进、子任务列表保留为明细页。接口为 `GET /me/assistant/board`，只读，只有所有者本人能看，与其他「我的助理」接口一样记访问日志。

## 三、等你：沿用现有分工，在总表里汇总

所有者已定：不涉及写操作的纯决策不进审批系统，仍按在场 / 不在场区分，现有设计尽量保留。

- **写操作**：不变。在场发飞书确认卡，不在场进审批系统。
- **纯决策**：不变。在场时助理当场问；不在场时记成 `decide` 或 `needs_owner` 的待跟进，进摘要「等你当面处理」一节，带「现在处理」按钮，点了开一轮在场轮次当面办。
- **本设计只加汇总**：总表的「等你」一组把这两类列在一起。写操作那一行带审批链接，纯决策那一行带「现在处理」按钮；组标题分别显示两类的数量，所有者能看出哪些要去审批系统、哪些要在私聊里办。
- 唯一的小改动：纯决策的待跟进可以在备注里写助理的建议（「建议选 A，因为……」）。总表与摘要把这条建议显示在标题下面，所有者点「现在处理」前就能先看到。这一条由提示词约定，不加新工具。

## 四、能力缺口

### 4.1 每轮告诉助理它有什么

平台在组装每一轮时已经知道本轮挂了什么，把这份清单放进**本轮块**（不放稳定段，以免打掉缓存）：

- 飞书个人授权：已授权的业务域，以及最近被拒的权限。
- 业务系统：本轮挂上的系统名称与读写级别（业务令牌、目录代理、MCP 类系统）。无人在场的轮次标明哪些被收起。
- 云签名代理：放行的产品与动作级别。
- 个人凭证：已有凭证的名称（不含值）。

节点上的命令行工具（比如代码仓库的命令行客户端）平台不知道，由助理在每日例行整理时自检一次，结果记进置顶页的「运行环境」一节。

### 4.2 登记缺口

新表 `assistant_gaps`：

- `kind`：`feishu_scope` / `business_system` / `cloud_product` / `credential` / `node_tool` / `other`
- `key`：规范化标识（权限名、系统标识、产品名、凭证名），与 `kind` 一起在同一位助理内唯一，用来去重
- `need_enc`：要什么（一句话）
- `status`：`open` / `requested`（已发起开通）/ `resolved` / `declined`（所有者明确不开）
- `fix`：开通方式，由平台按 `kind` 与 `key` 判定（见 4.3），不由助理填
- 时间戳：创建、状态变化

新工具 `gap_report`，参数为 `kind`、`key`、`need`、`followups`（被卡住的编号列表）。平台按 `kind + key` 合并已有记录，把这些待跟进的 `gap_id` 指过去。同一缺口卡住的事越多，排序越靠前。

### 4.3 告诉所有者怎么开

缺口出现在三处：总表「卡在权限」一组、每周回顾、「我的助理」页的缺口清单。按解锁的事项数排序，每项一行：缺什么 → 能解锁哪几件事 → 怎么开。

「怎么开」按种类给出可以直接点的入口：

| 种类 | 入口 |
|---|---|
| 飞书权限 | 现有的就地授权卡片 |
| 个人凭证 | 现有的个人凭证表单（安全表单，不经聊天） |
| 业务系统 | 业务系统目录里该系统给助理开启的入口；系统自带权限申请流程的（比如 MCP 系统的申请工具），由助理以所有者身份代为提交申请，审批走该系统自己的流程，`status` 改为 `requested` |
| 云签名代理产品 | 只能由平台管理员配置：显示「联系管理员」和要放行的产品 |
| 节点工具 | 只能由节点管理员安装：显示要装什么 |

所有者也可以点「不开」，`status` 改为 `declined`。相关待跟进回到原阶段，助理按「这条路走不通」处理，不再反复提。

### 4.4 开通后自动续接

符合「权限融在使用过程中」的原则：缺口变成可用之后，平台把关联的待跟进刷新 `progress_at`，并开一轮交回轮次，告诉助理「缺口 X 已可用，F0xx 可以继续」。判断「已可用」的方式：

- 飞书授权与个人凭证：已有的完成回调。
- 业务系统、云代理产品：每轮组装能力清单时比对，发现新出现的就把对应缺口置为 `resolved`。
- 节点工具：助理自检时调 `gap_report` 把它标为已解决（工具参数允许 `resolved: true`，仅限 `node_tool` 与 `other`）。

## 五、提示词规则

待跟进规则段补三条：

1. **先查后提醒**：交回的事凡是现有权限能只读查的，先查完，把结论写进进展，再决定要不要找所有者。
2. **卡住要登记**：查不了、办不了的，调 `gap_report` 写清缺什么，不能只写一句「需要权限」。
3. **提醒要带下一步**：发给所有者的每条提醒都要说清谁在办、下一步是什么、需要他做什么。没有下一步的事不发提醒，只更新进展。

另外明确：凡是写操作都可以起草成待批单交给所有者批，不要只提醒他自己去做（具体范围见 D3）。

## 分期

1. **总表**：第一节的新字段与 `followup_progress`、状态推导、`/me/assistant/board`、飞书「看板」指令、早报改版、页面总表视图、第五节的规则 1 与 3。**已实现**（迁移 0114），与本规格有两处不同：
   - 规格写「早报第一段换成总表」，实现是每次摘要卡片都以总表计数行开头、先列等你与停滞（早报内容本来就随摘要发出）；
   - 被卡住但没挂在待跟进上的子任务不再单独列在页面上（原「等你出手」有），助理按新规则应把它挂到对应条目。
2. **缺口**：每轮的能力清单、`assistant_gaps` 与 `gap_report`、缺口清单与「怎么开」入口、开通后续接、规则 2。
3. **申请代办**：审批单挂靠待跟进（`followup_id`）、代为提交业务系统的权限申请。

每期各自独立上线。第一期不依赖其他两期，第一期的「等你」一组里，写操作的审批单先按现有方式单独列出，第三期挂靠后再归到对应条目下；第二期的「卡在权限」一组在第一期先按空处理。

## 测试

- 状态推导：每个阶段与停滞判断的边界（工作日计算、snoozed 到期、多个条件同时满足时的优先级）。
- `followup_progress`：备注超长时保留开头、丢最早的进展行。
- 「看板」指令：只有所有者本人触发得了；不开助理轮次；空清单的文案；每组超过 10 条时只显示个数。
- 缺口：按 `kind + key` 去重；`declined` 后不再出现在清单里；能力清单比对后自动置为 `resolved` 并开续接轮次（只开一次）。
- 「等你」一组：在途审批单与 `decide` / `needs_owner` 待跟进都列出，两类的按钮各自正确，计数分开。
- 本轮能力清单不进稳定段（稳定段逐字不变的既有测试继续通过）。
- 加密台账：新的 `_enc` 列登记进 `sealed.COLUMNS`。

## 待核实

- 助理节点能否以所有者身份调用业务系统目录里的 MCP 类系统，以及无人在场的轮次里哪些被收起。这决定助理自述里「业务数据只读通道」的缺口能否走 4.3 的自助入口，还是只能由管理员开。
- 代码仓库只读访问：节点上是否装了命令行客户端；令牌走个人凭证是否满足仓库所在组织的要求。

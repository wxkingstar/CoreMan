# 平台代理写操作确认卡

## 背景

业务系统有两种令牌下发方式：

- `env`：令牌放进运行环境，Agent 自己调用。写操作只靠提示词要求「先说明、等确认」。
- `proxy`：平台代为调用（`systems_call`），令牌不进运行环境。

`env` 模式下平台拦不住调用。曾有一次，用户确认了一句「补原价」，Agent 就写了个循环，用同一个令牌逐条调写接口 5 万多次，下游事件队列因此积压。

`proxy` 模式能管住可调范围、调用次数和风险等级，但它现在的写操作规则是：员工授权开了 `allow_write` 就直接执行，**没有逐次确认**。在把高风险系统从 `env` 切到 `proxy` 之前，必须先补上确认这一环。

## 原则

1. **写操作由平台强制确认，不靠模型自觉。** 模型只能「提议」写操作，执行权在平台手里，用户点了确认，平台才调用。
2. **卡片内容取自实际请求。** 方法、路径、参数、请求体都由平台按暂存的请求渲染，模型写的说明另起一栏，标明「AI 说明，未经平台核实」。
3. **点确认后原样执行，不经过模型。** 用户确认的是什么，平台就执行什么。参数改了就要重新确认。
4. **确认有上限。** 一张卡片最多 20 个写操作，超过就拒绝，引导用户走业务系统的批量功能。从机制上杜绝逐条调用几万次。
5. **复用群聊写入确认卡的做法**（`feishu_docs/confirm.py` + `worker/group_write_cards.py`），不另起一套。

## 范围

| 风险等级 | 现在（proxy） | 改后 |
|---|---|---|
| `read` | 直接执行 | 不变 |
| `write` | 有 `allow_write` 就直接执行 | 有 `allow_write` 才能提议；**必须确认后执行** |
| `destructive` | 禁止 | 与 `write` 相同：有 `allow_write` 才能提议，必须确认后执行 |
| `financial` | 禁止 | 永远禁止 |

`allow_write` 的含义不变：它决定这个 AI 员工能不能提议写操作。确认是额外加的一道，不能关掉。

## 流程

```
模型调 systems_call（write 操作）
  → 平台做所有现有检查（目录可见、权限码、参数校验、allow_write）
  → 暂存到本轮的「待确认批次」，不调用业务系统
  → 返回 pending_confirmation：「已加入待确认列表，本轮结束后发确认卡。
     告诉用户需要确认，不要说已经完成。」
本轮结束（worker 收尾）
  → 本轮有待确认批次：给提问人发一张确认卡（这一轮里的所有写操作合在一张）
用户点「确认执行」
  → 核验：点击人 = 提问人、卡片未过期、授权与目录仍然允许
  → 以提问人身份签发令牌，按暂存的请求逐条执行，遇到第一个失败就停
  → 卡片更新为逐条结果
  → 续接原会话：把执行结果交给模型，让它读回并汇报
用户点「取消」或卡片过期
  → 不执行；续接时告诉模型「用户取消了，不要重试」（过期的不续接）
```

### 为什么本轮结束才发卡

一次批量修改往往在一轮里连续提议多个写操作。每个都发一张卡，用户要点 N 次，而且很容易只点了一部分。合成一张卡，一次确认一个完整的意图，也和「确认范围就是说明范围」对应。

## 暂存

使用 `InteractionState`，`kind = "systems_write"`，每个任务（一轮）最多一条 `open` 记录：

```jsonc
{
  "origin_task_id": 123,
  "user_id": "…",              // 提问人；只有他能点
  "chat_id": "…",
  "items": [
    {
      "system": "shop",
      "operation_id": "updateListing",
      "op_digest": "…",        // 编译后操作定义（方法、路径、风险、校验规则）的摘要
      "path_params": {"id": "L1001"},
      "query": null,
      "body": {"price": 19.9},
      "idempotency_key": "…",  // 暂存时生成，见下文
      "note": {                // 模型给的说明，选填，只用于展示
        "target": "挂牌 L1001",
        "changes": [{"field": "price", "before": "21.9", "after": "19.9"}],
        "impact": "…",
        "rollback": "…"
      },
      "digest": "…"            // (system, operation_id, 参数) 的摘要，用于去重
    }
  ]
}
```

- 请求体可能含业务数据，`items` 整体加密存储（以任务编号为 AAD），不写进日志；`state` 里明文只有来源任务、提问人、会话和条数。
- 同一批里参数完全相同的项只留一个。
- 已经满 20 项时，第 21 个提议返回 `confirmation_batch_full`：「一次最多确认 20 个写操作。更多的修改请让用户在业务系统里用批量导入或批量编辑完成，不要拆成多轮逐条提交。」
- 每轮 30 次的 `systems_call` 上限照旧，提议也计入。

### `systems_call` 新增的选填参数

```jsonc
"note": { "target": "…", "changes": [...], "impact": "…", "rollback": "…" }
```

只对写操作有效，读操作忽略。提示词要求模型先用读操作查到修改前的值再填 `changes`，平台不核实。

## 确认卡

纯文本渲染，不让参数里的 `@`、链接等标记生效（与群聊写入卡相同）。

```
确认：执行 3 个业务系统写操作                                    [橙色标题；含 destructive 为红色]

1. [商品后台] 修改挂牌价格  PUT /listings/{id}
   id = "L1001"
   请求体 = {"price": 19.9}
   AI 说明（未经平台核实）：对象："挂牌 L1001"；price："21.9" → "19.9"
2. …
3. …

[确认执行]  [取消]
只有提问人能操作，将以提问人身份按顺序执行，遇到失败即停止，10 分钟内有效。
```

- 每项的路径参数、查询参数、请求体都按实际值显示，每个值最多 500 字符，超出截断并标明。
- 卡片超过平台大小限制时，只完整显示前几项，其余项只显示操作名和路径参数，并注明「另有 N 项，共 M 项」。确认对整批生效。
- 卡片发到原会话。群聊里也发在群里（与群聊写入卡一致），但只有提问人点击有效。

## 点击后的执行

在 worker 的卡片回调里处理（新增 `worker/systems_write_cards.py`，结构照搬 `group_write_cards.py`）：

1. **核验**：卡片来源（`group_card_scope` 或私聊对应的 scope）、点击人 = `user_id`、`status == open`、未过期。
2. **先落库**：`status = submitted`，提交事务后再调业务系统。中途崩溃、任务重试都不会再执行一遍。
3. **逐项复核**，每一项都要满足：
   - 系统仍为 `proxy`，员工仍有该系统授权且 `allow_write` 为真；
   - 当前目录里仍有这个操作，风险仍为 `write`，`op_digest` 与暂存时一致（目录刷新后操作定义变了就不执行）；
   - 提问人的权限码仍然允许这个操作；
   - 参数按当前目录重新校验，仍然通过。

   任一项不满足，整批都不执行，卡片显示原因。
4. **执行**：以提问人身份签发令牌（`purpose="proxy"`），按顺序逐项调用 `proxy.call` 的同一套请求构造与响应处理。遇到失败（非 2xx 或连接失败）就停，后面的项标记为「未执行」。
5. **审计**：每项都写一条 `system_calls`。`outcome` 增加 `confirmed_ok` / `confirmed_http_error` / `confirmed_unreachable`，提议时写 `proposed`。取消、过期只体现在 `interaction_states.status` 上。
6. **更新卡片**：逐项显示 ✅ / ❌（状态码）/ 未执行。
7. **续接**：照 `group_write_cards._resume` 的方式，向原会话追加一轮（`serialize_session`、`stale_confirmed`），payload 键为 `systems_write_result`，内容是逐项结果（状态码 + 截断后的响应），并附一句：「已按确认执行，结果如下。读回关键字段核对后如实汇报；失败的项不要自行重试。」

### 幂等键

编译后的目录本来就保留了 header 参数。操作里名为 `Idempotency-Key` 或 `X-Operation-Request-Id` 的 header 由平台填写，不再算作「不支持的必填参数」。暂存时为每一项生成一个 UUID，执行时放进对应的请求头；直接执行的读操作每次用新值。

- 这样一来，必须带这两个请求头的写接口就能走代理了（现在 `build_request` 遇到必填 header 会直接报错）。
- 键在暂存时就固定下来，重复执行（重复点击、任务重试）会被业务系统按同一个键去重。

其他 header 参数仍不支持。

## 不能确认的场景

以下回合没有能当场点卡的人，写操作一律返回 `confirmation_unavailable`，并说明「这一轮无人能确认，不执行写操作，只说明应该怎么做」：

- 定时任务；
- AI 员工之间互相求助的协作回合；
- 由卡片按钮触发的回合（这种回合发出的确认卡过不了来源核验，与群聊写入相同）；
- 通过 API 驱动、没有接到 IM 会话的任务；
- 第一期的企业微信会话（见「待定」）。

## 提示词

`PROXY_RULES` 的写操作部分改为：

> 写操作（risk=write）调用 `systems_call` 只会进入待确认列表，平台会在本轮结束时发确认卡，由提问人点确认后执行。调用前先用读操作查到要改的对象和当前值，在 `note` 里写清对象、修改前后的值、影响和恢复方法。提议完后告诉用户需要在卡片上确认，不要说已经完成。一次最多 20 个写操作；更多的修改请用户在业务系统里批量处理，不要逐条提交。用户取消或卡片过期后不要重提，除非用户再次明确要求。

这段话放在 system prompt。Codex 续聊不会重读 system prompt，所以本轮块里也要加一句提醒（与 `ENV_WRITE_REMINDER` 相同的做法）。

## 测试

- 写操作提议后不调用业务系统，返回 `pending_confirmation`；本轮结束后只发一张卡。
- 同一轮提议 3 个写操作，卡片显示 3 项；第 21 个提议被拒绝。
- 只有提问人点击有效；过期、重复点击都不会执行；`submitted` 之后任务重试也不会再执行。
- 目录刷新后操作定义变了、`allow_write` 被关了、权限码被收回：点确认后整批都不执行。
- 第 2 项失败时第 3 项不执行，卡片和续接结果逐项正确。
- 幂等键在暂存时生成，执行时出现在请求头里，两次执行用的是同一个键。
- 定时任务、协作回合、卡片触发的回合里提议写操作，返回 `confirmation_unavailable`。
- 业务系统在响应里回显令牌时会被打码，与现在一致。

## 决定

1. **`destructive` 确认后可以执行**，与 `write` 走同一张卡。批次里有 `destructive` 项时卡片标题为红色，该项标「不可恢复」。
2. **第一期只做飞书**，企业微信回合里写操作返回 `confirmation_unavailable`。
3. **有效期 10 分钟**，与群聊写入卡一致。
4. **20 项上限全平台固定**。

## 补充：大结果与文件转存

同一个改动里，代理调用的大结果和文件改为转存到平台的短期附件存储，模型拿到预览和链接：数据结果只有本轮运行环境能下载（目录 MCP 凭据鉴权），文件给 1 小时有效的签名链接。主存储新增 `S3_ADDRESSING`，以便接入只认 virtual 寻址的 S3 兼容服务（如阿里云 OSS）。细节见 `docs/business-system-catalog.md`「大结果与文件转存」。
